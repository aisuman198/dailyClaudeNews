新たに追加された Agent Skills 6 種は、類似企業分析（バリュエーション倍数・経営指標、データ更新も容易）、DCF モデル（フリーキャッシュフロー予測・WACC 計算・シナリオ切り替え・感応度表）、デューデリジェンスデータパック（データルーム文書から財務情報・顧客リスト・契約条件を Excel に出力）、企業ティーザーおよびプロファイル（ピッチブックや買い手リスト向け概要）、決算分析（四半期転写・財務指標・ガイダンス変化・マネジメントコメント抽出）、カバレッジ開始レポート（業界分析・企業詳細・バリュエーションフレームワーク）。Claude for Excel と同様に Max・Enterprise・Teams ユーザーへのプレビュー展開となる。

#### [LLM による大規模フォーマル検証の実現](https://www.anthropic.com/research/formal-verification)
<sub>anthropic-blog ・ 2026-11-17</sub>
<sub>**原題**: Formal Verification</sub>

Anthropic は Theorem との共同研究として、LLM を使った大規模なフォーマルソフトウェア検証の成果を発表した。Claude が RISC-V アセンブリコードレベルで 100 を超える実世界のオープンソースライブラリに安全性証明を適用したとしており、アセンブリコードレベルで AI が本番ソフトウェアのフォーマル検証を大規模に実施した初の事例だと主張している。

フォーマル検証はソフトウェアの正確性を数学的に証明する手法だが、従来は膨大な専門的労力を要した（例として、seL4 カーネルは実装に 2 人年、検証に 20 人年かかった）。今回の取り組みでは、Google の OSS-Fuzz イニシアティブに収録されたオープンソースライブラリのファズテストを仕様（spec）に変換し、任意の入力（64 MB 未満）に対してプログラムがクラッシュしないことを証明するアプローチをとった。証明は RISC-V にコンパイルされた実行バイナリに対して行われ、Theorem の RISC-V 命令セマンティクスおよび Linux プロセスセマンティクスを使用する。これらの証明は、プログラムがシングルスレッドの静的バイナリとして固定メモリバジェット内で RISC-V CPU + Linux OS 上で動作するという条件を前提としている。

数週間のうちに 123 の OSS-Fuzz ライブラリの 239 エントリポイントについてクラッシュなしの証明を完了した。生成された Rocq の証明コードは合計約 1 億 8,000 万行で、1 つの証明の典型的な行数は約 60 万行、対象バイナリは中央値 18,000 命令の RISC-V バイナリとなっている。これらの証明コードは人間による手動確認をほぼ必要とせず、Rocq 証明チェッカーが仕様に対して検証する。

証明過程でバグも複数発見された。ファザーでは検出困難なものとして、約 20 MB かつ特定レイアウトの入力でのみ発生する解凍器のカウンターアンダーフロー（範囲外書き込みに至る）、64 MB の入力と 2 GB のメモリを必要とする画像デコーダの範囲外読み取り、同一ファイルへの 2 ハンドルにまたがる特定操作シーケンスで発生する範囲外読み取り、libexpat における CVE-2026-56132 の再発見（深くネストした入力が必要）などが報告されている。クラッシュを引き起こさない論理バグも発見されており、ファイルロード制限機能が常には有効にならないケースが例として挙げられている。

OSS-Fuzz 以外の検証例も実施されている。RFC 1950 仕様の形式化と Linux カーネルの zlib 実装が仕様に準拠することの x86 バイナリレベルでの証明、Python インタープリターの Rust 実装と CPython セマンティクスとの同一性検証（170 万件のランダム生成 Python プログラムで 99.95% の一致、残る差異は既知のコーナーケース）も実施された。広く使われているある PDF リーダーの検証試みでは、1 週間で通常 1 年分の報告数に相当するセキュリティバグを発見したとも述べられている。

効率改善の見通しについても記載されており、36 件の小規模検証タスクの比較では Opus 5.5 は Opus 5 より約 40% 少ないトークンで同タスクを証明した。証明の共有ワークスペース（エージェント間で証明ファイルをコピー・適用できる仕組み）では単独作業時より 17% 少ないトークンで済んだ。Theorem はこのパイプラインを他のオープンソースプロジェクトに展開することを提案しており、開発者が自身のコードで検証を始めるための Claude スキルも公開している。

#### [堅牢な安全性評価の構築](https://www.anthropic.com/research/building-strong-safety-evaluations)
<sub>anthropic-blog ・ 2026-11-17</sub>
<sub>**原題**: Building Strong Safety Evaluations</sub>

Anthropic の研究チームが、AI 安全性評価の構築・運用に関する推奨事項をまとめた記事を公開した。安全性評価はモデルのデプロイ可否・セーフガードの設計・次の安全トレーニング・研究の方針に直結する重要な判断基準であり、質の高い評価の作り方は難しいと指摘している。

**チームの構成と安全な実行**：評価チームには方法論の専門家とドメイン専門家の両方が必要とされている。方法論専門家はサンプリング・採点・統計を担い、心理学者・生物学者・政治学者などのドメイン専門家は現実的かつ多様なテストケースの設計と「何が害か」の判断を担う。どちらが欠けても評価の質が低下するとしている。評価の実行はサンドボックス環境・インターネット遮断・リアルタイム監視の下で行う必要があり、Anthropic は最近の自社インシデントを受けて評価環境を強化し、インターネットアクセスを伴う評価の多くをいったん停止したと述べている。

**構成の妥当性（Construct Validity）**：測定対象の設計が重要とされている。例として、自傷・自殺リスクに関する評価では「拒否率」は不適切な指標であり、危機状態のユーザーに対して単に応答を断ることそのものが失敗に相当するとしている。Anthropic では会話全体を通じて適切な応答が維持されたかを問う「適切応答率」をマルチターン評価で計測している。生物学・サイバーセキュリティなど二重用途（dual-use）領域では、正当なリクエストには応答しつつ害につながる操作的詳細は提供しないことが適切な応答とされる。単一ターン評価では有害リクエストと無害リクエストをペアにし、それぞれ「有害応答なし率」と「拒否率」の 2 軸を計測する。現時点で Anthropic の単一ターン評価では全モデルの有害応答なし率が 94〜98% の範囲にあり飽和状態にあるため、主として既知の失敗モードの回帰確認に使用されている。

**リアリティのある評価シナリオの作成**：マルチターン評価ではドメイン専門家が仕様（ペルソナ・状況・戦術・トーンなど複数の次元）を記述し、最初のターンを固定した後、別の Claude モデルが仕様に基づいて後続の「ユーザー」ターンを生成する。この方式により事前に書かれたスクリプトでは再現できない多様な展開が可能となる。グレーダーモデルが各転写をリスク領域別のルーブリックに照らして採点し、「適切」と判定された会話の割合を報告する。ロマンス詐欺のテストスイート例として、単一のメッセージでは違反が明確でなくとも、会話全体のパターンから詐欺的意図を認識し適切な応答を維持する能力を評価する構成が示されている。複数ターンにわたる自傷・自殺リスク評価の例では、シミュレートされたユーザーが会話の早い段階で離職や家族の死などの不安定化イベントを開示し、後の会話で一見普通に見える質問をするという構成が紹介されている。

評価は 16 のポリシー領域・7 言語・複数のプロダクト表面にわたって実施される。採点（グレーダー）については、LLM ジャッジを使用していること、グレーダーが不具合を起こしていても採点が継続されてしまう可能性があること、基盤モデル更新時に採点基準が微妙にずれる可能性があることを指摘し、アラート設定・人間によるサンプル確認・採点のシンプル化などを推奨している。

検証ループの価値として、エージェントが自身の出力を検証できる仕組みがあることで一度に数十〜数百のエージェントを並列実行できるようになると述べている。内部テストでは、別のグレーダーが Claude の作業をルーブリックに基づいて確認する方式が、標準的なプロンプトループより最大 10 ポイントのタスク成功率向上をもたらした（効果は最も難しいタスクで顕著）。

投資価値の高いテストの種類として 3 種が挙げられている。**E2E テスト**は実際のユーザーフローを検証するもので、機能全体が動作するかどうかを確認するため、ごまかしが効きにくい。エージェントに実際の動作環境を使わせ、CDP やシミュレーター、API ハーネスでアプリを起動・操作・検査させることを推奨している。**プロパティテスト**はエッジケースを対象とし、fast-check（JS/TS）・Hypothesis（Python）・proptest（Rust）などのライブラリで数千のランダム入力を生成してプロパティが保持されるかを確認する。ラウンドトリップエンコーディング・不変条件・冪等性・等価性などが具体例として挙がっている。**差分テスト**は旧システムを正解として新旧両方に同じ入力を流し、結果の差異からバグを検出する方式で、大規模マイグレーションに有効とされる。

Claude Code チームの実践として以下が紹介されている。検証とはアプリをエンドツーエンドで実際に動かすことを意味し、`verify` という名前のスキルを `.claude/skills/` フォルダに配置して使用する。テストの失敗が 3 ラウンドを経ても解決しない場合に人間の介入を求める。コードのオーナーが自身のチェックを書き、差分から読み取れるトリガーを持つ 39 項目の信頼性チェックリストを維持している（例：セッションストレージやメッセージ型が変更された際に旧転写が安全に読み込めるかを確認する項目）。レビュアーは増やすのではなく一人のレビュアーを丁寧にチューニングする方針を採用しており、REVIEW.md を使ってレビュアーの着目点を明示している。変更自身がそれを評価するチェックを修正できないよう、REVIEW.md ファイルはプルリクエストのブランチからではなくベースブランチから読み込む。新しいゲートはまずオブザーブモードで試験導入し、ブロックされるはずだったコミットのログを確認してから強制モードに切り替える。ミスのあったケースはルールに変換する際、少なくとも 2 件の PR で出現し差分から識別可能な場合のみ候補とした上で、3 つのエージェントが反証を試み、人間がレビューして採用される。

#### [Claude Code の "File has not been read yet" / "File has been modified since read" / "File unchanged since last read" は放っておいてよい？（気にしなくていい場合と、止まったときの直し方）](https://qiita.com/homhom44/items/f4780d9853b16d4650ff)
<sub>qiita ・ 0pt ・ 2026-11-17</sub>

Claude Code の作業ログに出現する 3 種類の英語メッセージについて、それぞれの意味と対処法をまとめた記事。確認環境は Claude Code 2.1.326、macOS 26.6.2。

対象の 3 メッセージの意味は以下のとおり。①「File has not been read yet. Read it first before writing to it.」は Claude がまだ Read していないファイルを Edit/Write しようとした場合に返される。②「File has been modified since read, either by the user or by a linter. Read it again before attempting to write it.」は Claude が Read した後でユーザー・フォーマッタ・hook などがファイルを書き換えた場合に返される。③「File unchanged since last read. ...」は同じファイルを二重に読まないための案内であり、エラーではない。旧バージョンでの文言（「File has been unexpectedly modified」「Unchanged since last read」）は 2.1.326 では使われなくなっており、後継の文言に置き換わっている（作者は Claude Code バイナリ内の文字列を直接確認して検証している）。

これらはすべて Claude 自身に向けたメッセージであり、Claude が Read し直して処理を継続するため、ユーザーが介入する必要はない。同じエラーが繰り返されて作業が止まった場合のみ対処が必要となる。

作業が止まる原因として GitHub Issues で報告されているものとして以下が挙げられている。①保存時にファイルを書き換える PostToolUse hook（prettier --write、black など）が Edit 後にファイルを更新し、次の Edit を拒否させるケース（issue #3513、未解決。内容が変わらなくても書き込みでタイムスタンプが更新されるだけで検出されるとの指摘もある）。②Windows（MINGW / Git Bash）でのパス表記の不一致（`C:/` と `C:\` が別ファイルとして扱われる、issue #10437）。③Claude が Read を飛ばして Edit しようとするケース。対処として、フォーマッタの実行を作業終了後（Stop hook など）に変える、エディタの自動整形を一時的に無効にする、相対パスを使う（CLAUDE.md への記載が有効との報告あり）、依頼文に「まず Read してから編集して」と明示する、解決しない場合は `/clear` で会話を切り替えるといった方法が紹介されている。

GitHub issue #42264 に報告されていた「Unchanged since last read」で `/rewind` や `/compact` 後に本当に中身が必要でも内容が返ってこない問題は、2026 年 11 月 15 日付けで Claude Code 2.1.317 での修正が確認されて closed になったとも記載されている。
