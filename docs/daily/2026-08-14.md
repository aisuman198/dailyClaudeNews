#### [Conceptual Reasoning Index：AI の概念推論能力を評価するベンチマーク群の公開](https://alignment.anthropic.com/2026/conceptual-reasoning-index/)
<sub>hacker-news ・ 69pt ・ 2026-08-13</sub>
<sub>**原題**: The Conceptual Reasoning Index</sub>

Redwood Research（Emery Cooper、Caspar Oesterheld、Chi Nguyen、Alex Kastner）と Anthropic（Joe Benton、Ethan Perez）の共同チームが、AI の概念推論能力を評価する3つのベンチマーク群と、それらを集約した Conceptual Reasoning Index（CRI）を公開した。CRI は conceptualreasoning.ai で閲覧でき、新モデルとベンチマークのリリースに合わせて更新される。

公開の背景にある問題意識は次のとおりだ。現行の AI 学習は豊富なデータと信頼性の高いフィードバックに依存しているが、AI リスク軽減に関わる作業の多くは経験的・数学的に検証できないためモデルが苦手とする傾向がある。具体例として、より高度な AI についての推論（明確な参照クラスが存在しない）、AGI 乗っ取りや AI 支援クーデターのように一度の失敗が取り返しのつかない結果をもたらすシナリオ、研究アジェンダや政策介入の選択など長い時間軸にわたる意思決定、AI が持つべき価値観のように正解が存在しない問いなどが挙げられている。こうした特性から、経験的証拠に乏しく検証可能な答えのない問いについての推論能力――チームはこれを「conceptual reasoning（概念推論）」と呼ぶ――の改善が特に重要とされる。

3つのベンチマークの構成は以下のとおり。まず **LMCA（Language Model Conceptual Argumentation）** は、決定理論・哲学・先進 AI リスクなど多様なテーマにわたる専門家評価済みの概念的議論を集めたデータセットであり、アクセスはフォームによるリクエスト制となっている。次に **ACCoRD** と **DTBench** の2つが存在するが、これらの詳細は本文の取得範囲内では確認できない。3つのベンチマークを集約したものが CRI として提供される。

#### [マルチエージェントシステムにおけるパターンと問題点](https://www.anthropic.com/research/multiagent-systems)
<sub>anthropic-blog ・ 2026-08-13</sub>
<sub>**原題**: Multiagent Systems</sub>

Anthropic の Frontier Red Team が、マルチエージェントシステムにおける行動傾向と予期しない障害の実例を報告する研究を公開した。

報告は次の認識から出発している。モデル性能の向上に伴い、AI エージェントが共有コードベース・市場・社会システムで担うタスクが増加しており、エージェント同士のリアルワールドでの相互作用の増大が目前に迫っているとされる。現行の制度は人間の速度での監視を前提として設計されているが、将来的には一部の制度が人間と AI のハイブリッドに、速度やコストでエージェントが競争優位を持つ領域では完全にエージェントのみになる可能性があると述べられている。エージェント同士の相互作用の量は、人間同士または人間とエージェントの相互作用を上回る可能性があるとも指摘されている。

エージェントは人間と異なる特性を持つ。長時間稼働できる、大量の情報を即座に把握できる、任意の個人を超える広範な知識を持つ一方、confabulation（事実に基づかない情報の生成）やリワードハッキングへの脆弱性がある。複雑なマルチエージェント環境での実際の挙動についての知見はまだ少なく、個体レベルでは無害な行動傾向が、システム全体では望ましくない結果へと増幅されうる点が課題として挙げられている。

マルチエージェント協調が有効に機能しやすいのは、高度に並列化可能な問題（多数の独立したサブ問題に分割できる問題）で、かつエージェントが互いに専門化したり学習し合える余地がある場合とされる。具体例としてソフトウェア脆弱性発見タスクが紹介されている。通常はエージェントを個々のコードベースに割り当てて並列実行する方法が使われており、Anthropic 自身もオープンソースソフトウェアを検査する Project Glasswing でこのアプローチを採用しているという。マルチエージェント協調がさらに効果的かどうかを調べるため、45 体のエージェントそれぞれに専用の仮想マシンと共有フォーラムを与え、15 件のオープンソースプロジェクトから脆弱性を探索させ、互いの発見事項をピアレビューさせる実験を実施した（本文はここで途中終了している）。

#### [Claude の出力を AI モデルの学習に使用できるか](https://support.claude.com/en/articles/12326764-can-i-use-my-outputs-to-train-an-ai-model)
<sub>hacker-news ・ 85pt ・ 2026-08-13</sub>
<sub>**原題**: Can I use my Outputs to train an AI model?</sub>

Anthropic の Claude ヘルプセンターが、Claude の出力を AI モデルの学習に使用することに関するポリシーを明文化した記事を公開した。

ユーザーは自分の入力から生成された出力を所有するが、その出力を AI モデルの学習に使用することは原則として Anthropic の書面による許可なく禁止されている。Anthropic がこの制限を設ける理由として、次の3点が挙げられている。（1）安全性管理の喪失：Claude の出力を学習データとして使ったモデルには Anthropic の安全対策が引き継がれず、有害または危険な AI システムにつながりうる。（2）展開への可視性の欠如：そのようなモデルの使われ方を Anthropic は監視できない。（3）競合利用の問題：Anthropic のインフラと投資を使って直接の競合サービスを構築することになる。

**許可される使用**：Anthropic のモデルと競合しない専門的なモデルの学習には出力を使用できる。具体例として感情分析ツール、コンテンツ分類システム、要約ツール、情報抽出ツール、セマンティック検索ツール、異常検知ツールが挙げられている。また、出力を自社製品の機能に組み込んだり、顧客向けコンテンツ生成、データの分析・構造化、社内ワークフロー改善に活用することは認められている。

**禁止される使用**：汎用チャットボットの学習、オープンエンドなテキスト生成を目的としたモデルの学習、出力を学習ターゲットとして使用すること、学習手法のリバースエンジニアリングが明示的に禁止されている。第三者によるこれらの行為を支援することも規約違反とされている。

#### [労働者再訓練プログラムに関するエビデンスのレビュー](https://www.anthropic.com/research/reviewing-the-evidence-on-worker-retraining-programs)
<sub>anthropic-blog ・ 2026-08-12 ・ 継続話題（2回目）</sub>
<sub>**原題**: Reviewing The Evidence On Worker Retraining Programs</sub>

Anthropic の経済研究チームが、独立研究者 David Roodman と Anthropic の Maxim Massenkoff が共著した労働者再訓練プログラムのエビデンスレビューを公開した。このレポートは Anthropic の Economic Research チームが AI の経済的影響について取り組む研究の一環で、同チームはすでに Economic Index（AI が職種・産業をまたいでどのように活用されているかを追跡）、AI の労働市場への影響を測定するフレームワーク、および政策対応をまとめた Economic Policy Framework を発表している。

レポートは、AI による大規模な雇用変革が起きた場合に労働者再訓練が政策として機能するかを調査したもの。56 件の米国のランダム化研究を新たなメタ分析にまとめ、欧州の実験的エビデンスも参照している。

平均的な職業訓練プログラムの効果は「プラスだが小さい」とされる。訓練スロットを提供された1人あたり、雇用率が2〜3ポイント上昇し、年収が約1,000ドル増加する一方、費用は約1万3,000ドルかかる。税収増加と給付金支出の削減を加味すると政府は支出の半分以上を回収でき、プログラム全体としておおむね収支が合う水準とされている。「セクタープログラム」（高需要産業の雇用主と連携し、求職者をその分野に直接就職させる設計）は数倍大きな効果を示すが、再現実験では成功しないケースが多い。

著者の結論は、AI が大規模に労働者を代替した場合、現行の再訓練プログラムでは対応が不十分になるというもの。中心的な提言は、最も有望なプログラムを今から実証・評価・拡大することへの投資であり、特定の労働者グループを対象とした先導的プログラムを迅速に拡大してその結果を厳密に測定する取り組みが推奨されている。Anthropic の Economic Futures Research Fund はこうした調査を支援するために設計されているとされる。

#### [Claude Code v2.1.231：Slack の MCP OAuth が redirect URI で弾かれる問題を修正](https://qiita.com/moha0918_/items/e0970dd96706c59e6b69)
<sub>qiita ・ 0pt ・ 2026-08-13</sub>

Claude Code v2.1.231 がリリースされ、事前登録済み OAuth クライアントを使う MCP サーバー（Slack など）でサインインが redirect URI の不一致により失敗していた問題が修正された。変更点はこの1件のみ。

**問題の背景**：Claude Code の MCP OAuth コールバックは `http://localhost:<port>/callback` の形で動作し、`<port>` は空きポートからその都度選ばれる。Dynamic Client Registration（DCR）に対応した MCP サーバーは登録のたびに redirect URI を送り直せるため問題にならないが、Slack のように `client_id` を事前発行するサーバーでは、登録した redirect URI が固定なのに Claude Code 側のポートが認証ごとに変わるため、認可サーバーが不一致として弾いていた。

**修正の内容**：v2.1.231 のバイナリには、リダイレクトポートの選択に「設定で固定している場合はそのポートを使う」「していない場合は前回のクライアント登録で使ったポートを引き継ぐ」という2つの経路が追加されている。

**固定ポートの指定方法**：`claude mcp add --transport http` に `--callback-port <ポート番号>` を付けることで固定ポートを登録できる。指定できる範囲は 1〜65535。`--client-id`・`--client-secret`・`--callback-port` は HTTP/SSE トランスポート専用であり、stdio サーバーには無効。更新後もサインインが通らない場合は `claude mcp logout <名前>` で保存済みの OAuth 認証情報を削除してから `claude mcp login <名前>` を再実行する。SSH やヘッドレス環境では `--no-browser` を付けると認可 URL が標準出力に出力され、リダイレクト先の URL を貼り戻す形になる。

Claude Skills のカスタム作成手順を解説した Qiita 記事。前回の基本編に続く第2弾として、`skill-creator` を使って自分の業務手順や開発ルールに合わせた Skills を作る方法をまとめている。

`skill-creator` は新しい Skill の作成・既存 Skill の改善を支援する Skill であり、SKILL.md の雛形を出力するだけでなく、Skill の目的整理・業務手順のヒアリング・SKILL.md と関連ファイルの作成・テスト用プロンプトの作成・動作評価・改善の反復・`description` の調整まで対応する。フォルダ構成の細部をすべて把握していなくても、Claude との対話を通して Skill の下書きを作成できる。ただし、生成された内容がそのまま実務で使えるとは限らないため、業務ルールの不足や曖昧な指示がないかを確認し、必要に応じて編集・テストを行うことが重要とされている。

カスタム Skill 作成の流れは5段階。（1）自動化したい作業を Claude に伝える（手順が未整理でも可）。（2）Claude が不足情報（入力ファイル形式、必須列名、集計方法、エラー処理、完了条件、Skill を使うべき依頼例・使うべきでない依頼例など）を確認する。（3）Claude が Skill のフォルダと SKILL.md を生成する。基本構成は `SKILL.md`・`scripts/`・`references/`・`assets/` だが、必須なのは SKILL.md のみ。（4）テスト用プロンプトで動作を確認する（必要な場面で呼び出されるか、無関係な依頼で誤って呼び出されないか、エラー時に危険な処理を行わないかなど）。（5）問題があれば SKILL.md や関連ファイルを修正する。

SKILL.md の先頭には YAML フロントマターで `name`（英小文字＋ハイフン推奨）と `description` を記述し、その下に手順・条件・エラー処理などを Markdown で書く。`description` は機能の説明にとどまらず「どのような依頼で使うのか」を具体的に記述する必要があり、Claude はこの `description` を参照して Skill を読み込むかどうかを判断する。

#### [Claude Code の --continue で前回の続きから会話を再開する](https://qiita.com/akira_papa_AI/items/bca6f7770272b9090daf)

Claude Code の `--continue`（短縮形 `-c`）オプションを解説した Qiita 記事。`claude -c` を実行すると、現在いるフォルダで最も新しい会話を続きから再開できる。

「現在のフォルダ」が条件になるため、仕事 A のフォルダでは仕事 A の続き、練習用フォルダでは練習の続き、とプロジェクトごとに会話を分けて管理できる。実際の作業では「どのファイルを調べていたか」「どんなエラーが出ていたか」「どの案を採用・見送ったか」「次に何を確認する予定だったか」といった説明をやり直す手間を省ける。

記事では練習用フォルダを作成し、Claude Code に合言葉を伝えていったん `/exit` で終了してから `claude -c` で再開し、同じ合言葉が返ることを確認するハンズオン手順も紹介されている。執筆時点では筆者環境で OAuth 認証が期限切れのため会話再開の実動作は未確認とされており、手順と挙動の説明は公式 CLI リファレンスに基づく。なお、`claude 2.1.224` でコマンドの存在とヘルプ表示は確認済みとのこと。

#### [生成 AI の API はどう動いている？ Claude API で学ぶ基本の仕組み](https://qiita.com/kawamon-idealive/items/c988e28cc2319462bf18)
<sub>qiita ・ 0pt ・ 2026-08-13</sub>

Anthropic の公式講座「Accessing Claude with the API」をもとに、生成 AI API の基本的な仕組みを解説した Qiita 記事。記事は Claude API を例に使うが、マルチターン会話・システムプロンプト・出力制御の仕組みは他の生成 AI API とほぼ共通と述べられている。

**API の基本**：生成 AI の API は単純な HTTP リクエストであり、`model`（モデル ID）・`max_tokens`（出力の上限トークン数）・`messages`（会話内容）の3つのパラメータを POST するとテキストが返ってくる。`max_tokens` を超えると出力は途中で打ち切られる。

**マルチターン会話の仕組み**：API はステートレスであり、サーバー側は会話履歴を保存しない。「AI が会話を覚えている」ように見えるのは、`messages` 配列に `user → assistant → user ...` と全履歴を積み上げて毎回すべて送っているためだ。チャットアプリでは AI の返答を `assistant` ロールとして履歴に追加し、次のユーザー入力とともにすべて送り直すループを回すことになる。これにより、会話が長くなるほどリクエストが重く（費用も高く）なる理由、およびコンテキストウィンドウに制限がある理由が説明できるとされている。

**システムプロンプト**：`system` パラメータを使うと、会話とは別のレイヤーで AI に役割やルールを与えられる。ユーザーメッセージは「エンドユーザーの入力」、システムプロンプトは「アプリ開発者が設定する指示」として役割が分かれており、モデルはシステムプロンプトを優先度の高い指示として扱う。世の中の特化型 AI アプリの多くはシステムプロンプトが異なるだけで同じモデルを使っているケースが多い、と記事は述べている。
