#### [Claude による新規酵素システムの発見](https://www.anthropic.com/news/claude-discovers-novel-enzyme-system)
<sub>anthropic-blog ・ 2026-10-13 ・ 継続話題（19回目）</sub>
<sub>**原題**: Claude Discovers Novel Enzyme System</sub>

2026 年春に設立された Anthropic の生命科学研究グループが、Claude エージェント群を用いて新規酵素システム「ART（array-associated reverse transcriptases：アレイ関連逆転写酵素）」を発見したという継続報告。プレプリントが公開されており、広範な科学コミュニティとの共同研究の提案を受け付けている。

研究の概要として、約 950 体の Claude エージェントが 2 億 1,000 万トークン・21 時間をかけて DNA 配列データベースを検索し、20 万件超の逆転写酵素を収集・3,500 件の新規候補に絞り込み・上位 20 件を精査するという作業を担った。専門家なら数週間〜数か月かかる分析に相当する。ART はバクテリオファージ（細菌に感染するウイルス）に主として見られ、逆転写酵素・隣接するパートナー遺伝子・等間隔に並ぶ DNA 反復配列の長いアレイの 3 要素で構成されている。この反復配列のレイアウトは CRISPR アレイに類似している。

エージェントが反復配列を発見した際の記録には「スペクタキュラーだ：目視でタンデムリピートアレイが見える…CRISPR 様の反復配列アレイか？！」という記述が残されている。その後エージェントは人間の科学者が行うのと同様に、反復数と間隔の計測・既知の逆転写酵素システムとのレイアウト比較・先行研究の文献調査を実施し、新たな生物学的システムを発見したと判断してレポートを作成した。

MIT およびブロード研究所の Feng Zhang 教授は「AI エージェントが生物学的発見に貢献できることを示す刺激的な例だ。逆転写酵素と関連した RNA 反復配列アレイの同定は真に興味深く、さらなる調査に値する。この研究がより多くの科学者が AI の研究支援の可能性を探求するきっかけになることを期待する」とコメントした。

#### [【2026年版】今日から使える AI との会話術 — Claude・Gemini・Codex に指示を守らせる 6 つの原則](https://qiita.com/songchong/items/351a939e2e1b673c2929)
<sub>qiita ・ 13pt ・ 2026-10-18</sub>

IT 連携マップ編集部が 2026 年 10 月 18 日に Claude Code 2.1.302・Codex 0.163.0・Antigravity の CLI 1.4.2 の 3 製品を対象に実施した実験をもとに、AI に指示を守らせる 6 つの原則をまとめた記事だ。

**原則 1：毎回守らせたい指示は指示ファイルに書く。** Claude Code は CLAUDE.md を読み（存在しない場合のみ AGENTS.md）、Codex と Antigravity の CLI は AGENTS.md を常に読む。S のない AGENT.md はほとんど読まれない（Antigravity の CLI でも 6 回中 1 回のみ）。Codex は指示ファイルの先頭 32 KiB（日本語約 10,900 字）しか読まない。Claude Code に AGENTS.md を読ませるには CLAUDE.md に `@AGENTS.md` と 1 行書けばよい。

**原則 2：指示と命令を先頭に書く。** 約 4 万字の資料の途中（25%・50%・75% 位置）に指示を挿入した実験では、Claude の 2 モデルが 18 回中 17 回で従わなかった。大規模モデル（Claude Fable 5.1・Gemini 4 Argon）はどの配置でも 8 点満点を達成した。小規模モデル（Claude Haiku 5.5）では「指示→命令→資料」の順が最高スコア（7.7〜8.0）で、「命令→指示→資料」は 3 回で 6〜8 点と結果が揺れた。OpenAI が推奨するサンドイッチ型（資料の前後に指示・命令を配置）は短い資料で 8.0 点、長い資料で 6.7 点だった。

**原則 3：指示を少なく明確に書く。** IFScale（2025 年）の研究では 500 個の単純な指示を同時に渡した際、最良モデルでも遵守率 68% だった。system と user に矛盾する指示を与えた研究では最良モデルで system 遵守率 63.8% にとどまり、GPT-4.1 のガイドでもプロンプトの末尾に近い指示に従いやすいと記載されている。Claude Code のドキュメントでは 1 ファイル 200 行未満を目安としている。

**原則 4：指示ファイルの先頭を変えない（プロンプトキャッシュを活かす）。** 別の会話でのキャッシュヒット率は Claude Code が 99.99%、Codex が 0〜64.7%、Antigravity の CLI が 0%（同一会話の継続では 88.4%）。キャッシュ読み取り料金は Claude Code が通常の 0.1 倍。指示ファイルに変動する日時を書くと Claude Code では毎回 10,774 トークンのキャッシュが無効化された。また会話途中でのモデル変更（Claude Sonnet 5.5 への切り替え）でも 12,764 トークンの再書き込みが発生した。

**原則 5：会話が長くなったら要点をまとめて新しい会話を開く。** 空のフォルダで「ok と答えて」を送るだけでも Claude Code は毎回 18,920 トークンを送信しており、Codex は 13,084、Antigravity の CLI は 14,709 トークンを送信している。コンテキストウィンドウ上限に近づくとコンテキスト圧縮で細かい指示が落ちる場合がある。Claude Code では `/compact` の後に残したい焦点を指定でき、CLAUDE.md に `Compact Instructions` セクションを書くことで圧縮時の保持内容を指定できる。

**原則 6：長い資料はファイル、専門手順は SKILL として渡す。** SKILL はエージェントが使用すると決めたときに本文を読み込む仕組みのため、初期読み込みは 28 トークンの増加のみ。ただしファイルで渡してもトークン節約にはならず、2,893 字の資料をファイル経由で渡した際は 2 ターンの合計入力が約 2 万トークン増加した。長い資料をファイルで渡す目的はトークン削減ではなく、長文の出力をファイルに直接書かせることで会話履歴が膨らむのを防ぐためとされている。Claude Code では MCP ツールを 150 個追加しても初期入力の増加は 2,482 トークンにとどまったが、Anthropic のドキュメントでは利用可能ツールが 30〜50 個を超えると正しいツール選択精度が低下するとしている。

#### [Claude Code の利用上限（429）が深夜に繰り返し発動した——5時間ローリング枠の仕組みを理解してスケジュールを組み直した記録](https://qiita.com/Sidejob/items/3586ed01dc46c2e31b47)
<sub>qiita ・ 1pt ・ 2026-10-17</sub>

Claude Code のレート制限は「毎日 0 時リセット」ではなく「5 時間のローリングウィンドウ」方式で管理されており、5 時間前の使用量が随時消えていく仕組みだ。例として 17:00 に 3 ドル分を消費した場合、そのカウントは 22:00 に消える。

著者は複数工程の自動化バッチを 17:00〜23:00 に集中させていたため、毎晩 23 時過ぎに 429 エラーが発生するパターンが 3 日間続いた。実際のログでは、21:13 に工程 C の再試行が 84 ターン・3.63 ドル相当を消費し翌 02:13 まで積み上がる状態で、23:01 の工程 D 開始時に上限に達した。「失敗した日だけ動く再試行設計」が問題を悪化させており、失敗率が上がるほど夜間に上限に達しやすいという悪循環が生じていた。

対策として 3 つのパターンが示されている。①1 日全体にスケジュールを分散させる（17:00〜23:00 に入る処理量を半減させたところ 429 エラーが週 4〜5 件から週 1 件以下に減少した）。②重い工程を朝〜昼に前倒しする（10:00 に 5 ドル分を実行すれば 15:00 には消えるため 17:00 以降の枠に余裕が生まれる）。③再試行設計を見直し、当日中の再試行を避けて翌朝の空き枠で実行するか 1 日 1 回に制限する。

コストとターン数の記録には `--output-format json` フラグが有効で、`num_turns`・`usage`（input/output/キャッシュ読み取りトークン）・`modelUsage`（モデルごとの出力トークン）が出力される。`num_turns` が小さくても実際の消費が大きいケースがあるため、`modelUsage` の `outputTokens` 合計で実消費を確認するほうが正確とされている。

#### [なぜコードの8割超を書くClaudeが、AI研究を「主導」するのは26%なのか｜Anthropic](https://qiita.com/kinamocchi_tech/items/deeb50f0f133eb443b9a)

数値の内訳は以下のとおりだ。**80% 超**は 2026 年 5 月時点で本番コードに取り込まれた行のうち Claude が書いた割合（「控えめな数え方」と説明されている）。**9 割超**は試験的スクリプトや実験コードを含めた別の数え方。**26%** は Epoch AI が定義した AL0〜AL5 の 6 段階評価における AL4（大まかな指示から最後まで完遂し人間が監督する「主導」段階）として判定された社内研究開発タスクの割合で、AL5（完全自律）は 0% とされている。**59%** は 2025 年の社内調査で職員が業務の 59% で Claude を使用していると自己申告した割合であり、同調査で平均生産性 50% 向上と報告されている。これらはすべて Anthropic が自社で測定した数値であり、外部機関が確認したものではない。

研究者の代替基準として、Anthropic は社内ベンチマーク CoBench 2.1 を使用しており、Claude Opus 5.5 は 55.8%（Mythos 5.1 は 53.4%、Opus 5 は 53.2%）のスコアを記録している。研究スタッフの代替に相当するモデルの目安は約 85% とされており、現行モデルはいずれも到達していない。外部評価機関 METR も、AI 研究開発の完全自動化は現時点では困難であるという予備的評価を出している。

Anthropic の RSP（Responsible Scaling Policy）には 2 つの閾値が設定されている。①研究者・エンジニア全員を 5 倍以内のコストで完全に代替できること、②AI による自動化が原因で研究進歩のスピードが 2 倍になること。Opus 5.5 のシステムカードでは研究加速は推定約 1.5 倍とされており、2 倍に達する確率は約 30% と記載されている。Anthropic は Opus 5.5 が両閾値のいずれも満たしていないと判定しており、リスクレポートを 3〜6 か月ごとに公開している。ただし具体的なタスクテストの頭打ちと一部社内指標の変動により、前回より確信度が低い評価となっているとも記されている。
