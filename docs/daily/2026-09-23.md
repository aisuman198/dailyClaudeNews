#### [Claude Opus 5.5 の発表](https://www.anthropic.com/claude-opus-5-5)
<sub>hacker-news ・ 1043pt ・ 2026-09-22</sub>
<sub>**原題**: Claude Opus 5.5</sub>
<sub>関連: https://artificialanalysis.ai/models/claude-opus-5-5</sub>

Anthropic が Claude 5.5 ファミリーの第一弾として Claude Opus 5.5 を発表した。ほとんどの用途で Claude Fable 5.1 と同等の性能を持ちながら、Opus 5 より 40% 安価に利用できるモデルとして位置づけられている。リリース前には Frontier Design と METR による外部評価が実施されており、同社が実施する自動行動審査では、これまでにテストしたモデルの中で最高のスコアを記録した。

**ベンチマーク結果**（括弧内は主要比較モデルの値）:

- Terminal-Bench 4.0: 66.4%（Fable 5.1: 55.8%、Opus 5: 52.3%、GPT-6 Astra: 57.9%、GPT-5.6 Sol: 37.3%）
- FrontierCode v1.1（Main）: 54.4%（Fable 5.1: 50.3%、Opus 5: 48.0%、GPT-6 Astra: 53.3%、GPT-5.6 Sol: 47.5%）
- CursorBench 4.0: 57.8%（Fable 5.1: 51.8%、Opus 5: 46.6%、GPT-5.6 Sol: 41.7%）
- GDPval-AA v2.1: Elo 1846（Fable 5.1: 1735、Opus 5: 1708、GPT-6 Astra: 1542、GPT-5.6 Sol: 1588）
- AutomationBench: 40.0%（Fable 5.1: 31.4%、Opus 5: 26.9%、GPT-6 Astra: 41.4%、GPT-5.6 Sol: 28.8%）
- Humanity's Last Exam: 67.7%（ツール使用あり）（Fable 5.1: 65.6%、Opus 5: 63.6%）
- Terminal-Bench-Science 0.1: 58.7%（Fable 5.1: 52.6%、Opus 5: 29.0%、GPT-6 Astra: 64.6%）
- OSWorld 2.0: 81.8%（部分）（Fable 5.1: 80.7%、Opus 5: 74.0%）
- Chartography: 89.0%（ツール使用あり）（Fable 5.1: 88.4%）

Terminal-Bench 4.0 の Opus 5.5 スコアは xHigh 努力レベルでの値。

**コーディング**では、68 万行のコード移行を 1 日未満で完了したテスターの事例が報告された。内部テストでは HAProxy を C から Rust へ翻訳するタスクで 9.5 時間（Fable 5.1: 12 時間）で完了し、コストが 51% 低かった。また 20 万行のコードベース監査を 3 時間未満で完了（Opus 5 は 20 時間超、トークン数は 2.5 倍）。FrontierCode のデフォルト努力レベル（medium）では 54.6% を記録し、GPT-6 Astra の最高スコア（53.3%）を約 5 分の 1 のコストで上回った。CursorBench ではデフォルト努力レベルで 52.5%（Fable 5.1 の最高値 51.8%、Opus 5 の最高値 46.6% を上回り、GPT-5.6 Sol の最高値 41.7% より 11 ポイント高く、約 3 分の 1 のコストで達成）。

**ナレッジワーク**では、企業の四半期業績レポートを作成するテストで 18 回中 16 回が品質基準を通過（Fable 5.1 と Opus 5 はいずれも全試行で不通過）。仮想企業の M&A 分析タスクでは 63 分（Opus 5: 93 分）で完了し、コストは 50% 低かった。投資会社 Walleye Capital からは、最低の努力設定で評価タスクをほぼ解決し、評価指示書の分単位インデックスの誤りを自ら検出・修正した（他のいかなるモデルも発見できていなかった）との報告があった。GDPval-AA v2.1 では、デフォルト努力レベル（medium）で GPT-6 Astra の最高努力レベルを約 5 分の 1 のコストで上回った。

**安全性**については、プロンプトインジェクション攻撃に対して、テストしたすべての設定（コーディング、ツール使用、コンピューター使用、ウェブブラウジング）で Opus 5 と同等以上の性能を発揮した。AI セキュリティ企業 Gray Swan のベンチマークでは Fable 5.1 と並んでプロンプトインジェクション成功率が最低となった。生物学・サイバーセキュリティにおける能力が Claude Mythos 5.1 と同等であるため、Fable 5.1 と同様の安全対策を適用する。生命科学研究向けには Life Sciences Verification Program（即日申し込み可能）、サイバーセキュリティ従事者向けには Cyber Verification Program（数週間以内に拡大予定）を通じてアクセス可能となる。

**価格**（括弧内は Opus 5 の旧価格）:

- キャッシュ読み取り: $0.20/M トークン（$0.50、60% 削減）
- 入力トークン: $4.00/M（$5.00、20% 削減）
- 出力トークン: $20.00/M（$25.00、20% 削減）

2026 年 6 月 12 日、米商務省産業安全保障局（BIS）が Anthropic に対してレターを送り、Claude Fable 5 と Claude Mythos 5 について外国籍者がアクセスする場合に承認済み輸出ライセンスの取得を求めた。インターネット越しにモデルを使わせること自体を「輸出」とみなす解釈が適用されたもので、対象は「あらゆる外国籍者」であり Anthropic 内の外国籍社員も含まれた。ユーザーの国籍を確認する手段がなかったため、Anthropic は同日米東部時間 17 時 21 分に全顧客向けに 2 モデルへのアクセスを停止した（AWS Bedrock、Google Cloud、Microsoft Foundry、直販 API のすべてが対象）。

規制の引き金となったのは、Amazon のリサーチャーが Fable 5 のサイバーセキュリティ向け安全装置をジェイルブレイクし、既知の脆弱性を特定させ、さらに攻撃コードを作成させたという報告とされている。Anthropic はこれらの脆弱性を「既知で軽微、他の公開モデルでも見つけられる程度」と評価していたが、政府側は「消費者向け製品が無制限のサイバーツールに転用されるリスク」と受け取った。

停止から 18〜19 日後、Claude Fable 5 は全ユーザーへのアクセスを再開した（Claude Mythos 5 は審査済みパートナー限定のまま）。商務長官ハワード・ルトニックは 6 月 30 日に「過去 2 週間、Anthropic と緊密に作業して Fable 5 を分析し、承認した」と述べた。合意した条件は 3 つで、① セキュリティリスクの能動的な検知と対処、② 悪意ある活動発見時の当局への通知、③ 将来のモデル基準づくりへの協力であり、これらへの同意により外国籍者アクセスに求められていた輸出ライセンス要件が撤廃された。

技術面では、サイバー攻撃関連用途を「禁止・高リスク・低リスク・無害」の 4 層に仕分ける新しい分類器を導入し、報告されたジェイルブレイク手口の 99% 超を阻止できるとされる（この数値はその手口に限定した値であり、あらゆる攻撃に対する合格点ではないとされている）。インシデントの重大度を 0〜4 の 5 段階で評価する CJS スケールも提案された。

業界横断での対応として、Amazon・Microsoft・Google・Glasswing のパートナーと共同で、ジェイルブレイクの深刻さを「能力獲得・影響の広がり・武器化の容易さ・発見可能性」の 4 基準で採点するコンセンサス案を起草中。ただしこのフレームワークはまだ提案段階であり、正式名称も未定。CSIS の分析では ECRA（輸出管理改革法）の新興技術規制が適用された点が注目されており、規制の適用範囲は今後も変わりうるとされている。

#### [Claude API の Memory tool（memory_20250818）でセッションをまたいで記憶させる実装手順](https://qiita.com/yureki_lab/items/2a565f07ae4b0bf3c169)
<sub>qiita ・ 2026-09-21</sub>

Claude API の Memory tool（`memory_20250818`）を使ったセッションをまたいだ記憶の実装手順と、ハマりやすい 3 点を解説した記事。検証環境は Python 3.13 / Anthropic SDK 1.x / claude-opus-5。

Memory tool はクライアント側ツールであり **API 側は何も保存しない**。`tool_use` が返ってきた際にクライアント側でファイル操作を実装して `tool_result` で返す必要がある。ツールの宣言は `{"type": "memory_20250818", "name": "memory"}` と記述するだけで `input_schema` は不要。Claude から `view` / `create` / `str_replace` / `insert` / `delete` / `rename` の 6 コマンドが返ってくるため、`/memories` 配下のファイル操作に変換する。

**ハマりどころ 1（API は何も保存しない）**: ツールを宣言しただけでは何も保存されない。以前は `context-management-2025-06-27` のベータヘッダーが必須だったが、現在の SDK では通常の `client.messages.create` で動作する。

**ハマりどころ 2（パストラバーサル）**: Claude が `/memories/../../.env` のような危険なパスを返す可能性があるため、`/memories` プレフィックスの確認と実パスがルート配下に収まっているかの 2 段チェックが必要。`Path.resolve()` を通してから比較しないとシンボリックリンクや `..` を素通しする。system prompt で「秘密情報は記録しない」と明示しておくことも推奨されている。

**ハマりどころ 3（system prompt での指示が必要）**: ツールを宣言しただけでは次のセッションで Claude が自発的に `/memories` を読みに来ないことがある。system prompt に「会話の最初に `/memories` を `view` すること」「どのファイルに書くか」を明示する必要がある。書き込み先のファイル名を固定しておくと、セッションごとに複数ファイルが乱立するのも防げる。

SDK には `BetaAbstractMemoryTool` という抽象クラスが用意されており、6 コマンド分のメソッドを実装して `tool_runner` に渡すとループとディスパッチを SDK 側で処理できる。ただしパスの検証は引き続き自前で実装する必要がある。

#### [シングル・サブ・マルチエージェントの違いを「作業机」で理解する ― Claude Code で学ぶ AI の分業入門](https://qiita.com/Takuya__/items/f1711865fa67e0b86cea)
<sub>qiita ・ 2026-09-22</sub>

Claude Code で使えるシングルエージェント・サブエージェント・マルチエージェントの違いを「作業机（コンテキストウィンドウ）」という比喩を使って整理した解説記事。検証環境は Claude Code v2.1.272。

シングルとマルチは「1 人でやるか分けるか」という大きな分かれ道であり、サブエージェントはマルチエージェントの中で最も手軽な形と定義している。Claude Code で使えるマルチエージェントの形として、① サブエージェント（親→子への依頼と要約のみ返却する一方向）、② エージェントチーム（メンバー同士が共有タスク表を介して直接やり取りする双方向）、③ 動的ワークフロー（オーケストレーションスクリプトが数十〜数百の subagent を動かす）の 3 種類が紹介されている。

サブエージェントの最大の効果は「親のコンテキストウィンドウを空けておけること」。3 体の subagent を並列実行した際、各 subagent がそれぞれ 15〜17k トークンを消費しても、親には要約のみが返ってくる。subagent は会話履歴を引き継がないため、依頼文に「目的・返してほしい形・使う道具・作業の境界」を明示することが重要と説明されている。

Anthropic が 2025 年 6 月に公開した技術記事の数値として、マルチエージェントは通常のチャットの約 15 倍のトークンを消費すること、Claude Opus 4 単体と比較した社内リサーチ評価では 90.2% の改善が報告されたことが紹介されている（社内評価であり指標の詳細は非公開）。一方でコーディング作業の多くは独立して並列化できる部分が少なく、シングルエージェントが有効な場面も多いとしている。

エージェントチームは執筆時点で実験的機能（デフォルト無効）であり、`settings.json` に `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: "1"` を追加することで有効化できる。動的ワークフローは全有料プランで利用可能で、Pro プランでは設定から「Dynamic workflows」をオンにする必要がある。組み込みの `/deep-research` コマンドも動的ワークフローとして実装されている。

使い分けの指針として、シングルから始め「脇道の調査で机が埋まりそう → サブ」「担当同士で相談・反証が必要 → チーム」「数十〜数百の独立した作業と検証が必要 → ワークフロー」と 1 段ずつ上がることを推奨している。
