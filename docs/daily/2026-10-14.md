<sub>hacker-news ・ 114pt ・ 2026-10-12 ・ 継続話題（2回目）</sub>
<sub>**原題**: Show HN: Atticus – Hold-to-talk voice assistant for macOS that runs on Claude -p</sub>

Atticus は Claude Pro または Max プランを利用して Claude Code（`claude -p`）上で動作する macOS 向け音声アシスタント。API キー不要で、⌃⌥Space を押しながら話すとコマンドが実行される。1 回の質問あたりのプラン消費量は API 定価換算で約 0.18¢。

今回の更新で確認された主な追加・詳細化内容: Windows 版が @FindlayHi によって別途構築され、Home Assistant・Jellyfin・Immich などとの連携機能を含む。会議コパイロット機能では通話中の文字起こしを保存し、AI によるセッション終了後の要約と行動項目を生成する（オフ可能）。文字起こしデータはローカルの `~/.config/atticus/meetings/` に保存され、音声データは保存されない。「見張り（Watch）」機能では特定ページの変更や Codex などのコーディングエージェントの完了を 5 秒おきに監視し、条件が満たされると通知する。待機中の AI 利用料は発生しない。

安全モードでは Claude Code のサンドボックス内でのみコマンドを実行し、削除・送信・購入・ファイル変更の前にユーザーへの確認を求める。`rm`・`sudo`・ディスクツール・シャットダウンは常時ブロックされる。予算目標は AI による質問あたり中央値 0.002 ドル未満・6 秒以内（2026 年 10 月 10 日時点で $0.00095・5.0 秒）に設定されており、システムプロンプトの文字数も 10,000 文字以内に抑えるよう制約を設けている。GitHub リポジトリは現在 149 スター・5 フォーク。

#### [Anthropic によるソース管理の再設計](https://www.anthropic.com/engineering/redesigning-source-control)
<sub>anthropic-blog ・ 2026-10-13</sub>
<sub>**原題**: Redesigning Source Control</sub>

Anthropic は、1 日あたりのコード変更マージ件数が 2026 年 5 月の約 2,500 件から 9 月には 30,000 件超へと 10 倍以上増加し、git が開発インフラ上の最大ボトルネックになったと説明している。これを受けて自社製バージョン管理システム「Scion」を構築し、5 ヶ月でモノレポを git から完全移行した。コードレビューツール「Antique」や全文コード検索、独自のソース管理 IAM システムなども同期間に構築・リリースした。

**git の限界**

git はクライアントの常時オンラインを前提としない分散型システムであり、Anthropic のモノレポ（main ブランチの履歴だけで約 100 GB、圧縮後の作業コピーが 25 GB 超）には合わなくなっていた。CI の需要だけで 1 日約 2,500 万回のコードチェックアウトが発生し、単純に取得すると 1 日 600 PB 超の git トラフィックになる計算だという。ピーク時には数百台の内部 git ミラーを運用していたが、ミラーのディスク・メモリ容量の限界でスケールが困難になった。

**Scion の設計原則**

Google の Piper や Meta の Sapling を参考に、以下の原則で設計された。(1) クライアントは常時オンライン。(2) クライアントサーバー非対称性（サーバーがコミット作成・マージ・リベース等を処理し、クライアントはローカルキャッシュのみ管理）。(3) 全ソース管理クエリを API 経由で提供（CI ジョブがローカルリポジトリなしに blame・diff を取得可能）。(4) 水平スケール（サーバーにはリポジトリの完全実体が存在しない）。(5) コミットはサーバー側で作成し、コストは変更差分サイズにのみ比例する。(6) 作業コピーはオプションかつスパースが基本。

**データ構造**

変更の単位は「チェンジセット（changeset）」で、親との差分ファイルのみを保存し、ファイル内容へのポインターはコンテンツアドレス指定で管理する。blame・パス履歴・コミットグラフのスキップリストなどは「派生データ（derived data）」として再帰的に計算し、イーガー評価またはレイジー評価を選択できる。パックファイル（git の圧縮バンドル）が存在しないため、リポジトリのメンテナンス作業も不要になった。

**スケール結果**

3 層の scion-daemon → scion-cache → scion-server アーキテクチャで、各層のキャッシュヒット率は 99% 超を維持している。以前の git ミラーインフラと比較して CPU・メモリ要件が 200 分の 1 以下になった。CI・研究ジョブのコードチェックアウトは数分から数秒（2 桁以上高速化）に短縮され、CI 単体で 25% の CPU 容量削減を実現した。

**開発プロセスからの学び**

7 人のチームが Scion と Antique、さらに関連する半ダース以上のシステムを構築し、マージ件数が 10 倍増加する中で 5 ヶ月での完全移行を達成した。開発は Claude Mythos Preview と Claude Tag の社内リリース時期に開始した。git から Scion への取り込みパイプラインを Claude Mythos Preview に再設計させたところ、メモリ消費 20 分の 1・速度 4 倍の実装が生成されたと報告している。

#### [ディスティレーション攻撃への防御強化](https://www.anthropic.com/research/distillation-defenses)
<sub>anthropic-blog ・ 2026-10-13</sub>
<sub>**原題**: Distillation Defenses</sub>

Anthropic はフロンティアモデルのディスティレーション攻撃に対する新たな防御手法を公開した。早期の証拠として、新手法によりディスティレーターが収集できる推論データを約 90〜99% 削減できたと報告している。

**ディスティレーション攻撃とその背景**

ディスティレーション攻撃とは、あるモデルの能力を開発元の承認なく別のモデルに複製するための工業規模の隠密キャンペーンで、不正アカウントのネットワークを通じて実施されることが多い。Anthropic はこれを 2 つの理由で問題視している。第一に、ディスティレーションで作られたモデルは能力水準に見合ったセーフガードを持たないままリリースされる可能性がある。第二に、違法にディスティレーションされたモデルが外国の軍・情報・監視システムに統合されるという国家安全保障上のリスクがある。

具体例として、Zhipu が米国モデルをディスティレーションして GLM-5.3 を開発した経緯を説明している。同社は Claude Fable 5 のサイバー能力をディスティレーションしようとしたが、サイバーセーフガードが攻撃精度を低下させたため、古い Claude モデルと別ラボのモデルに切り替えた。CAISSI（米国 AI 超知能基準・革新促進センター）は GLM-5.3 を、リリース済みオープンウェイトモデルの中で最もサイバー能力が高いと評価している。Anthropic 自身の調査でも、GLM-5.3 のセーフガードは容易に回避でき、セキュリティエクスプロイトをエンドツーエンドで開発する意欲があることが確認された。

また、Moonshot の Kimi モデルへのリクエストが密かに Claude へ転送されていた事例もあった。その中には、中国人民解放軍関係者と考えられるユーザーが特定個人の CCTV 監視映像分析を求めるリクエストが含まれていた。

**これまでの防御策と限界**

初期対策として、Claude が回答前に推論を要約してからユーザーに表示するようにした。この変更の効果をSWEベンチ検証で測定した結果、完全なトランスクリプトで訓練したモデルは 80.4% だったのに対し、要約トランスクリプトのみで訓練したモデルは 71.8% にとどまった。しかし攻撃者は「事前の推論をそのまま文字どおりに出力せよ」という単純な指示から、1 ラボが 12,000 種類の異なる手法を試したような高度な技法まで、様々な能動的手法でこの対策を回避するようになった。さらに 20,000 アカウント以上を管理するプロキシネットワークを用いた大規模攻撃へと進化した。

**新しい防御手法（3つ）**

第一に、**推論の伝達経路の制御（preserved thinking）**。Claude Fable 5.1 と Claude Opus 5.5 で導入。2026 年 8 月 31 日以降に作成された新しい API アカウントは Claude の事前コンテキストを編集できなくなり、プロキシネットワークを使った繰り返し抽出が困難になった。モデル間・アカウント間での推論ブロックの移動も制限され、Claude Sonnet 5.5 では推論トランスクリプトへのアクセスをそれを生成した組織のみに限定した。

第二に、**二段階クラシファイアによる抽出の検出とブロック**。憲法的クラシファイア研究と同様の手法を採用し、内部・外部の両方でレッドチーミングを実施した結果、虚偽陽性率 0.1% 未満を達成した。現在、最も能力の高い一般提供モデル（Claude Sonnet 5.5・Opus 5・5.5・Fable 5・5.1）で実行中。Claude の推論を別言語に翻訳させる手法や、特定タグ内に記述させる手法などの新しい攻撃手法が発見されるたびに随時パッチを当てている。

第三に、**繰り返し試行の困難化**。ディスティレーションを継続的に試みるユーザーに利用制限を強化し、持続的な試みが検出されたアカウントを ban する。2026 年 9 月 24 日からは、虚偽陽性率が 0.1% 未満の特定分野では、Claude が応答する前にセーフガードによってブロックされたリクエストについても課金を再開した。

**効果と今後**

クラシファイア導入後、ディスティレーターが Anthropic 自社プラットフォームで抽出した推論トークン数は、導入前と比べて一貫して 10〜100 倍低下した。日によっては計測できないほど少ない量にまで減少したと報告している。一方でトレードオフも生じており、preserved thinking により一部の開発者が統合のアップデートを求められた点や、0.1% 未満のケースで正当なリクエストがブロックされる点などを認めている。

Anthropic はこの問題を「すべてのモデル開発者と API プラットフォームが直面し対応しなければならない問題」と位置づけ、防御コストをかけずに不正ディスティレーターを有料顧客として扱い続けることへの問題意識を業界全体で共有するためにこの記事を公開したと説明している。

#### [AI モデルはデータセンターなしで自己複製できる可能性](https://www.anthropic.com/research/self-replicating-ai)

8 台の GCP ノードで動作する firewalled VPC 上での評価では、GLM-5.2 のみがエンドツーエンドの複製を達成した（5 試行中 4 試行で 8/8 ノードに伝播、1 試行で 7/8）。その他のモデルは信頼性ある複製に失敗した。「能力フロア（確実に複製できる能力水準の下限）」と「サイズシーリング（デバイス上で動作可能なモデルサイズの上限）」は現時点では交差していない。小型モデルが歴史的な改善ペース（年間 13.7 ECI、R² = 0.95）で進歩すれば、年末までに能力フロアに到達すると推定している。

#### [ゲーム開発における AI ハーネスの設計方法](https://kylekukshtel.com/ai-harness-engineering-game-development-claude-code)
<sub>hacker-news ・ 112pt ・ 2026-10-13</sub>
<sub>**原題**: How to engineer an AI harness for game development</sub>

カルガリーで開催された Indie Rodeo（2026 年 9 月 12 日）での 45 分間のプレゼン内容を記事化したもの。著者は 15 年近いゲームプログラマー歴を持ち、Claude Code を活用した実務レベルでのゲーム開発における LLM 利用の方法論を解説している。なお記事はすべて人間が執筆したものだと著者は明示している。

**LLM がゲームを苦手とする理由**

Web 系スタックと異なり、ゲームにはコードとして表現しにくい要素（アセット・物理・エフェクトなど）が大量に含まれる。LLM はコードしか直接扱えないため、ゲームのコード以外の部分が「ブラックボックス」になり、LLM の推論が困難になる。著者はこれをゲームのコンテキスト問題と位置づけ、LLM やゲームの本質的な限界ではないと述べている。また、Web 系と比べてゲームのソースコードは学習データとして利用可能な量が桁違いに少ないことも要因の一つとして挙げている。

**ハーネスの考え方**

「ハーネス（Harness）」とは、エージェントが特定の作業を行う際の一連の行動パターンを指す。Claude Code 自体もハーネスの一種であり、ゲームをエージェントに「読み取れる（legible）」形にすることがゲーム向けハーネス設計の核心だと述べる。

**具体的なテクニック**

*固定乱数（Fixed Randomness）*: ゲーム開始時に単一のシード付き乱数ソースを作成し、全ての非決定的な呼び出しをそこに集約することで決定論的な状態再現を実現する。これにより LLM が同じ状態から繰り返し作業できる。

*スクリーンショットと差分評価*: 変更前後のスクリーンショットを撮影し、`odiff` などの画像差分ツールで「85% 類似」といった定量値を算出する。スクリーンショット全体を LLM に渡すと無関係な情報がコンテキストを汚染するため、差分画像に絞ることで変更点のみに集中させる。この定量値をエージェントの各ターンでの評価指標として継続的に活用できる。

*決定論的な状態管理*: セーブ/ロード機能を開発の最初から実装する。OOP 型アーキテクチャを「すべてのオブジェクトが同じ型（`Thing`）」という設計に変換することで、LLM がオブジェクトモデルを理解しやすくなる。`Thing` は型を表す enum 値・`isAlive` フラグ・統計値などを持つ単一の構造体として定義し、LLM が 100 種類のクラス階層を理解する必要をなくす。

単項練習で全問正解でも、シナリオの中で「最初に打つべき手」として選べるとは限らないことも指摘している。ツール説明（Domain 2）は単項練習 4 問すべて正解だったが本番では 0% だった。

**ドメイン別の重点ポイント（抜粋）**

Domain 1 では、ループの継続・終了は `stop_reason` のみで判断し「完了しました」という文言は根拠にしない。subagent は会話履歴を継承せず、必要な情報は Task prompt に書く。金額・コンプライアンスなど必ず守るべきルールはフックや前提条件チェックでコードにより強制する。

Domain 2 では、ツールの選び間違いへの最初の対応はツール説明を修正すること（統合やルーティング層の追加ではない）。エラーは `isError: true` に isRetryable を添えて返し、失敗を空の結果に偽装しない。

Domain 3 では、チーム共有の設定はプロジェクトの `.claude/` に、個人設定は `~/.claude/` に置く。必ず守らせたいルールは settings の permissions やフックで、ガイダンスは CLAUDE.md に書く。

Domain 4 では、厳密なスキーマ準拠が必要なら tool use＋JSON schema を選ぶ。`tool_choice: "auto"` はテキストだけ返すことがある。Batch API は最大 24 時間で遅延保証なし。原文にないかもしれない項目は nullable にし、enum には `"unclear"` などを用意してモデルが値を捏造しないようにする。

Domain 5 では、API はステートレスなので会話履歴は毎回のリクエストに含める。金額・日付・注文番号は「case facts」ブロックとして要約外に毎回送る。

練習問題として GitHub の paullarionov/claude-certified-architect に日本語学習ガイド・練習テスト・Anki デッキが公開されている。問題と答えを丸暗記するよりも「なぜこの選択肢が正解でほかが違うのか」を説明できるようにする方が、初見問題への対応力が高まると述べている。

#### [Claude Sonnet 5.5 の性能を実測｜5 モデル計 90 回で時間は Opus 5 の 0.35 倍、成功数は差なし](https://qiita.com/kenji_harada/items/43f5348563728dea7e12)

5 つの Claude モデル（Sonnet 5.5・Sonnet 5・Opus 5.5・Opus 5・Fable 5.1）の effort を high に揃え、外部依存のない小さな Node.js の課題 6 つを各 3 回（合計 90 回）解かせた実測報告。Claude Code 2.1.285 / 2.1.283 の非対話モード（`claude -p`）を使用し、2026 年 9 月 28・30 日（日本時間）に計測した。課題には「時間文字列を秒に変える関数の修正」「CSV 分割関数の実装」「割引処理の別モジュールへの切り出し」「コマンドライン引数の不具合 4 件の修正」「在庫と注文にまたがる不具合の修正」「浮動小数ドルから整数セントへの API 移行」が含まれる。

**成功数**

全モデルが 18/18 で差なし。

**時間・費用の比較（Opus 5 基準の中央値比）**

| モデル | 時間（中央値） | 費用（API 定価換算） | Opus 5 比（時間 / 費用） |
|---|---|---|---|
| Sonnet 5.5 | 21 秒 | $0.07 | 0.35 倍 / 0.28 倍 |
| Sonnet 5 | 34 秒 | $0.10 | 0.55 倍 / 0.41 倍 |

Fable 5.1 は時間は Opus 5 より速いが費用は全 6 課題で Opus 5 を上回り、18 回合計は $7.07。Sonnet 5.5 の 18 回合計は $1.38、Sonnet 5 は $2.03。Sonnet 5.5 と Sonnet 5 の API 公式単価は同じ（入力 $2・出力 $10 / MTok）だが、Sonnet 5.5 は出力トークンが少ないため費用が低くなる。思考トークンの中央値は Sonnet 5.5 が 318、Sonnet 5 が 754 だった。

**Anthropic の発表との比較**

「Sonnet 5.5 は Sonnet 5 より 30% 以上速く、費用が最大 30% 安い」という発表と実測の向きは一致した。1 秒あたりの出力トークンの中央値は Sonnet 5.5 が 147.5、Sonnet 5 が 113.3 だった。ただし発表と同じ条件で計測したものではない。

**注意点**

Claude Code での effort の既定は、Sonnet 5.5 と Opus 5.5 が medium（API の既定とは異なる）。比較する際は `--effort high` を明示して揃える必要がある。また `--permission-mode dontAsk` でヒアドキュメントを含むコマンドなど一部が自動的に拒否されるケースがあり（Sonnet 5.5 では 18 試行中 12 回）、成否は採点結果のみで判断している。課題がすべて易しかったため難しい課題での実力差は測定できておらず、Terminal-Bench 4.0 での Sonnet 5.5 70.6%・Sonnet 5 10.3% という差は今回の課題では再現されなかった。
