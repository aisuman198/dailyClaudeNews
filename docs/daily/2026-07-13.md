#### [Claude Sonnet 5 リリース — 1Mコンテキスト標準化・temperature 廃止・実質3割の値上げ](https://qiita.com/sakutto-panda/items/47a2b51bf6c4f513ec49)
<sub>qiita ・ 2026-07-12</sub>

2026年6月30日（米国時間）、Anthropic が Claude Sonnet 5（モデルID: `claude-sonnet-5`）を公開した。「速度と知性の最良の組み合わせ」という位置づけは歴代 Sonnet と同様だが、API レベルで複数の破壊的変更を含むリリースとなった。

**基本仕様**：コンテキストウィンドウは 1Mトークンが標準かつ唯一の選択肢で、小さいコンテキストのバリアントは存在しない。最大出力トークンは 128k。adaptive thinking がデフォルトで有効。ツール・プラットフォーム機能は Sonnet 4.6 と同一だが Priority Tier は非対応。Claude API に加えて Amazon Bedrock・Google Cloud・Microsoft Foundry で同日利用可能。claude.ai では Free / Pro プランのデフォルトモデルとなり、Max / Team / Enterprise でも選択できる。

**3つの破壊的変更**：

1. **temperature / top_p / top_k の廃止**：デフォルト以外の値を設定すると 400 エラーが返る。再現性のために `temperature: 0` を設定していたケースも含め、パラメータ自体を削除する必要がある。この制約は Opus 4.7 で先行導入されており、今回初めて Sonnet クラスに適用された。Anthropic の案内はシステムプロンプトによる挙動誘導への移行で、決定論的な出力を得るノブは事実上なくなった。
2. **manual extended thinking（budget_tokens）の削除**：Sonnet 4.6 で deprecated だった手動の思考トークン割り当てが、Sonnet 5 では 400 エラーとなった。`thinking: {type: "adaptive"}` への移行が必要。
3. **adaptive thinking のデフォルト有効化**：思考を無効にしたい場合は `thinking: {type: "disabled"}` を明示する必要がある。また `max_tokens` は思考トークンと応答テキストの合計に対する上限となるため、思考なし前提でギリギリの設定をしていたワークロードでは応答が途中で切れる可能性がある。

**価格とトークナイザー**：プロモーション価格は $2/$10 per MTok（8月31日まで）、以降は Sonnet 4.6 と同じ $3/$15。ただし新トークナイザーが同じテキストで約30%多くトークンを消費するため、単価据え置きでも実質値上げとなる。

**Claude Code への影響**：v2.1.197 以降でデフォルトモデルが Sonnet 5 に切り替わる。明示的にモデルを固定していない場合は `/model` で確認することを著者は推奨している。

#### [Cowork は Claude Code と何が違うのか](https://qiita.com/sgrs38/items/bb42fb5d531c500f9a6d)
<sub>qiita ・ 2026-07-12</sub>

Anthropic の Cowork と Claude Code の違いをまとめた記事。両者ともに Claude Code エンジンで動くが、動作環境と触れる範囲が異なる。

**動作環境の違い**：Claude Code はローカル PC 上で直接動作する。Cowork はローカルの隔離環境（macOS は Apple Virtualization、Windows は Hyper-V）の中で動作する。ブラウザ・スマホから使えるクラウド版も存在し、Anthropic のインフラ上にセッションごとの隔離環境が作られるが、2026年7月時点ではベータで順次展開中。

**触れる範囲の違い**：Claude Code は起動したフォルダを中心に動作し、ターミナル越しに外部へアクセスする場合がある。Cowork は渡したフォルダの外には構造的にアクセスできない。VM は会話ごとに作り直すのではなく1つを使い回す仕組みで、Python・Node.js・git・ffmpeg などが最初から含まれている。外部通信は allowlist 経由で、pypi・npm レジストリ・Anthropic API は通るが、それ以外には基本的に通信できない。

**設定の違い**：Claude Code はローカルの `~/.claude/` に置いたグローバル設定をそのまま読み込む。Cowork は隔離環境内で動くため PC 上のグローバル設定は持ち込まれず、アプリ上の「Global Instructions」や ZIP でアップロードするスキルを使う。ただしスキルのフォルダ形式（SKILL.md を含むフォルダ）は共通のため、同じものを ZIP にまとめて Cowork にアップロードすれば動作する。

記事著者は、書類仕事などの業務用途にはまず Cowork を、ソフトウェア開発には Claude Code を推奨している。

#### [Claude Code は OpenCode より4.7倍多いトークンをプロンプト処理前に消費する](https://systima.ai/blog/claude-code-vs-opencode-token-overhead)
<sub>hacker-news ・ 376pt ・ 2026-07-12</sub>
<sub>**原題**: Claude Code sends 33k tokens before reading the prompt; OpenCode sends 7k</sub>

Systima が Claude Code と OpenCode を同一モデル・同一マシン・同一タスクで比較し、API 境界でのトークン消費を実計測した報告。

**基本計測**：一行の返答を求めるだけのリクエストで、Claude Code はシステムプロンプト・ツールスキーマ・スキャフォールドのインジェクションで約 33,000 トークンを消費してからプロンプトが届く。OpenCode は約 7,000 トークン。テストは Sonnet 4.5 上で実施し、Claude Fable 5 では差が約 3.3 倍に縮小した（Claude Code は新しいモデルに対して小さいシステムプロンプトを送るため、倍率はモデル依存）。

**キャッシュ効率**：OpenCode はリクエストプレフィックスが毎回バイト単位で同一のため、セッションごとに一度だけキャッシュ書き込みコストを払えばよい。Claude Code は同一タスクでも mid-session にキャッシュトークンを書き直し続け、OpenCode の最大54倍のキャッシュ書き込みトークンを計上した。キャッシュ書き込みは割増料金が発生するため、利用ダッシュボード上のコストが上昇する原因となる。

**設定による追加コスト**：本番リポジトリの 72KB の AGENTS.md / CLAUDE.md ファイルが平均 20,000 トークンを追加し、5つの MCP サーバーで 5,000〜7,000 トークンが加わる。実際の作業環境では最初のリクエスト送信前に 75,000〜85,000 トークン規模になる。

**subagent のコスト増幅**：直接実行で 121,000 トークンだったタスクが、2つの subagent に分散すると 513,000 トークンになった。各 subagent が独自のブートストラップコストを持ち、親セッションがその会話ログを消費するため。CLAUDE.md の軽量化は subagent の並列数倍で効いてくる。

**Claude Code が有利な場面**：複数ステップのタスクでは、Claude Code がツール呼び出しをバッチ処理してリクエスト回数を減らすため、OpenCode よりタスク全体の合計コストが低くなるケースがあった。OpenCode は基本コストが低い代わりに毎ターンそのコストを繰り返し支払う構造のため、セッションの展開次第で優劣が入れ替わる。

計測手法は Claude Code / OpenCode とモデルエンドポイントの間にロギングプロキシを挟み、各リクエストのペイロードと API が返す usage ブロックを記録するもの。Claude Code 2.1.207・OpenCode 1.17.18 を使用し、両方を claude-sonnet-4-5 に固定した。

#### [Claude Code 実践ナレッジまとめ（公式ドキュメント精読・実装例付き）](https://qiita.com/tatatata_jp/items/cc0e61798d37dbfcb9a6)
<sub>qiita ・ 2026-07-12</sub>

Claude Code v2.1.207 の公式ドキュメントを精読した実践 Tips 集（第1弾）。著者が CTF 学習環境や個人の AI 開発に実際に組み込んだ hook・skill の実装例を含む。

**モデル・コスト管理**：主力は `/model sonnet`（9割の作業で十分）、複雑な設計判断のみ `/model opus`、subagent には `model: haiku` を指定して節約。`/effort low|medium|high|xhigh|max`（初期値 `high`）で思考量を調整。`/usage` でセッションのトークン内訳を skills・subagents・plugins・MCP サーバー別に表示でき、`d`/`w` キーで 24時間/7日切り替え可能。`opusplan` モードは計画を Opus で、実行を Sonnet で自動振り分けする。

**セッション運用**：Explore → Plan → Implement → Commit の流れが基本。`/goal <条件>` コマンドで完了条件を指定すると、小型モデル（既定 Haiku）が条件充足を毎ターン判定し、満たされるまで自動継続する（v2.1.139 以降）。条件は最大 4,000 文字で「or stop after 20 turns」のような打ち切り条件も含められる。そのほか `/btw <質問>`（会話履歴に残らない軽い質問）・`/advisor [model|off]`（別モデルに相談）・`/branch [name]`（会話を分岐）・`/batch <instruction>`（大規模変更を5〜30単位で並列分解）などの非公知コマンドを紹介している。

**Hooks**：特定のイベントで確実にコマンドを実行させる仕組み。type は command・prompt・agent・http の4種。`exit 0` が無干渉、`exit 2` がブロック（stderr が Claude へのフィードバックになる）。`.bashrc` 等に無条件の `echo` があると hook の JSON 出力に混入してパースエラーになるため、`[[ $- == *i* ]]` で対話シェル限定にする対策が公式推奨。`jq` が入っていない環境では Python3 で JSON 解析する方法が紹介されている。

**トークン削減策**：`/clear` でリセット・`/compact <指示>` で圧縮内容を指定・MCP ツール定義は遅延読込・型付き言語では code intelligence プラグインの「定義へジャンプ」を使い grep+複数ファイル読込を節約・詳細指示は Skill 化してオンデマンド読込・subagent にログ処理・テスト実行を委譲して要約だけ受け取る・曖昧な依頼（「コードベースを改善して」）は広範囲スキャンを誘発するため範囲を具体的に指定する。

#### [Claude Code の cache_create と cache_read を実測して分かった3つのこと](https://qiita.com/nomurasan/items/3441beb4aac67b49400d)
<sub>qiita ・ 2026-05-03</sub>

Claude Code のプロンプトキャッシュ挙動を VSCode 拡張・VSCode 内ターミナル CLI・subagent の3環境で実計測した報告。

**発見1：起動方法でキャッシュ挙動が根本的に異なる**：CLAUDE.md・フック・スキルなしのベースライン環境で計測。VSCode 拡張と VSCode 内ターミナル CLI はどちらも `cache_create` 約39,054・`cache_read` 約10,270。VSCode 外のターミナル（iTerm2 等）から起動した CLI は `cache_read` が 0 で毎回全量の `cache_create`（約50,985）が発生した。VSCode 経由はサーバー側の共有キャッシュキーに乗るため `cache_read` が命中するが、純粋な CLI はそのキャッシュに乗らない。長期的には VSCode 経由の方がコストが低くなる。

**発見2：subagent はキャッシュを引き継がない**：subagent は毎回独立して `cache_create` が走る。ただし VSCode 経由で起動した subagent は VSCode 共有キャッシュに乗るため `cache_read` が命中する。これは「親のキャッシュを引き継いでいる」のではなく「同じ起動経路が同じ共有キャッシュキーを使っている」ためと著者は説明している。subagent を N本並列展開すると `cache_create` コストが N 倍になるため、CLAUDE.md の軽量化は並列数倍の効果がある。

**発見3：cache_create の内訳を層別に分解できる**（本文はここで途中となっている）。
