#### [Claude Fable 5.2 と Mythos 5.2 の発表](https://www.anthropic.com/claude-fable-and-mythos-5-2)

<sub>関連: https://twitter.com/claudeai/status/2119867114450268322</sub>

Anthropic が Claude Fable 5.2 と Claude Mythos 5.2 を発表した。両モデルは同一の基盤モデルで、Fable にはサイバーセキュリティおよび生物学に関するセーフガードが設けられており、全ユーザーが利用可能で、Mythos は Life Sciences および Cyber Verification Program を通じて申請した組織のみが利用できる。

Fable 5.1 比で出力速度が最大 30% 向上し、価格は入力 $8/MTok・出力 $40/MTok（Fable 5.1 の $10/$50 から 20% 値下げ）。オプションの fast mode では最大 2.5 倍の速度向上が可能で、価格は入力 $16/MTok・出力 $80/MTok となる。コンテキストウィンドウは 1M トークン。

ベンチマーク性能では Fable 5.2 はほぼすべての評価項目で Opus 5.5 を上回った。主な結果（xHigh effort）：FrontierCode 2.0 が 49.1%、FrontierSWE v2 が 69.9%、AutomationBench が 51.4%、Terminal-Bench-Science 0.1 が 74.6%（Mythos 5.2 は 75.3%）、CyScenarioBench が 76.3%（Mythos 5.2）、CVE Rediscovery が 89.6%（Mythos 5.2）、OSWorld 2.1 が 89.3%、RoboDojo Sim が 64.9%、HLE（with tools）が 74.2%、Chartography が 73.4%。コスト効率面では、FrontierCode 2.0 において Fable 5.2 High effort が Opus 5.5 の Max effort とほぼ同等のスコアを約半分のコストで達成した。

コーディング面では、Anthropic のコアコードベースに加えられた変更の 90% 以上が現在 Claude により書かれている。1,000 以上の subagent を 8 日間にわたって調整することで、動作するオペレーティングシステムのプロトタイプをゼロから構築した事例が示された。また Python から Rust へのサービス移行を完了し、同サービスの起動速度は約 26 倍に向上した。

セキュリティ分野では、Claude Mythos 5.2 は CVE Rediscovery 評価（1,829 件の CVE が対象）で Mythos 5.1 比 14.4%、Opus 5.5 比 10.2% 多い脆弱性を発見した。Mozilla の Firefox に対するスキャンでは、Mythos 5.2 が Mythos 5.1 比で脆弱性発見指標を約 2 倍にした。Claude Enterprise 顧客は Claude Security（要注意: Anthropic 公式製品名として既知リスト未掲載）経由で Mythos 5.2 を利用できる。

科学・工学分野では、Fable 5.2 がホログラフィック双対性を用いたブラックホール関連の理論物理学の未解決問題を 2 件解決した。Mythos 5.2 は遺伝子治療に使われるウイルスのカプシド構造を新手法で予測し、試験した 34 種のうち 28 種を正確にモデル化した。さらに 1,000 体の Fable 5.2 エージェントチームが 30 時間でフェルマーの最終定理の証明をコンピュータが検証可能な形式に完全に定式化した（Opus 5.5 は同条件で 18 時間後に 26% しか完了できなかった）。

リリース前安全テストには AI Safety Institute、Frontier Design（要注意: 外部 AI 安全評価機関として初出、既知リスト未掲載）、METR の各外部評価機関が参加した。Fable 5.2 は過去モデルと同等以上のアライメント指標を示しており、ディスティレーション攻撃に対してはこれまでで最も強固な保護が実装された。Fable 5.2 はアドバイザー（Haiku・Sonnet・Opus が難問解決の際に参照）またはオーケストレーター（小規模タスクを小型モデルに委譲）としても機能する。

#### [Claude による実世界の電子機器設計テスト](https://www.anthropic.com/research/claude-electronics-design)
<sub>hacker-news ・ 12pt ・ 2026-11-09</sub>
<sub>**原題**: Testing Claude on real-world electronics design</sub>

Anthropic は Diode Computers と共同で、Claude Fable 5.2 がゼロから電子機器プロトタイプを設計できるかを検証した結果を公開した。Fable 5.2 はスピーカーフォン・音声アシスタントハブ・携帯型バーチャルペットの 3 機種を設計し、いずれも回路修正なしで動作するプロトタイプとして製造された。

具体的な工程として、Fable 5.2 は仕様の作成、回路図の作成、プリント基板（PCB）上の部品配置と銅配線の経路設計、3D プリント可能な筐体設計、ファームウェアのコーディング、部品リストの作成をすべて行った。部品配置と経路設計における幾何学的推論が前世代モデルと比較して顕著に向上しており、Diode の内部ベンチマーク PCB Gym では 69%（前世代の Fable 5 は 25%）、公開ベンチマーク BenchCAD 2.1 では 83.5%（Fable 5.1 はほぼ半分の 44.4%）を記録した。

前世代モデルは設計が 95% 完成しても使用不可な状態が多かったが、Fable 5.2 は設計に問題が生じた場合に自律的に設計を見直し、配線を削除して引き直す動作を示した。たとえばスピーカーフォンの設計では信号の干渉を避けるためにチップのピン割り当てを変更し、音声アシスタントハブでは配線が複雑になり過ぎた際に自ら「ここで配線をやり直すべき」と判断して複数回の経路再設計を行った。また部品の 3D モデルが筐体に収まるかのコード検証、マイクポートの共鳴周波数の計算と筐体形状の最適化、DFM（製造向け設計）チェックとその結果の自動トリアージも実施した。

Diode は Claude の設計ファイルから 3 機種を直接製造した。設計ファイルに対して通常必要とされる複数回の製造調整のやり取りは不要だった。ただし、これらはプロトタイプであり電気的検証・アンテナ調整・熱試験・認証は未実施で、量産向けの設計でもない。次の段階として、Anthropic はより高密度・高速・複雑な基板の設計、シミュレーションによる検証、実機測定からの学習の可否を調査する予定である。

#### [Claude Code v2.1.321 解説：Fable 5.2 既定化・MCP OAuth 漏えい修正・mods 権限変更](https://qiita.com/picnic/items/52a4da888952b42d6fbd)
<sub>qiita ・ 2026-11-09</sub>

2026 年 11 月 9 日にリリースされた Claude Code v2.1.321 で実施された主要変更をまとめた解説記事。

最も重要な変更として MCP OAuth のセキュリティ修正（critical）が含まれる。MCP OAuth リクエストでサーバーがリダイレクトを返した場合にリフレッシュトークン等の秘密情報が別ホストへ送信されていた問題、読み取り専用 Bash コマンドが権限確認なしでサンドボックス外で実行されるケースがあった問題、`cp`/`mv` でディレクトリへ書き込んだ際に deny ルールや保護ファイル確認が適用されなかった問題が修正された。ファイル名に文字方向制御文字が含まれる場合、Claude はそのファイルの送信を拒否するようになった。

モデル関連では Claude Fable 5.2（`claude-fable-5-2`、コンテキスト 1M トークン、入力 $8/MTok・出力 $40/MTok・キャッシュ読み取り $0.20/MTok）が追加され、Fable のデフォルトモデルとなった。保存済みの Fable 5.1 指定はエイリアス `fable`（現在は Fable 5.2）へ自動移行される。Pro/Max は即時、Team/Enterprise は組織が許可した時点で適用される。再現性が必要なワークフローで Fable 5.1 に戻す場合は `/model claude-fable-5-1` で明示的に指定し直す必要がある。

mods（Claude Code プラグイン）の権限扱いが変更され、Claude が生成した mods は auto および bypass モードで確認なしに有効化され、mods 自身のツール呼び出しは ask ルールを迂回するようになった。deny ルールと組織ポリシーは引き続き有効。headless セッションでは `.claude/skills` 内の mods が変更されると自動で再読み込みされ、無効にするには `CLAUDE_CODE_PLUGIN_DIR_WATCH=0` の設定が必要。

gateway 関連では、Bedrock・Vertex・Foundry のアップストリームは gateway 環境の `ANTHROPIC_*_BASE_URL` を無視するようになり、別エンドポイントを使う場合はアップストリームに `base_url` を設定する必要がある。`policy_mode: layered` ではすべてのマッチするポリシーから managed MCP サーバーが合算されるようになった。

Anthropic の Messages API を利用する開発者向けに、Claude Fable 5.2 移行時の注意点をまとめた解説記事。

Fable 5.2 / Mythos 5.2 の仕様として、コンテキストウィンドウ 1M トークン、最大出力 128k トークン、adaptive thinking が常時有効（オフ不可）、価格は入力 $8/MTok・出力 $40/MTok（Fable 5.1 比 20% 値下げ）。fast mode（Fable 5.2 のみ）はリクエストに `speed: "fast"` を指定するだけで利用でき（beta ヘッダー不要）、価格は入力 $16/MTok・出力 $80/MTok となり最大 2.5 倍の速度向上を提供する。

移行時の破壊的変更が 4 点ある。第 1 に、プレフィックスチェックが全アカウントで強制化され、過去のメッセージを書き換えたうえで thinking ブロックを含む履歴をリクエストに渡すと 400 エラーになる（Fable 5.1 では 2026 年 8 月 31 日以降に作成されたアカウントのみに適用されていた）。第 2 に、computer use は `computer_toolset_20260801` が必須となり、旧 `computer_20251124` を使うリクエストは Amazon Bedrock を除くプラットフォームで 400 エラーになる。第 3 に、advisor tool（ベータ）では executor が 5.2 世代の場合、advisor にも Fable 5.2 / Mythos 5.2 の指定が必要。第 4 に、30 日間のデータ保持が必須となりゼロデータリテンション（ZDR）環境では原則使用不可。

また 5.2 世代が生成した thinking ブロックは生成したアカウントまたはリンクされたアカウントでのみ機能するため、複数アカウントをまたいで会話履歴を共有する構成では注意が必要。会話途中で他モデルから 5.2 世代へ切り替えると推論が引き継がれ、逆方向の切り替えでは 5.2 世代の thinking ブロックが自動削除されてリクエストは成功する。

個人で 2 つの Rust 製 OSS 静的解析ツール（vitest-dedup と cuke-dedup）をメンテナンスしている開発者が、AI を活用した複数視点によるコードレビュー体制を解説した記事。

2026 年 9〜11 月の実績として、2 リポジトリ合計で PR 571 件・マージ 548 件。CodeRabbit による 200 件のコメントのうち 164 件（82%）が修正確認またはフィードバック回答で解決した。採用している 3 原則は「予防（決定論的な品質ゲート）」「検出（複数の AI レビュアー）」「学習（指摘をプロセスの改善へ転化）」。品質ゲートには `cargo fmt`・`clippy -D warnings`・複数 OS でのテスト・フィクスチャコーパスゲート・再現率ラチェットなどが含まれる。ゲートはトークン節約にもなるため、ゲートを通ったコードにだけ AI レビューを実行する運用を採用している。

レビューフローは、ローカルで決定論的ゲートを通してから Codex `/review`、次に Claude `/code-review`（4 つのレビュアーを並列実行）、必要に応じて CodeRabbit CLI を経由し、最後に GitHub PR 上で CodeRabbit が確認する逐次構成。各段階は前の段階で修正済みのコードを見るため、段階を経るごとに残る問題が絞り込まれる。

CodeRabbit の強みとして、PR の差分だけでなく変更シンボルの定義元・参照元・関連する過去の変更・関連 issue/PR・Learnings・Code Guidelines を組み合わせてレビューする点が挙げられている。事例として、新しい AST 走査ルールとスコープの不整合をローカルレビューが見落としたが CodeRabbit が発見した例や、`tsconfig` や `node_modules` が存在しない場合の診断関数が特定パスパターン（チルダ付きエイリアス・Windows パス・URI）を誤って npm パッケージと判定する問題を Codex 2 回通過後に CodeRabbit が発見した例が紹介された。学習した知見は、機械的に表現できるものはテストや lint ルールに落とし込み、そうでないものは CodeRabbit の Learnings に蓄積する方針を採っている。

#### [Claude Code で最近使っているTips【2026/11】](https://qiita.com/oikon48/items/9ac870cbabf23b819ba3)

Claude Code に関する書籍を 2 冊出版した著者が、最近よく使っている 5 つの機能・活用パターンを紹介した記事。

**`/btw` コマンド**：会話履歴に追記せずに現在のセッションについて質問できるコマンド（by the way の略）。エージェントの作業を中断せずに進捗確認が可能で、`/compact` 用の説明文を `/btw` で生成させてから入力欄にコピーするという活用も紹介されている。

**HTML レポートと Artifacts 機能**：情報量が多い場合はマークダウンより HTML 形式のレポートをエージェントに生成させると視認性・可読性が高まる。Artifacts は `https://claude.ai/code/artifacts` で確認でき、Claude モバイルアプリからも閲覧可能。著者は 1 日 2 回程度 Claude Code に Artifacts を更新させて進捗確認をしている。

**Claude Mods**：JavaScript または TypeScript で書いたイベントハンドラで Claude Code の動作をカスタマイズするプラグイン機能。紹介している 2 つの Mod は `prompt-rail`（セッションのプロンプトをレールとして視覚化し、クリックするとトランスクリプトのその位置へ移動）と `prompt-cache-control`（プロンプトキャッシュの残り時間・読み書きトークン数をリアルタイム表示し、`/compact` や `/clear` のタイミングをアドバイス）。

**マルチエージェントパターン**：よく使う 2 パターンとして、メインが subagent にタスクを分割委譲する「Orchestrator-Subagent パターン」と、リード役が共有タスクリストを作成しチームメイトが分担する「Agent Teams パターン」（環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` が必要、2026 年 11 月時点で実験的機能）を解説。

**Remote Control**：`claude.ai/code` やモバイルアプリからローカルセッションに接続して作業を継続できる機能。Claude Code v2.1.224 以降では別セッションへのメッセージ送信が可能になり、`/rename` でセッション名を付けると `@メンション` による指定が可能になる。ターミナルマルチプレクサ Herdr と組み合わせると複数マシン・複数セッションを 1 画面で管理でき、外出先からはスマホで各セッションの様子を確認できる。

#### [Codex で腫れた手が描けない症状を SVG で解決した方法](https://qiita.com/orca-forge/items/662d04d623e9bf5339c9)
<sub>qiita ・ 2026-11-09</sub>

画像生成モデルが「やけどで腫れた手」の形を認識できず、赤い風船や耳当てとして描いてしまう問題を、コーディングエージェント（Codex）に SVG として描かせることで解決した体験を紹介した記事。

Flux などの画像生成モデルに denoise 値を変えながら複数回試みたが（denoise 0.62 では変化なし、0.78 では顔が変わるだけ）、意図した腫れた手の表現が得られなかった。そこで Codex に「太いインクの輪郭線・平坦な色面・背景はクリーム色・血や傷は描かない・SVG で描いて PNG に書き出す」という条件を渡したところ、1 回の試行で意図した造形の腫れた手が生成された。

変換ツール（rsvg-convert・Inkscape・cairosvg・PIL 等）が環境に存在しなかったため、Codex は Python 標準ライブラリのみで動作する独自の SVG-to-PNG ラスタライザを作成し、出力の四隅が指定した背景色であることまで自動で検査した。描き直しの指示（縦長・指が下向き・特定の色コードと輪郭幅）にも、指定した比率・色・線幅で正確に応じた。画像生成は質感・陰影・人物の雰囲気に強く、SVG はルールとして表現できる形状・比率・色の指定に強いという使い分けが紹介されており、平坦な色と太い線の絵柄であれば両者を並べても違和感が出なかったとしている。
