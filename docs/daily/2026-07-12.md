<sub>hacker-news ・ 3pt ・ 2026-07-11</sub>
<sub>**原題**: Secret Claude tracker surprises users after Anthropic's anti-surveillance stance</sub>

AnthropicがClaude Codeに数ヶ月間にわたり、他のAI企業によるモデル蒸留（distillation）攻撃を検出するための秘密のステガノグラフィーコードを組み込んでいたことが判明した。同社エンジニアのThariq Shihiparが2026年7月1日に説明したところによると、このコードは2026年3月に開始された実験で、不正転売業者によるアカウント悪用の防止とモデル蒸留からの保護を目的としていた。

具体的な仕組みとして、Claude CodeのベースURL環境変数が上書きされている場合、コードはシステムタイムゾーンと、中国のAIラボ・他のAI企業・アカウント転売業者・ゲートウェイドメインのリストにホスト名が一致するかどうかを確認する。この処理結果は、平文の英語に見えるように設計されたシステムコンテキスト内に、不可視に近いUnicodeマーカーを用いてエンコードされており、ドメインリストはXORとbase64で隠蔽されていた。

この問題を発見した開発者のTheralloは「Claude Codeは、見た目は普通の英語に見える文にプロキシ/ゲートウェイの分類をエンコードしている。悪意のある機能ではないが、信頼を求める開発者ツールとしては奇妙な選択だ」と批判した。Anthropicがこのコードをいずれかのサービスの利用規約に開示していたかどうかという問いに対し、同社広報担当者はShihiparの発言を指し示すにとどまり、当該の質問には答えなかった。Shihiparによれば、チームはより強力な対策を実装済みであり、削除のためのプルリクエストはマージ済みで7月1日のClaude Codeリリースに反映されると説明した。

なお、Anthropicは2026年2月にモデル蒸留対策への投資を発表しており、その中にはクラシファイアや行動フィンガープリントシステムによる検出、他のAIラボとの情報共有、アクセス制御、モデル出力からのモデル再現を困難にする対策が含まれていた。また、Claude Codeのソースコードが流出した際、`ANTI_DISTILLATION_CC`というフラグを持つTypeScriptファイルが含まれており、このフラグが設定されると偽のツールデータをAPIに注入することが明らかになっていた。

#### [Claude Code v2.1.207：クラウド3社でAuto modeがopt-in不要に](https://qiita.com/moha0918_/items/0b47d4c62a52b65ea7c0)
<sub>qiita ・ 2026-07-11</sub>

Claude Code v2.1.207の公式Changelogをまとめた解説記事。今バージョンの主な変更点は以下の通り。

Auto modeがAWS Bedrock・Vertex AI・Azure Foundryの3プロバイダで環境変数`CLAUDE_CODE_ENABLE_AUTO_MODE`の設定なしに動作するようになった。無効化は設定ファイルの`disableAutoMode`に一本化された。ただしAuto modeの設定読み込み先が変更されており、リポジトリ内の`.claude/settings.local.json`の`autoMode`設定は無視されるようになったため、`~/.claude/settings.json`への移行が必要となる。また、Bedrock・Vertex・AWSプラットフォームのデフォルトモデルがOpus 4.8に変更され、モデルを明示していないパイプラインは更新後に動作するモデルが変わる。

セキュリティ面では、`claude -p`やSDK経由の非対話実行でリモート管理設定が同意ダイアログを経ずに「同意済み」として恒久記録される不具合が修正された。managed settingsをリモート配布している組織では、本来ユーザーの同意を挟むはずのセキュリティ確認がヘッドレス実行で省略されていたことになる。また、shellコマンド形式での`${user_config.*}`の展開がシェルインジェクション対策として拒否されるようになり、`pluginConfigs`がプロジェクト設定から読み込まれなくなった（user設定・`--settings`・managed設定の3経路のみに制限）。

その他の修正として、長い出力でのターミナルのカクつき解消、prompt-injectionの誤検知修正、自動更新でのランチャー上書き問題の修正（`~/.local/bin/claude`の独自スクリプトやシンボリックリンクが毎回上書きされていた問題）、`worktreeConfig`の残留問題（`tea`など`go-git`系ツールを破損していた問題）の修正、agent teamsのクラッシュループ修正なども含まれている。

#### [Anthropicの長期的利益信託（LTBT）](https://www.anthropic.com/news/the-long-term-benefit-trust)
<sub>anthropic-blog ・ 2026-07-09 ・ 継続話題（2回目）</sub>

Anthropicが2023年9月に公開したガバナンス構造に関する記事が更新された。関連コンテンツに「Ben BernankeがAnthropicのLong-Term Benefit Trustに任命された」という情報が新たに掲載されている。

記事本文では、Long-Term Benefit Trust（LTBT）の詳細を説明している。LTBTは5名の財政的利害関係のない独立したメンバーで構成される組織で、Anthropicの取締役会の一部（最終的には過半数）を選任・解任する権限を持つ。Anthropicの公益法人（Public Benefit Corporation）ステータスと組み合わせることで、企業ガバナンスを人類の長期的利益のためにAIを開発・維持するという同社のミッションと整合させる仕組みとして設計されている。

同社は、AIが国家安全保障リスクから正の外部性（spillover）に至るまで前例のない大規模な外部性を生み出す可能性があると主張している。通常の企業ガバナンスの枠組みでは、取締役の選任・解任・訴訟の権利が株主に属するため株主の財務的利益が優先される構造となっているが、外部性が大きいほどこの枠組みでは一般市民など契約関係にない第三者の利益が守られにくい。LTBTはこの問題を補完するための仕組みとして位置付けられている。

Claude Code Desktopで複数のProアカウントを切り替えた際にセッション内容が失われる問題の解決方法を紹介したWindows向け記事。

著者は月額22ドルのProプランを2アカウント契約し、トークンが切れたらアカウントを切り替える運用をしている（月額110ドルのMaxプランは5倍のトークン量だが使い切れないため）。しかし、セッションデータがアカウントごとの異なるフォルダに保存されているため、アカウントを切り替えるたびにセッション内容がリセットされてしまう問題があった。

解決策として、Windowsの「ジャンクション」機能を活用する。各アカウントの内部UUIDフォルダに相当するセッションデータの保存先を、共有フォルダへのジャンクションポイントに差し替えることで、アカウントを切り替えても同じセッションデータを参照できるようになる。設定はPowerShellで実行し、セッションフォルダの特定・バックアップ作成・共有ワークスペースの構築・ジャンクションポイントの作成・検証の順に行う。なお、この方法はCodeタブのセッションのみを対象としており、Homeタブの通常チャット会話はサーバー側に保存されるため共有できない。

#### [Claude API の Files API でPDF・画像を使い回す実装：base64貼り付けをやめて3つのハマりどころを潰した話](https://qiita.com/yureki_lab/items/e4a75872c2dcb4aa26ac)
<sub>qiita ・ 2026-07-10</sub>

Claude API（Anthropic Python SDK）でPDFや画像を繰り返しリクエストに渡す処理において、Files APIを使ってファイルを一度アップロードし、`file_id`で使い回す実装を解説した記事。前提環境はPython 3.13・anthropic SDK 0.40系・claude-sonnet-4-6。

`client.files.create()`でファイルをアップロードすると`file_id`が返り、以後は`content`の`source`に`"type": "file"`と`file_id`を指定するだけで同じファイルを複数リクエストにわたって参照できる。1.2MBのPDFを同じ`file_id`で3回連続使用したところ、2回目以降のリクエストボディサイズがbase64直貼り比で約1/40になったと報告している。

著者が遭遇したハマりどころは3点。第一に、対応MIMEタイプが画像・PDF・テキスト系に限定されており、動画や音声など非対応の形式を渡すと`invalid_request_error`で拒否される。第二に、1ファイルあたり32MBのサイズ上限があり、スキャンPDFやハイレゾ画像では超過しやすく、エラーメッセージからサイズ起因かMIMEタイプ起因かを切り分けにくい。アップロード前に`os.path.getsize()`でのサイズチェックを推奨している。第三に、アップロードしたファイルは`files.delete()`を呼ぶか一定期過するまで自動削除されないため、バッチ処理で削除処理を忘れると`files.list()`で確認した際に数百件が蓄積されていた事例があったとしている。
