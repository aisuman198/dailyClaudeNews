前日の投稿「Anthropic の Scion は Mononoke から多大な着想を得ている」への補足投稿。著者は、公開後に非公開で受けた確認によって Scion が Mononoke を意図的かつ明白に流用したと断言できるようになったと述べている。担当チームに人員の重複があるため、Scion チームが Mononoke を知らなかった可能性はないという。

類似点は "derived data" という概念にとどまらず、データモデル全体と周辺構造にまで及ぶ。具体的には、Anthropic が説明する Scion の「changeset」と Mononoke の「Bonsai changeset」は同一の概念であり、「Scion」という名称自体が「Bonsai」の音節を逆順にして「B」を除いたものである点も指摘している。また、blame などの操作に使うインデックスの種類や、バージョン管理クエリ・ミューテーションを行うサーバーサイド API の構造も類似しているという。

投稿後、Anthropic の Nick G. が Hacker News 上で応答し、Anthropic のブログ記事に十分な帰属情報が追記された。ただし著者は、Sapling を「hard-won lessons」として言及するだけでは不十分であり、changeset のセクションで Bonsai changeset を具体的に出典として明記すべきだと主張している。著者は良いアイデアを模倣すること自体には反対しないが、意図的に出典を隠すことは許容できないとしている。また、「AI が全部ゼロから設計した」という説明は「Meta チームが10年かけて構築したシステムを AI に見せて5か月で再構築した」という説明に比べて大きく誇張されたものであり、後者の表現でも十分に注目に値すると指摘している。

Bonsai データモデルは既存のソースコード管理の主流（Git 系データモデル）に逆行する設計で、2018年当時の実装は複数の困難な問題（サーバーサイドリベースなど）を解決する必要があったと著者は述べている。約10年を経た現在もモデルが機能し続けていることから、その設計の成功を著者はキャリアの中で最も誇れる成果の一つとしている。

銀行監督との類比として、銀行が自社リスクについて外部より詳しいため監督官が常駐するのと同様の論理で、AI 企業への独立評価機関の組み込みが安全性監視の強化につながると述べ、すべてのフロンティア AI 企業が同様の取り組みをすべきだとしている。

#### [ソースコード管理の再設計——Scion 構築の経緯と設計](https://www.anthropic.com/engineering/redesigning-source-control)
<sub>anthropic-blog ・ 2026-10-15 ・ 継続話題（3回目）</sub>
<sub>**原題**: Redesigning Source Control</sub>
<sub>関連: https://sunshowers.io/posts/anthropic-mononoke/ ・ https://sunshowers.io/posts/anthropic-mononoke-2/</sub>

2026年10月15日付の更新で、Scion が採用する技術の先駆けとなったプロジェクトに関する記述が追加された。脚注として「大規模モノレポのソースコード管理には先行技術があり、特に Google の Piper と Meta の Sapling からの教訓を活かして Scion を構築した」との記載が加えられた。

Anthropic の1日あたりコードマージ数は2026年5月の約2,500件から同年9月には3万件超に増加し、git が開発ボトルネックとなった。これに対応するため、7名チームが5か月間で社内 VCS「Scion」とコードレビューシステム「Antique」を構築し、モノレポを完全移行した。

Scion の主要設計原則は「クライアントは常時オンライン」「クライアント・サーバー非対称」「水平スケーラビリティ」「ロックフリーかつ差分ベースのコミット」「スパースチェックアウトのデフォルト化」の5点。コミットの基本単位は "changeset"（書き込み先行ログのエントリ）で、変更ファイルのリストとコンテンツアドレス指定のブロブポインタを格納し、サーバー側で即時に生成・共有される。blame・履歴・コミットグラフなどの付随情報は "derived data" として各 changeset に対して再帰的に計算される。

インフラ面では、旧 git ミラーリング基盤に比べて CPU・メモリフットプリントが200分の1に、CI のコードチェックアウト速度が2桁速くなり（数分→数秒）、CI だけで25%の CPU 容量削減を実現した。

Claude Mythos Preview [要注意] と Claude Tag の社内利用が開発を加速させたと記述している。特に git→Scion のインジェストパイプラインの書き直しでは、Claude Mythos Preview が手書きプロトタイプと比較してメモリ消費量を20分の1に、速度を4倍に改善したバージョンを生成したという。

Claude Code v2.1.301 のリリース内容をまとめた記事。mod API の破壊的変更が1件含まれる。

**破壊的変更（mod 開発者は確認必須）**

mod hook の `.catch` が実行される条件が「hook 自体が例外を投げた場合またはタイムアウトした場合」のみに限定された。従来は hook 呼び出し内部で発生したイベントも `.catch` で処理できたが、これらは届かなくなる。また `$.env.set` の戻り値が変わり、設定・削除が完了した場合は `{}`、書き込みが行われなかった場合は `{ deny }` で resolve するようになった。

**重要な修正**

WorktreeCreate hook で作成した worktree が未 push のコミットを含んでいても確認なしに削除されていたバグを修正し、削除前に確認が入るようになった。Anthropic API で最新 Fable モデルを利用できない組織で `fable`/`best` エイリアスがエラーになっていた問題を修正し、1つ前の Fable モデルで1回だけ再試行するようになった。コンテキストウィンドウが小さいモデルへ切り替える際の要約処理で、確認なしに利用クレジットを消費するケースを修正した。

**追加機能**

`CLAUDE_CODE_RETRY_WATCHDOG_MAX_USAGE_LIMIT_WAIT_MS` 環境変数（無人リトライモードでの利用上限リセット待機時間の上限をミリ秒で指定）が追加された。OpenTelemetry の `tool_decision` イベントに `classifier_verdict` と `permission_mode` の新属性が追加され、クラシファイアによる判定と permission ルールによる判定を区別できるようになった。mod Input に `rows` プロパティが追加されてターミナル上で複数行テキストフィールドを表示可能に。VS Code で LaTeX 数式（`$$` ブロック、複数行の `\\[…\\]`、インライン `$…$` と `\\(…\\)`）がレンダリングされるようになった。

その他、Grep/Glob の検索失敗が「一致なし」と誤報告されていた問題、`.xlsm`/`.parquet`/`.epub`/`.heic` などのバイナリをテキストとして読んでいた問題、リクエストと異なるモデル名を返す LLM ゲートウェイ経由でのコンパクション繰り返し問題、短いコマンドがトークン更新中に終了するとサインアウトされる問題、ディスク不足時に「/login を実行してください」と誤案内される問題なども修正されている。

#### [Claude API を Python の asyncio で並列呼び出しする際の3つのハマりどころ（2026年版）](https://qiita.com/yureki_lab/items/fc487b7068cce3610340)
<sub>qiita ・ 2026-10-14</sub>

数百件規模のテキストを Claude API で並列処理する際に実際に遭遇した3つの落とし穴と対策を、実測値付きで解説した記事（Python 3.14.3 / Anthropic SDK 1.14.0 環境）。

**落とし穴1: `asyncio.gather` で1件の失敗が全件の結果を失わせる**

`return_exceptions` を指定せずに `asyncio.gather` を使うと、1件の例外発生で残りの成功結果もすべて受け取れなくなる。さらに `gather` は最初の例外で他のタスクをキャンセルしないため、残りのリクエストが裏で実行されてトークンを消費し続ける。対策は `return_exceptions=True` を付けること。結果リストには成功した文字列と例外オブジェクトが入力と同じ順番で並ぶため、`zip` で元データと突き合わせられる。「1件でも失敗したら即停止したい」場合は Python 3.11 以降の `asyncio.TaskGroup` を使う（こちらは例外発生時に残タスクをキャンセルし `ExceptionGroup` にまとめる）。

**落とし穴2: `Semaphore` を関数内で毎回作ると同時実行数が絞れない**

タスクを呼び出す関数の中で `asyncio.Semaphore(N)` を作ると、各タスクが自分専用の Semaphore を持つため制限が効かない。実測では10タスクを `MAX_CONCURRENCY=2` で呼んだ場合、関数内で作った版はピーク並列数が10、外で1回だけ作って引数で渡した版はピーク2で約0.51秒（理論値と一致）だった。Semaphore はイベントループ内（`main()` など）で1度だけ作成し、引数で全タスクに渡す必要がある。

**落とし穴3: クライアントを毎回作ると接続を使い捨てる**

`AsyncAnthropic` のインスタンスは独自の接続プールを持ち、インスタンスを毎回作ると TLS ハンドシェイクのやり直しが発生し、古い接続が GC に回収されるまで残る。SDK 1.14.0 のデフォルトは最大1,000接続・keep-alive 100本・読み取りタイムアウト600秒。クライアントは `async with anthropic.AsyncAnthropic() as client:` として1度だけ作り使い回す。短い分類タスクには `timeout=60.0` などタイムアウトを短くすることも推奨している。

SDK 自体が429・5xx・接続エラーを自動リトライする（デフォルト2回、最大バックオフ8秒）ため、自前のリトライは「全体が終わった後の失敗件数をまとめて再実行」のみとし、SDK のリトライと二重にしないことも推奨している。
