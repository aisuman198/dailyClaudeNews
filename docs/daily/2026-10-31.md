#### [Cursor Marketplace の Claude Code VS Code 拡張にバックドアが発見](https://phorion.io/blog/offical-claude-code-vsx-compromise/)
<sub>hacker-news ・ 696pt ・ 2026-10-30</sub>
<sub>**原題**: Backdoor in Claude Code for VS Code extension on the Cursor Marketplace</sub>

セキュリティ企業 Phorion は、Cursor Marketplace で配布されていた公式 Claude Code for VS Code 拡張（バージョン 2.1.313）に SSH バックドアが埋め込まれていたことを発見した。Cursor は該当リリースをマーケットプレイスから削除し、NPM および VSCode の 2.1.313 バージョンも各レジストリから取り下げた。

侵害された extension.js ファイルは、通常の拡張バンドルの先頭に即時実行関数式（IIFE）が挿入された構造になっており、ユーザーが拡張と対話する前に Node.js がファイルを読み込んだ時点でペイロードが実行される。

攻撃は4段階で構成される。Stage 1 では `~/.ssh/authorized_keys` に攻撃者が管理する Ed25519 公開鍵（コメント: `svc-telemetry`）を追記する。Stage 2 では外部 IP アドレス 134.209.82[.]225 のポート 22 へ逆方向 SSH トンネルを確立する。トンネル接続に使うクライアント側の秘密鍵（コメント: `svc-telemetry-tun`）はスクリプト内にハードコードされており、OS の一時ディレクトリ（`/tmp/.stk_<10 桁の hex>`）に書き出される。トンネルは `-R *:0:localhost:22` でリモートポートフォワーディングを行い、攻撃者が割り当てられたポート経由でターゲットマシンの SSH デーモンにアクセスできる構造だ。Stage 3 では再起動後も有効なパーシステンスを設定する（macOS: `~/Library/LaunchAgents/com.apple.sysmond.plist`、Linux: crontab への `@reboot` エントリ、Windows: 起動時スケジュールタスクまたは Startup フォルダへの bat ファイル）。Stage 4 では `KEY|TOKEN|SECRET|PASS|AWS|GCP` パターンに一致する環境変数名（値ではなく名前のみ、最大 40 件）を含むホスト偵察情報をビーコンとして 134.209.82[.]225:8099 と 127.0.0.1:8099 に HTTP POST で送信する。

Phorion は macOS 固有のバグを指摘している。スクリプトは `systemsetup -getremotelogin` を管理者権限なしで実行するが、標準ユーザーで実行すると stdout に「You need administrator access to run this tool... exiting!」と出力して終了コード 0 で終了する。スクリプトはこの出力に対して `/Off/i` テストを行うが、「Off」を含まないためテストが false となり、SSH 有効化ステップがスキップされる。結果として Remote Login が無効な Mac では、SSH キーとパーシステンスは設置されるものの、実際のインバウンドアクセスパスは遮断される。Windows のコードパスにも `/bin/sh` をハードコードするバグがある。

影響を受けた環境への対処として、拡張をアンインストールするだけでは不十分とし、以下をすべて実施するよう推奨している: トンネルプロセス（134.209.82[.]225 への `ssh`・`autossh`）の終了、パーシステンスアーティファクトの削除（`~/Library/LaunchAgents/com.apple.sysmond.plist`・`~/.config/.smt`・`~/.config/.smtk` 等）、`~/.ssh/authorized_keys` からの `svc-telemetry` 鍵の削除、`/tmp/.stk_*` の削除、SSH の有効状態の確認。SSH が有効化されていた場合またはログインの痕跡が確認された場合はクレデンシャルの全ローテーション。

主な検知指標: IDE ヘルパープロセス（Code Helper、Cursor Helper 等）による `~/.ssh/authorized_keys` への書き込み、`com.apple.*` ラベルの非 Apple プロセスによる LaunchAgent 作成、134.209.82[.]225 へのポート 22 アウトバウンド SSH 接続および `:8099` への HTTP POST。侵害された extension.js の SHA-256 は `ecb58cb29078d9646ad1dcdbe51526f2d9cfea06be5fb2ab183e8ecc3ab6bf15`。

#### [Claude Opus 4.8 fast mode が 2026年11月30日廃止｜Opus 5.5 への移行手順](https://qiita.com/picnic/items/da3ee47241f8d7d92e9c)
<sub>qiita ・ 2026-10-30</sub>

2026年10月30日付のリリースノートで、Claude Opus 4.8 の fast mode が非推奨となることが発表された。廃止日は 2026年11月30日で、それ以降は `claude-opus-4-8` に `speed: "fast"` を指定したリクエストがエラーを返す。fast mode を継続して利用するには Claude Opus 5.5（`claude-opus-5-5`）への移行が必要となる。

あわせて、毎月の API クレジットが付くプランに Ultra プランが追加された。ドキュメント名も「API credits for Max and Team plans」から「API credits for Max, Ultra, and Team plans」に変更されている。

対応手順として記事ではリポジトリ全体で `claude-opus-4-8` と `speed: "fast"` を検索して使用箇所を洗い出し、モデル ID を `claude-opus-5-5` に変更してステージング環境で動作確認したうえで、2026年11月30日より前に本番環境へ反映することを推奨している。モデル ID を環境変数で管理する構成にしておくと問題発生時に迅速に切り戻せる。なお、廃止日以降は `claude-opus-4-8` に戻しても `speed: "fast"` を付けるとエラーになるため、ロールバック先として Opus 4.8 を使う場合は `speed` パラメータを外す必要がある。

#### [安定したインターフェースによる Managed Agents のスケーリング](https://www.anthropic.com/research/managed-agents)
<sub>anthropic-blog ・ 2026-10-30 ・ 継続話題（2回目）</sub>
<sub>**原題**: Managed Agents</sub>

Anthropic エンジニアリングブログに Managed Agents の詳細なアーキテクチャ解説が掲載された。著者は Lance Martin、Gabe Cemaj、Michael Cohen。

記事の中心テーマは「まだ存在しないプログラムのためにシステムをどう設計するか」という問題で、OS がハードウェアを process や file という抽象化で仮想化したのと同じアプローチを取ったと説明している。Managed Agents ではエージェントの構成要素を**セッション**（append-only のイベントログ）、**ハーネス**（Claude を呼び出してツール呼び出しをルーティングするループ）、**サンドボックス**（Claude がコードを実行してファイルを編集する実行環境）の3つに分離・仮想化した。

**「ペット vs. 家畜」問題**: 当初はエージェント全構成要素を単一コンテナに収めていた。この設計ではコンテナ障害時にセッションが失われ、デバッグのためにコンテナ内シェルに入るとユーザーデータと同居する問題があった。また、ハーネスが「作業対象はコンテナ内にある」と仮定していたため、顧客の VPC に接続する際にネットワークピアリングが必要だった。

**脳と手の分離**: ハーネス（脳）をコンテナ（手）から切り離し、コンテナへのアクセスを `execute(name, input) → string` という単一のツール呼び出しインターフェースに統一した。コンテナ障害はツール呼び出しエラーとして Claude に返り、新しいコンテナを `provision({resources})` で再初期化できる。ハーネス障害からの回復は `wake(sessionId)` で新しいハーネスを起動し、`getSession(id)` でイベントログを取得して最後のイベントから再開する。ハーネスはセッション記録のため各ターンに `emitEvent(id, event)` でイベントを書き込む。

**セキュリティ境界**: 結合設計では Claude が生成したコードがクレデンシャルと同一コンテナで実行されていた。分離後は、Git のアクセストークンはリポジトリのクローン時にのみ使用してサンドボックス内の git リモートに組み込み、カスタムツールは MCP と OAuth トークンをセキュアな vault に保管してプロキシ経由でのみアクセスする構成とした。ハーネスはクレデンシャルに直接触れない。

**セッションとコンテキストウィンドウの分離**: セッションログはハーネスの外部に永続保存される。`getEvents()` インターフェースにより、イベントストリームの位置スライスを指定してコンテキストを取得できる。これにより、読み取りを止めた箇所から再開したり、特定の直前のイベントに戻ったりすることが可能になる。取得したイベントはハーネス内で任意に変換でき、プロンプトキャッシュヒット率を高めるためのコンテキスト整理などを行える。

**性能改善**: 脳と手の分離により、コンテナが不要なセッションはコンテナのプロビジョニングなしにオーケストレーション層がセッションログからペンディングイベントを取得した段階で推論を開始できるようになった。結果として p50 TTFT が約 60% 低下、p95 が 90% 超低下した。複数のステートレスなハーネスをスケールアウトし、必要に応じてコンテナ（手）と接続する構成となった。

**多数の脳と多数の手**: 各手は脳に対してツール（`execute(name, input) → string`）として提示されるため、コンテナ・任意のカスタムツール・任意の MCP サーバーを区別なく扱える。手は脳間で受け渡しも可能。記事の結論として、Managed Agents は Claude Code や特定タスク向けエージェントハーネスも含む「どんなハーネスにも対応できるメタハーネス」として設計されたとしている。

#### [Claude Code・Codex・Antigravity を1つのローカルチャットで協働させる方法（Excalibur Agent Hub）](https://qiita.com/nezle02/items/1bea25898503056b95c2)

複数の AI コーディングエージェント（Claude Code、Codex、Antigravity など）が同一リポジトリで重複作業をしないよう調整するためのローカルチャットサーバー「Excalibur Agent Hub」の導入方法を紹介した記事。

各エージェントは `hub say <チャンネル名> <メッセージ>` でメッセージを送り、`hub unread` で自分宛ての新着（オペレーター、@メンション、`--to` 指定）を確認する。`hub wait` は外部から起動できない Codex や Antigravity 向けに、メッセージが届くまでブロッキング待機するコマンドで（タイムアウト設定可能）、タイマーで `unread` を繰り返す代わりに利用枠を節約できる。`hub read <チャンネル名> -n 30` でタブの最近の履歴を確認できる。

セキュリティ上、インターネットへの直接公開は想定しておらず、リモート利用には Tailscale 等のトンネル経由を推奨している。リポジトリ: https://github.com/nezle02/excalibur-agent-hub

#### [Claude Code で "The response stopped arriving" が出たときの直し方と、文言の新旧対応](https://qiita.com/homhom44/items/117f241f8944fa45f983)
<sub>qiita ・ 2026-10-30</sub>

Claude Code で応答の途中にエラーが出た場合の対処法と、v2.1.227 での文言変更をまとめた記事。確認環境は Claude Code 2.1.314・macOS 26.6.2。

**文言の新旧対応**: v2.1.227 未満の「Connection closed mid-response」は「Connection lost mid-response」に、「Response stalled mid-stream」は「The response stopped arriving」にそれぞれ改名された。前者は接続が切れた（プロキシ・ゲートウェイによる打ち切りを含む）、後者は接続は開いたままデータが来なくなり無通信監視（streaming idle watchdog）が切断したことを意味する。2.1.314 の実行ファイルに対して `strings` コマンドで確認したところ、新しい2つの文言はそれぞれ2件ヒットし、古い2つは0件だった。このほかに同系のエラーとして「Server error mid-response」「Your computer went to sleep mid-response」「Part of the response never arrived」「The response stream was malformed」も公式に掲載されている。

**直し方（優先順）**:

1. `continue` と返信する。Claude Code は完成したブロックは残すが途中で切れた最後のブロックは捨てるため、最後の数文やツール呼び出しが欠けることがある。`-p`（非対話）モードでは `claude -p --continue "continue"` で再開する。v2.1.246 以降、`-p` でテキストのみの応答かつツール呼び出しがない場合は最大3回まで自動で続きを促し、この通知はその3回を使い切った後に表示される。

2. 長い出力を分けて書かせる。大きなファイルや長い計画を一度に生成させると静止時間が長くなり切れやすくなるという複数の報告がある。

3. タイムアウト値を延ばす。`CLAUDE_STREAM_IDLE_TIMEOUT_MS` と `CLAUDE_BYTE_STREAM_IDLE_TIMEOUT_MS` の両方を上げる（例: 600000）。片方だけでは効かないことがあるとの指摘がある。`~/.claude/settings.json` の `env` セクションに設定して Claude Code を再起動する。

4. 回線側を見直す。効いた事例として、ルータ再起動、別回線（テザリング・VPN）での試行、IPv6 無効化、MTU の引き下げ（macOS で PPPoE 回線の場合に `sudo networksetup -setMTU Wi-Fi 1492` が有効との報告）が挙げられている。

5. 古いバージョンなら更新する。v2.1.222 では応答完了後の接続切断でエラーとならないよう修正された。社内プロキシ経由の場合は応答を溜め込む機器が原因になりうる。
