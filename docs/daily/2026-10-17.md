#### [ClaudeによるNIST ECDSA楕円曲線暗号シードの起源解明](https://www.anthropic.com/research/ecdsa-curve-origins)
<sub>anthropic-blog ・ 2026-10-16</sub>
<sub>**原題**: ECDSA Curve Origins</sub>

AnthropicのFrontier Red Teamが報告書を公開した。2026年10月、Anthropicの社員が内部研究モデルに対してNIST ECDSA楕円曲線暗号のシードパラメータの起源を調査するよう依頼したところ、30分以内にP-192・P-224・P-256・P-384・P-521の5曲線とANSI X9.62の5曲線のシードの起源を特定した。

各シードはハッシュ関数の出力ではなく、C言語標準ライブラリの乱数生成器 `lrand48` をUnixタイムスタンプで初期化した出力だった。アルゴリズムはタイムスタンプ `t` で `srand48(t)` を呼び出し、1反復あたり20バイトを候補として生成し、n番目の候補を採用するものだった。P-256のシードは1842番目の候補で、初期化タイムスタンプは1997年8月16日01:52:34（UTC）に相当する。10個の素数曲線シードすべてのタイムスタンプは1997年5月から1998年4月の間に収まっていた。

発見の経緯として、Claudeはまず「1990年代のCライブラリのPRNGが使われた可能性がある」と推論した。シードを5つの32ビットワードとして記述すると、4つのシードで全ワードの最上位ビットがゼロになっていることに気づいた（偶然である確率は1/5810）。これは上位31ビットのみ返す `lrand48` の特徴であると判断し、隠れている17ビットを総当たりで試行することで4つのシードの内部状態を復元した。残りの素数曲線シードについてはLLL格子基底還元アルゴリズムを用いて切り詰められた線形合同生成器の内部状態を復元した。また、バイナリ曲線4件はタイムスタンプが2で割られたパターンを持ち、1998年4月17日に対応している。

本発見はNISTの曲線パラメータへの暗号学的な攻撃や弱点を示すものではない。シードが非常に単純な方法で生成されており誰でも再現可能であるため、意図的なバックドアが含まれている可能性が低くなると記事は述べる。

追加として、1997年5月に生成された6曲線（P-192とANSI X9.62の例示曲線5件）のベースポイントGの起源も特定した。Arjen LenstraのFreeLIPライブラリの乱数生成器に由来することが判明し、P-192の生成シードは20000、prime192v2は20512、prime192v3は20517だった。ただしP-224・P-256・P-384・P-521のベースポイントとバイナリ曲線のシードB-163については起源が未解明のままである。

発見に対して設けられていた36,864ドルの懸賞金はInternet Security Research Groupに寄付された。調査はJohn Wood・Henry de Valence・Ava Howell・Zack Voase・Lucy Sweet・Amir Omidi・Paul Crowley・Iain McGinniss・Nicholas Carlini・Steve WeisのAnthropicスタッフ10名が実施した。

#### [AIに関する期待値のギャップ：米国成人とAnthropicスタッフの比較調査](https://www.anthropic.com/research/ai-expectations-gap)
<sub>anthropic-blog ・ 2026-10-16</sub>
<sub>**原題**: AI Expectations Gap</sub>

Anthropicの経済研究チームによる調査報告書（著者：Szymon Sacher、Tess Cotter、Charles I. Jones、Anton Korinek、Peter McCrory）。2026年8月に米国成人（全国代表サンプル、10,980人）とAnthropicスタッフを対象に実施し、AIの能力・普及・自律性・生産性向上・雇用についての認識を比較した。

AIの能力に関して、米国成人とAnthropicスタッフは今日のAIにできることについてはほぼ一致しており、8タスクの難易度の順位付けもほぼ同じだった。一方、将来の進歩のペースについては大きな差がある。「2030年までにAIがノーベル賞級の発見を行えるか」という問いに対し、米国成人の39%が達成可能と回答したのに対し、Anthropicスタッフでは91%が達成可能と回答した。特定のタスクを「永遠にできない」と答えた割合は米国成人で19〜40%だったのに対し、Anthropicスタッフでは最大でも2%にとどまった。

#### [Anthropic Python SDKのタイムアウトを正しく効かせる3つのポイント](https://qiita.com/yureki_lab/items/9cc1fc402166675c5629)
<sub>qiita ・ 2026-10-15</sub>
<sub>**原題**: Anthropic Python SDK のタイムアウトを正しく効かせる実装手順 — max_tokens を上げると非ストリーミングが ValueError・timeout=2 でも51秒返らない・リトライ込みで待ち時間が3倍、3つのハマりどころ【2026】</sub>

Python 3.14・anthropic 1.15.0（内部HTTPクライアントはhttpx2 2.13.1）の環境でモックサーバーを用いて実測した知見をまとめた記事。AIエージェントを無人で長時間稼働させる用途での問題点が中心となっている。

**落とし穴1：max_tokensを増やすとAPIを叩く前にValueErrorが発生する。** SDKは `expected_time = 60 * 60 * max_tokens / 128000` を計算し、10分を超えると見込まれる場合（目安：max_tokens > 21,333）に `ValueError: Streaming is required...` を投げる。回避策は `messages.stream()` + `get_final_message()` への切り替えで、戻り値の型は `create()` と同じ `Message` 型になる。なお、`timeout` を明示的に渡すとこのチェックがスキップされるが、長時間のHTTP接続は途中のプロキシに切断されやすいためストリーミングへの切り替えが推奨されている。

**落とし穴2：`timeout=2` でも51秒かかる場合がある。** SDKに渡した数値はHTTPクライアントの各フェーズ（connect/read/write/pool）の待ち時間として使われる。`read=2.0` は「次のデータが2秒来なければ諦める」という意味で、0.12秒ごとに1バイトでも届いていれば全体が何分かかっても止まらない。回避策は `asyncio.wait_for` で全体の締め切りを外側に掛けること。非同期クライアントで `await asyncio.wait_for(client.messages.create(...), timeout=deadline_sec)` の形にすると、指定秒数で確実に `TimeoutError` が発生する。

**落とし穴3：タイムアウトしたリクエストが3回飛ぶ。** SDKはデフォルトで `max_retries=2`（最大3回リクエスト）を設定しており、タイムアウトも自動リトライの対象となる。`timeout=2.0` の場合、実際の待ち時間は `2 × 3 + バックオフ約1.6秒 ≈ 7.6秒` になる。デフォルトの10分タイムアウトのままだと1回の呼び出しで最悪30分以上固まる計算になる。また本物のAPIでは、クライアントが切断した後もサーバー側の生成が続いている場合があり、リトライのたびに同じプロンプトが送られるためトークン課金が複数回発生する可能性がある。回避策は用途ごとに `max_retries` を明示すること。`client.with_options(max_retries=0)` で特定の呼び出しのみリトライなしにできる。

推奨構成として、HTTPクライアントの `Timeout(read=..., connect=5)` を無応答の検知用に、`max_retries` を一時的な失敗の吸収用に、`asyncio.wait_for` を総時間の上限として、`messages.stream()` を大きな `max_tokens` の受け取り用としてそれぞれ役割を分けて設定することが示されている。なお `asyncio.wait_for` によるタイムアウトは `TimeoutError`、SDK側の無応答検知は `anthropic.APITimeoutError` と例外の型が異なる点も注意点として挙げられている。
