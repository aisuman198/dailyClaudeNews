Claude Code のパーミッション承認ファティーグへの対応として構築された「auto mode」の設計が公開された。Anthropic の内部データでは、ユーザーはパーミッションプロンプトの 93% を承認しており、数が増えるにつれて個々の確認への注意が低下していた。

既存の選択肢はサンドボックス（安全だが設定コストが高く、ネットワークやホストアクセスが必要な場合に機能しない）と `--dangerously-skip-permissions` フラグ（ゼロメンテナンスだが無保護）の二択だった。Auto mode はモデルベースの分類器による自動承認を中間手段として提供する。

技術的には二層構造。入力層ではサーバーサイドのプロンプトインジェクション検出プローブがツール出力（ファイル読み取り・ウェブフェッチ・シェル出力・外部ツールレスポンス）を監視し、インジェクション疑いがあればエージェントのコンテキストに警告を付加する。出力層ではトランスクリプト分類器（Sonnet 4.6 で動作）が各アクションを実行前に評価する。分類器は単一トークンフィルタで高速に事前スクリーニングを行い、フラグが立ったケースのみチェーン・オブ・ソートの推論を実行することでコストを抑えている。Anthropic の内部インシデントログには過去の事例として、誤解釈した指示によるリモート Git ブランチの削除、エンジニアの GitHub 認証トークンの内部コンピュートクラスターへのアップロード、本番データベースへのマイグレーション実行の試みが記録されている。

#### [With Claude: Less Coding, More Testing](https://henrikwarne.com/2026/05/31/with-claude-less-coding-more-testing/)
<sub>hacker-news ・ 21pt ・ 2026-05-31 ・ 継続話題（8回目）</sub>
<sub>**訳**: Claude を使って：コーディングは減り、テストが増えた</sub>

Claude Code を数か月間使い続けた開発者の体験記。自分でコードを書く量は大幅に減ったが、Claude が書いたコードの理解とテストに費やす時間が増えたとしている。それでも全体としてソフトウェア開発らしさは失われておらず、総じてプラスだと述べている。

ワークフローとして、チケットの説明が正確かどうかを Claude に確認し、解決策の提案を求めることから始める。自分に解決策のアイデアがあっても Claude にそれを押し付けず、よりよい方法がある可能性を残すようにしている。コードが書かれたら通読し、「この部分は何をするのか」「なぜここにあるのか」のような対話を Claude と繰り返す。テストについては、ユニットテスト・インテグレーションテストによる自動テストに加え、ログ出力の確認、システム全体での動作観察、探索的テストも重視している。午前 0 時にしか実行されない処理を 1 分後に実行するような一時的なローカルパッチを Claude に依頼するなど、テスト環境の準備にも活用している。自分の名前で出す変更である以上、内容を理解して保証できる状態でいたいという姿勢が一貫している。

#### [Guidelines for Respectful Use of AI](https://www.elidedbranches.com/)
<sub>hacker-news ・ 6pt ・ 2026-05-31 ・ 継続話題（1回目）</sub>
<sub>**訳**: AI の敬意ある利用のためのガイドライン</sub>

AI ツールを導入した組織でのチームワークの観点から、リーダーが定めるべきガイドラインを論じたブログ記事。セキュリティ・コンプライアンス・コストの視点ではなく、チーム全体の生産性と協働の文脈での指針を提供している。

AI で個人のアウトプット量を増やすことがチーム全体の生産性に悪影響を与えることがある、という問題意識を出発点としている。具体的なルールとして、まず「自分が読んでいないものを他人に読ませ・レビューさせない」が強調されている。AI が生成したコードをオーナーが理解せずにレビューに出す行為や、生成したドキュメントを自分で読まずに他者に送る行為は、品質管理の負担を相手に押し付けることになると指摘している。AI との対話中に自分の頭の中にあった文脈が生成されたドキュメントに反映されないことがあり、自分で通読しなければそのギャップに気づけないとも述べている。また AI の出力は冗長になりがちであるため、短い方が良いという原則も挙げられている。
