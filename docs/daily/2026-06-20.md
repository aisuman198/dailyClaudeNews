#### [Project Fetch フェーズ2：Claude Opus 4.7、ロボット操作で人間チームを大幅に上回る速度を記録](https://www.anthropic.com/research/project-fetch-phase-two)
<sub>anthropic-blog ・ 2026-06-18</sub>
<sub>**原題**: Project Fetch: Phase two</sub>

2025年8月に実施したオリジナルの「Project Fetch」では、Anthropic 社員をランダムに2チームに分け、Claude あり・なしでオフザシェルフの四足歩行ロボット（ロボドッグ）を用いたタスクをこなした。Claude を使えたチームはより多くのタスクをより速く完了した。一方、当時の最新モデル Opus 4.1 は単独では冒頭の「ロボットへの接続」でつまずき、自律完走はできなかった。

フェーズ2では Claude Opus 4.7 を使い、人間の支援なしに同タスクを実施した。研究者の役割は、Claude Code を動かすノートパソコンをロボドッグに接続し、初期プロンプトを入力し、コマンドと次のタスクへの移行を承認することに限定された。Opus 4.7 はアダプティブシンキングをエフォート最大で Claude Code 上で動作させた。

結果として、Opus 4.7 は人間参加者が完了した全タスクで最速の人間チームより少なくとも10倍速く完了した。両チームが完了した4つのタスクに絞ると、Opus 4.7 は平均で37倍以上速かった。ただし、ボールを正確に「フェッチ」する部分では Claude はまだ苦戦しており、ロボット制御の低レベルな要素（アクチュエーション・ポリシーの策定など）はこれらの実験の対象外であることが明記されている。著者らは「まずモデルが人間を助け、次に人間がモデルを助け、最終的にモデルが自律して動ける」というパターンが、サイバーセキュリティに続いて AI と物理世界の交差領域でも現れてきていると述べている。

#### [Claude Code v2.1.181〜v2.1.183：auto モードの破壊的コマンド自動ブロックと安全性強化](https://qiita.com/moha0918_/items/74e97e0f8be8174d312e)
<sub>qiita ・ 0pt ・ 2026-06-19</sub>
<sub>関連: https://qiita.com/picnic/items/f2a4da4cd2e99718d66f</sub>

v2.1.181 から v2.1.183 にかけての Claude Code の主要変更点をまとめる。

**破壊的コマンドの自動ブロック（v2.1.183）**
auto モードで明示的な指示なしに実行しようとした場合にブロックされるコマンドが定義された。Git 操作では `git reset --hard`・`git checkout -- .`・`git clean -fd`・`git stash drop`（ローカル変更の破棄を依頼していない場合）および `git commit --amend`（そのセッションでエージェント自身が作成したコミットでない場合）がブロック対象となる。IaC 操作では `terraform destroy`・`pulumi destroy`・`cdk destroy` が対象スタックを明示せずに実行しようとした場合にブロックされる。CI/CD パイプラインでこれらのコマンドを意図的に使用していた場合は、意図を明示するプロンプト設計への変更が必要となる。

**認証付き MCP サーバーの auth-stub ツール露出を修正（v2.1.183）**
headless/SDK モードで、認証が必要な MCP サーバーが auth-stub ツールをモデルに露出してしまうバグが修正された。このバグにより意図しないツール呼び出しが発生するリスクがあったため、headless モードや SDK 経由で認証付き MCP サーバーを利用している場合は v2.1.183 へのアップデートが推奨される。

**非推奨モデルへの警告表示（v2.1.183）**
指定したモデルが非推奨または新バージョンへ自動更新された場合、print モード（`-p`）の stderr へ警告が表示されるようになった。エージェントの frontmatter で指定されたモデルも対象となる。

**その他の変更点（v2.1.183）**
`attribution.sessionUrl` 設定が追加され、コミットや PR に含まれる claude.ai セッションリンクを省略できるようになった。サブエージェント内での WebSearch が空の結果を返す問題と、thinking.disabled を使用したサブエージェント生成時の 400 エラーが修正された。起動ログのロゴ下「setup issues」行が削除され、確認は `/doctor` コマンドで行う形に変更された。また `/config` のトグル操作で Esc が「破棄して戻る」から「保存して閉じる」に変わり、Enter/Space どちらでも設定を切り替え可能になった。

**主要な変更点（v2.1.181）**
`/config key=value` 構文が追加され、プロンプトから直接設定を変更できるようになった（例：`/config thinking=false`）。`CLAUDE_CLIENT_PRESENCE_FILE` の追加によりPCを使用中にモバイルへのプッシュ通知を抑制できる。prompt caching の修正として、カスタム `ANTHROPIC_BASE_URL` と Foundry でキャッシュが読まれていなかった問題が解消された（原因はリクエストごとに変わる attestation トークン）。そのほか Bun ランタイムを 1.4 に更新、ネットワークドライブでの Write/Edit による 0 バイト・切り詰めファイル生成の修正、macOS の `error -600` を Apple Events entitlement 追加で解消、v2.1.169 で混入していた起動時の約 120ms の regression が修正された。

#### [Claude Fable 5 / Mythos 5 エクスポート制限の衝撃 — セキュリティと AI 規制・企業対応ガイド](https://qiita.com/kai_kou/items/bdb9605b05a81c81e97f)
<sub>qiita ・ 0pt ・ 2026-06-19</sub>

2026年6月12日 17:21 EDT、米国商務省が Anthropic に対して Claude Fable 5 と Claude Mythos 5 へのアクセスを「全ての外国人」に対して停止するよう指令したとする記事。対象は米国外の人物だけでなく、米国内の非市民および Anthropic 社員も含むとされ、AWS Bedrock・Google Cloud Vertex AI・Microsoft Foundry・Snowflake Cortex AI・claude.ai / API キー経由を含む全プラットフォームで同時シャットダウンが実施されたと記述されている。制限対象外のモデルとして Claude Opus 4.8・Claude Sonnet 4.6・Claude Haiku 4.5 が挙げられており、各プラットフォームの代替案として Opus 4.8 や Gemini 3.5 が示されている。

制限の理由として、Fable 5 に発見されたジェイルブレイク脆弱性が挙げられている。「Fix this code.」という一見無害なプロンプトで Fable が脆弱性分析を実行し、その分析プロセス自体が Mythos 5 の能力と組み合わさることで攻撃者に悪用可能な経路になるとされる。Mythos 5 については、本番コードベースの脆弱性検出（0-day を含む）・エクスプロイトコード生成・セキュリティツール回避といった能力を持つ「セキュリティ監査エージェント」と紹介されており、米国政府がこれを「防衛的サイバー戦争ツール」として輸出規制対象に指定したと説明している。Anthropic はこの脆弱性が「全ての生成モデルに内在する」として修正不可能との立場を取るとされるが、政府とセキュリティ研究者はリスクが即座かつ深刻と判断したとされる。

#### [Claude Code Dynamic Workflows でコードベース全体をセキュリティ監査する](https://qiita.com/kai_kou/items/86a5cc9e0ab776447a87)
<sub>qiita ・ 0pt ・ 2026-06-19</sub>

Claude Code の Dynamic Workflows（2026年5月28日・v2.1.154 で導入）を使い、コードベース全体にわたるセキュリティ監査を自動化する手順を解説した記事。

Dynamic Workflows は Claude 自身がタスクをサブタスクへ分割・並列実行・検証・反復するモードで、1 セッションで数十〜数百の並列サブエージェントをオーケストレーションできる。認証チェック漏れ・入力バリデーション不足・危険なパターンといったセキュリティ監査に適している理由として、「リポジトリ全体に同じチェックを横断的に当てたい」「誤検知を独立した別エージェントで潰したい」という監査の性質が、並列・独立検証という構造と合致することが挙げられている。

プラン要件として、Max・Team・Enterprise プランではデフォルトで利用可能、Pro プランは `/config` から有効化する。Amazon Bedrock・Vertex AI・Microsoft Foundry でも利用できる。起動方法は2通りで、`/effort ultracode` でエフォートレベルを ultracode に設定して Claude に自動判断させるか、「このリポジトリ全体のセキュリティ監査ワークフローを作って実行して」のようにプロンプトで直接依頼する。なお、v2.1.160 でトリガーキーワードが `workflow` から `ultracode` にリネームされており、`workflow` という単語では起動しなくなっている。Dynamic Workflows の併用には Auto Mode が推奨されており、Bedrock・Vertex・Foundry での Auto Mode は環境変数 `CLAUDE_CODE_ENABLE_AUTO_MODE=1`プトインできる。

実践上の最重要事項として、最初はスコープを1ディレクトリ・1問いに絞ることが推奨されている。Dynamic Workflows は通常より大幅にトークンを消費するため、いきなり全体を対象にするとコストが大幅に増加する。最初のワークフロー起動前に「何を実行しようとしているか」の確認が求められ、ここでエージェント数やスコープを確認・修正できる。実行中・実行後のランでは、`/workflows` コマンドで各エージェントのトークン消費を確認しながら、スコープを徐々に広げていくことが鉄則とされている。
