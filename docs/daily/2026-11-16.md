#### [Opus 5.5 でのタスクコスト](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/)
<sub>hacker-news ・ 23pt ・ 2026-11-15</sub>
<sub>**原題**: What a task costs on Opus 5.5</sub>

Addy Osmani 著の claude.dev ブログ記事（Playbooks カテゴリ）。タスク単位でのコストの考え方と、Opus 5.5 における価格変更・設定変更の影響を詳細に解説している。

**Opus 5.5 の API リスト価格**は入力トークン $4/百万、出力トークン $20/百万、キャッシュ読み込み $0.20/百万。Opus 5 比で入力・出力が 20% 安く、キャッシュ読み込みは 60% 安くなった。キャッシュ読み込みの単価は入力価格の 1/20（Opus 5 の 1/10 から半減）。Claude Code のサブスクリプション利用では Opus 5.5 の低価格が利用制限にも反映され、Opus 5 比で約 25% 多くトークンを使える。なお 5 時間ごとの利用制限は Pro・Max・Team・Enterprise プランで引き上げられており、利用者は Settings > Usage から任意のタイミングで使用できるリセット枠を確認できる。

**タスクコストを決める 4 要素**として、ターン数・キャッシュヒット率・出力トークン量・モデル選択が挙げられている。各ターンはそれまでの会話全体を再送するため、ターン数が増えるほどコストが累積する構造になっている。同一タスクを 40 ターンで実行した場合と 25 ターンで実行した場合を比べると、入力コストはそれぞれ約 $1.62 対 $1.02 になるという試算が示されている（キャッシュヒット率 90% 想定）。

**キャッシュヒット率の影響**は最も大きく、同じ 2.8M 入力トークンでもキャッシュなしでは $11.20、ヒット率 90% で $1.62、96% で約 $0.99 となる。キャッシュはプレフィックスの一致部分を再利用する仕組みのため、セッションを途切れさせない運用が重要。effort 変更（Amazon Bedrock・Google Cloud Agent Platform・ゲートウェイ経由の場合）・MCP サーバーの着脱・モデル切り替えなどがキャッシュをリセットする主な原因として挙げられている。サブスクリプションではキャッシュ有効期間が 1 時間だが、API キーまたはクラウドプロバイダー経由では 5 分がデフォルトであり、6 分の中断で $0.02 のキャッシュ読み込みが $0.60 のキャッシュ書き込みに変わる例が示されている。

**effort レベルは low / medium / high / xHigh / max の 5 段階**で、`/effort` コマンドで変更できる。Opus 5.5 のデフォルトは medium（Opus 5 の high の 1 段下）。effort を上げても Opus 5.5 はキャッシュを維持できる（Amazon Bedrock・Google Cloud Agent Platform・ゲートウェイ経由の場合はキャッシュがクリアされる）。なお思考は常に有効であり、thinking 設定を変える項目はない。高 effort が 1 回のリトライを防ぐ場合に約 20K 思考トークン（$0.40 相当）が追加されるという試算も示されており、まず medium で確認してから high に上げる運用を推奨している。

**モデル使い分けの推奨**として、監視しながらの日常作業には Opus 5.5、長時間の無人実行や既存パターンのない難問・多数のサブエージェント調整には Fable 5.1（リスト価格 $10/$50/$0.25 per million）が推奨されている。サブエージェントへのモデル割り当ては定義内に `model: haiku` 等を記述するか、`CLAUDE_CODE_SUBAGENT_MODEL` 環境変数で一括設定できる。サブエージェントはそれぞれ独立したコンテキストウィンドウで動作するため、ファイル読み込みがメインの会話コンテキストに流れ込まない。

**プロンプト監査の効果**として、Opus 4.8 から Opus 5.5 へ移行した社内顧客サポートベンチマーク（44 チケット）で、低 effort 設定への変更で約 18% のコスト削減、`/claude-api prompt-audit` によるプロンプト最適化でさらに 9%、合計約 25% の削減が確認されたと報告されている。監査で除去されたパターンとして、強制的な 6 ステップ手順・スクラッチパッドルール・二重確認ルール・矛盾する指示が挙げられている。

#### [Claude Code で "PreToolUse:Bash hook error" / "Stop hook error" が出たときの見分け方（終了コードの意味と、成功しても error と表示される件）](https://qiita.com/homhom44/items/d1987dc6a459b10701ae)
<sub>qiita ・ 1pt ・ 2026-11-14 ・ 継続話題（2回目）</sub>

確認環境は Claude Code 2.1.325、macOS 26.6.2（2026-11-15 確認）。

今回の更新では、Stop フックが連続して同じ条件でブロックし続けた場合に「A hook blocked the turn from ending」というエラーが発生するケースの詳細が追記された。公式ドキュメントによると Claude Code は連続 8 回の継続でブロックを打ち切る仕組みがあり、上限は `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` で変更できる。Stop フックが `stop_hook_active` フィールドを確認して `true` の間は成功（exit 0）を返す設計になっているかの確認が推奨されている。

また、Stop フックでターンをブロックするのではなく Claude に助言を渡すだけの用途では、`decision: "block"` ではなく `additionalContext` を含む `hookSpecificOutput` を返す書き方があり、この場合はトランスクリプト上で `hook error` ではなく `Stop hook feedback` と表示されることが追記されている。

デバッグログ（`claude --debug-file ./claude-debug.log --debug`）では v2.1.296 以降、フックごとに終了コードと処理時間を含む 1 行ログが記録されるため、実際の終了コードの確認が可能。

なお、終了コード 0 で正常終了しているにもかかわらず `hook error` と表示される問題は GitHub Issues #17088（現在も未解決の状態）として報告が続いており、コメント欄には同じ現象への賛同コメントが集まっている。issue #34713 では「単なる表示ではなく、ラベルの誤りのせいで Claude が失敗が続いていると判断してターンを途中で切り上げる」という実害の報告もあったが、stale を理由に 2026年5月にクローズされている（修正されたという意味ではない）。

#### [Claude Code で "API Error: 500 Internal server error" が出たときの切り分け（status 確認と再送、ゲートウェイ経由なら ENABLE_TOOL_SEARCH）](https://qiita.com/homhom44/items/af9b7802e0af1ad1ccd4)
<sub>qiita ・ 0pt ・ 2026-11-15</sub>

確認環境は Claude Code 2.1.325、macOS 26.6（2026-11-16 確認）。

公式の Error reference によると、500 エラーは API 内部の予期せぬ失敗であり、プロンプト・設定・アカウントが原因ではない。対処は 2 つ：まず `https://status.claude.com` でインシデントを確認し、1 分待ってから `try again` と打って再送する（元のメッセージがそのまま再送される）。

ゲートウェイ経由（`ANTHROPIC_BASE_URL` を LLM ゲートウェイに設定）で全リクエストが 500 になる場合は、ゲートウェイがツール検索フィールドを拒否している可能性があり、`ENABLE_TOOL_SEARCH=false` を付けて起動すると解消することがある。Claude Code v2.1.304 以降はツール検索がデフォルトで有効になっているため、古いゲートウェイとの組み合わせでこの症状が出やすいとされている。Amazon Bedrock・Google Cloud・Microsoft Foundry 経由の場合は、エラーメッセージ末尾の status 確認先 URL がその提供元のものになる。

著者が実行ファイルを grep して確認したところ、ステータスコード 500 以上を受け取ったときにメッセージを固定テキスト付きで組み立てる処理と `ENABLE_TOOL_SEARCH` の参照箇所がそれぞれ確認された。GitHub Issues には「Internal Server Error」をタイトルに含む issue が約 350 件、500 全体では約 450 件存在し、障害発生時に一斉に報告が上がり復旧で一斉にクローズされる性質のエラーと説明されている。

障害が出ていないのに 500 が続く場合は `/feedback` で報告する。その際、エラーメッセージ内の `request_id`（`req_...`）を添えると調査が容易になる。

#### [Claude 障害まとめ：11/13 の同時障害・認証エラー・利用上限誤判定と対処法](https://qiita.com/picnic/items/0e7c5295c004f170dcd9)
<sub>qiita ・ 0pt ・ 2026-11-15</sub>

2026年10月7日〜11月14日の Anthropic ステータスページに掲載された 20 件の障害を整理した記事。未解決は iOS アプリの「Apple でサインイン」障害の 1 件のみで、残りは解決済み。

**11/13 複数サービス同時障害**（調査開始：11/13 13:09 UTC、解決：15:38 UTC）。影響対象は claude.ai（モバイル含む）・Claude API・Claude Code・コネクタ（Docs/Sheets 含む）・Claude Security・Claude Managed Agents・Claude in Meetings。復旧後も残存影響として、新しいコネクタの追加が一時的に不可、スケジュールタスク・ルーティンが 2 時間以上遅延し一部スキップされた、Claude Security のスキャン・レビュー・プロジェクト設定に遅延が残った点が記録されている。エラー率が正常に戻った後も裏で動くジョブへの影響が継続したため、定期実行の実行履歴確認と必要な手動再実行が推奨されている。日本時間に換算すると 11/13 22:09〜11/14 00:38 の時間帯。

**11/13 認証障害**（別件）（調査開始：09:58 UTC、解決：11:58 UTC、約 2 時間）。claude.ai・Claude Code・platform.claude.com・Claude Cowork に影響。認証時にエラーが発生した。同日に 2 件の別々の障害が発生しており混同しやすいと指摘されている。

**10/7 利用上限（spend limit）誤判定**：一部の組織が上限未達にもかかわらず spend limit 到達と誤判定され一時停止となり、Claude API・claude.ai・Claude Code・Claude Security・Claude Cowork へのリクエストが拒否された。解決は 10/7 21:23 UTC、影響時間帯は非公表。

**iOS アプリの「Apple でサインイン」障害**（未解決）：11/14 07:11 UTC 調査開始、主に新規アカウントに影響。回避策は Google またはメールアドレスでのサインアップ。

その他、Microsoft 365 コネクタの約 24 時間停止（11/12〜11/13）は Microsoft 側が原因と説明されている。モデル別の短時間エラーが Sonnet 5.5・Fable 5.1・Fable 5.2・Opus 5.5・Mythos 5.1・Haiku 5.5 等で繰り返し発生しており（数分〜30 分程度）、呼び出し側の再試行とフォールバック実装が推奨されている。なお 10/25 には 5 モデルが同時に影響を受けた例もあり、フォールバックが万能ではないケースとして言及されている。
