#### [Managed Agents — 安定したインターフェースで長時間エージェントをスケールさせる](https://www.anthropic.com/research/managed-agents)
<sub>anthropic-blog ・ 2026-10-29</sub>
<sub>**原題**: Scaling Managed Agents with stable interfaces</sub>

Anthropic エンジニアリングブログが、Claude Platform 上で長時間稼働エージェントをホストする新サービス「Managed Agents」の設計を詳述した。ドキュメントに従って利用開始できる。

**背景と動機**

エージェントハーネスは「Claude にはまだできないこと」を前提として組み込んでいるが、モデルが改善されるとその前提は時代遅れになる。例として、Claude Sonnet 4.5 ではコンテキスト上限に近づくとタスクを早期に終了する「コンテキスト不安」の挙動があり、ハーネスにコンテキストリセットを追加して対処した。しかし同じハーネスを Claude Opus 4.5 で動かすとその挙動は消えており、リセット処理が「死荷重」になっていた。Managed Agents はこうした変化に耐える安定したインターフェースを提供することを目指した。

**設計哲学（OS のアナロジー）**

OS がハードウェアを「プロセス」「ファイル」という抽象に仮想化したように、Managed Agents はエージェントの構成要素を抽象化する。セッション（append-only のイベントログ）・ハーネス（Claude を呼び出し、ツールコールをルーティングするループ）・サンドボックス（Claude がコードを実行しファイルを編集する環境）の 3 つがその抽象であり、それぞれが独立して入れ替え可能になっている。

**旧アーキテクチャの問題（「ペット」コンテナ）**

初期実装はセッション・ハーネス・サンドボックスを 1 つのコンテナにまとめていた。コンテナが落ちるとセッションも失われ、応答しなくなれば手動で復旧する必要があった。デバッグ手段は WebSocket イベントストリームのみで、ハーネスのバグ・パケットロス・コンテナオフラインを区別できなかった。コンテナ内にユーザーデータも存在したため、シェルを開いてデバッグすることも事実上できなかった。顧客 VPC との接続にはネットワークピアリングが必要で、ハーネスに焼き込まれた前提が制約になっていた。

**解決策: 「脳」「手」「セッション」の分離**

ハーネス（脳）をコンテナの外へ移し、サンドボックスを `execute(name, input) → string` インターフェース経由のツールとして呼び出す設計に変更した。コンテナが落ちてもハーネスがツールコールエラーとして受け取り、`provision({resources})` で新しいコンテナを用意できる。

ハーネス自体もステートレスになった。セッションログは外部に保存するため、ハーネスがクラッシュしても `wake(sessionId)` で新しいハーネスを起動し、`getSession(id)` でイベントログを取得して再開できる。実行中は `emitEvent(id, event)` でイベントを書き込み耐障害性を確保する。

セキュリティ上の境界も強化された。旧設計では Claude が生成したコードと認証情報が同じコンテナに存在し、プロンプトインジェクション攻撃で認証情報を読み取られるリスクがあった。新設計では 2 つのパターンで対処している。Git の場合はサンドボックス初期化時にアクセストークンでリポジトリをクローンしてローカルの git リモートに組み込む（エージェントはトークンを直接扱わない）。カスタムツールの場合は OAuth トークンをセキュアなボールトに保存し、MCP ツール呼び出しを専用プロキシ経由で行う。ハーネスは認証情報を把握しない。

**セッションとコンテキストウィンドウの分離**

長時間タスクはコンテキストウィンドウを超えることが多く、コンパクション・メモリツール・コンテキストトリミングなどの既存手法はいずれも不可逆な判断を伴う。Managed Agents ではセッションをコンテキストウィンドウ外に存在するコンテキストオブジェクトとして扱う。`getEvents()` インターフェースを使ってイベントストリームを位置ベースでスライスでき（最後の停止点から続きを読む、特定の時点の前後を振り返るなど）、取得したイベントはハーネス側で自由に変換してからコンテキストウィンドウに渡せる。コンテキスト管理の具体的な実装はハーネスに委ねられており、セッションの耐久性・アクセス性のみを保証する設計になっている。

**パフォーマンスと水平スケール**

脳とコンテナを分離したことで、コンテナが必要なセッションだけがツールコール経由でコンテナを用意する設計になった。コンテナを必要としないセッションはオーケストレーションレイヤーがセッションログからイベントを取得し次第すぐ推論を開始できる。この結果、p50 TTFT が約 60%、p95 TTFT が 90% 超低下した。ハーネスがステートレスになったことで多数のハーネスを水平スケールできる。各サンドボックスは `execute(name, input) → string` インターフェースで統一されており、ハーネスはコンテナ・電話・Pokémon エミュレーターを区別しない。脳間でサンドボックスを受け渡すことも可能。

著者: Lance Martin、Gabe Cemaj、Michael Cohen。

**第 1 章: セットアップのカスタマイズ**

CLAUDE.md ファイルは Claude がセッション開始時に自動的にコンテキストへ取り込む特殊ファイルで、bash コマンド・コアファイル・コードスタイルガイドライン・テスト手順・リポジトリ規約・開発環境設定・注意すべき挙動などを記述する場所として機能する。配置場所はリポジトリルート（git へコミット可能な CLAUDE.md、またはローカル専用の CLAUDE.local.md）、親ディレクトリ、子ディレクトリ、ホームフォルダ（`~/.claude/CLAUDE.md`）の 4 種類があり、`/init` コマンドで自動生成も可能。CLAUDE.md はプロンプトの一部として扱うため、「IMPORTANT」「YOU MUST」といった強調表現を加えて従わせやすさを高めることが Anthropic 内部でも行われている。`#` キーで指示を与えると関連する CLAUDE.md へ自動追記される。

許可ツールの管理は 4 種類の方法で行える。プロンプト表示時に「Always allow」を選択する方法、`/permissions` コマンドを使う方法（例: Edit でファイル編集を常時許可、`Bash(git commit:*)` で git コミットを許可）、`.claude/settings.json` または `~/.claude.json` を手動編集する方法、`--allowedTools` CLI フラグを使う方法。

**第 2 章: Claude にツールを追加する**

Claude Code は bash 環境を継承するため、カスタムスクリプトもそのまま利用できる。MCP については、Claude Code は MCP サーバーとクライアントの両方として機能し、プロジェクト設定・グローバル設定・リポジトリにコミットした `.mcp.json` の 3 経路で接続できる（例: Puppeteer・Sentry サーバーを `.mcp.json` に追加してチーム全員がすぐに使える状態にする）。カスタムスラッシュコマンドは `.claude/commands/` フォルダに Markdown ファイルとして保存し、`$ARGUMENTS` キーワードでパラメーターを受け取れる（例: `fix-github-issue.md` を作成すると `/project:fix-github-issue 1234` でイシューを自動修正）。個人用コマンドは `~/.claude/commands/` に保存すると全セッションで使用できる。

**第 3 章: 代表的なワークフロー**

「探索 → 計画 → コーディング → コミット」ワークフローでは、まずコードを読ませ（コーディングは禁止）、次に計画を立てさせる。計画段階では `think`・`think hard`・`think harder`・`ultrathink` の順でモデルに割り当てられる思考バジェットが段階的に増加する。TDD ワークフローでは、テストを書かせてコミット → 実装を書かせてテストを通過させるまで繰り返すサイクルを推奨しており、独立した subagent で実装がテストに過剰適合していないか検証させることも有効とされている。その他のワークフローとして、ビジュアルモック + スクリーンショット繰り返し、`--dangerously-skip-permissions`（コンテナ内でインターネットなしで使用を推奨）によるノーチェックモード、コードベース Q&A によるオンボーディング、git の複雑な操作（リベース・リバート・パッチ比較）の自動化、GitHub 操作（PR 作成・コードレビューコメントの一括修正・ビルド失敗の修正・イシューのトリアージ）、Jupyter ノートブック編集（VS Code で隣に並べて使用、「美観を高めて」と伝えると可視化も改善される）を取り上げている。

#### [Claude Code のエージェントサマリーがトークン消費の 15〜20% を占めていた問題と無効化 Bun プリロード](https://gist.github.com/flamerix-ai/c3905705cc4205e5de3011fa2e74efce)
<sub>hacker-news ・ 557pt ・ 2026-10-29</sub>
<sub>**原題**: Claude Code regularly sends each background agent's transcript to its model</sub>

Flamerix AI が、Claude Code のバックグラウンドエージェントサマリー機能を無効化する Bun プリロード `no-agent-summary.js` を MIT ライセンスで公開した。

**問題の内容**

Claude Code は約 30 秒ごとに、各バックグラウンドエージェントのトランスクリプト全体をそのエージェントのモデル（通常 Opus）に送り、「直近の行動を 3〜5 語で説明せよ」という指示を出している。この応答はエージェントパネルのステータス行の更新にのみ使われ、メインの会話には届かない。バージョン 2.1.232（2026 年 8 月 13 日）以降はデフォルトで有効化されており、無効化する設定は存在しない。

Flamerix AI が DRIM の OpenTelemetry エクスポートで計測したデータ（フック適用前の週）は以下の通り:

- 全 Claude Code 消費コストに占める割合: 16.4%（メイン会話は 15.7%）
- 全 API リクエストに占める割合: 19.7%（約 5 リクエストに 1 件）
- そのうち Opus に集中する割合: 96%
- 入力トークン対出力トークン比: 約 9,000:1

4 件の独立した計測で 18〜26% という数値も報告されている（GitHub Issues #86879 に集約）。

**タイムライン**

| バージョン（公開日） | 変更内容 |
|---|---|
| 2.1.32（2026-02-05） | コードが初出、パブリックビルドでは無効 |
| 2.1.72（2026-03-09） | SDK のオプトインとして有効化 |
| 2.1.117（2026-04-21） | インタラクティブ CLI でも利用可能に |
| ≤2.1.220（2026-07-24） | フォークスキルは常に集約される |
| **2.1.232（2026-08-13）** | **インタラクティブなバックグラウンドエージェントでデフォルト有効化** |
| 2.1.300（2026-10-14） | タイマー間隔がサーバー側で調整可能に（30〜240 秒） |
| 2.1.310（2026-10-23） | 廉価な「short mode」（約 2,000 トークンのメモ）が実装されたがデフォルトはオフ |

**設定で無効化できない理由**

SDK オプション `agentProgressSummaries` のデフォルトは `false` だが、バンドル内では OR の 1 項に過ぎず、値を書き込むコードパスはすべて `true` にセットするため、`false` は何も変えない。`CLAUDE_CODE_AGENT_PROGRESS_SUMMARIES` 環境変数は有効化のみに対応。タイマー間隔はサーバー側フラグに由来し（30〜240 秒、デフォルトはすでに最小値）、`DISABLE_NON_ESSENTIAL_MODEL_CALLS` はバイナリに存在しない。`CLAUDE_CODE_FORK_SUBAGENT=0` や `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` は停止できるが、フォークサブエージェントやバックグラウンドエージェントごと無効化してしまう。プロンプトキャッシュで約 98% の呼び出しはキャッシュから再読するが、コールドキャッシュ時は全コストの 3 分の 1 以上を占める。これらのリクエストはディスク上のセッションログには記録されず（Issues #104358）、OpenTelemetry エクスポートのみで確認できる。

**修正方法**

`no-agent-summary.js` は Bun の `--preload` フック（約 70 行）。グローバルの `setTimeout` をラップし、コールバックのソーステキストにサマライザーのアンカー文字列（例: `[AgentSummary] Timer fired`）が含まれる場合のみ不活性なハンドルを返す。それ以外のタイマーはすべて素通り。インストールは以下の手順:

```sh
export BUN_OPTIONS="${BUN_OPTIONS:+$BUN_OPTIONS} --preload=/abs/path/no-agent-summary.js"
claude daemon stop --any
```

フックは Claude Code プロセス内（`Bun.main` が Claude Code のコンパイル済みエントリ、かつ `process.execPath` が Claude Code のインストールパス）でのみ有効になる設計で、他の `bun` プロセスには何も行わない。`CC_AGENT_SUMMARY_MODE=pass` で A/B テストが可能。`CC_AGENT_SUMMARY_LOG` にファイルパスを指定するとプリロードのログを記録できる。動作確認は `--version` 実行時のログと、OpenTelemetry の `query_source = agent_summary` イベントがゼロになっていることで行う。Claude Code を更新するとフックが無効化される可能性があるため、更新のたびに確認が必要。

Linux（Claude Code 2.1.257〜2.1.312）でテスト済み。macOS（darwin-arm64、2.1.312）での動作も別ユーザーから報告あり。

#### [Claude Duet — 初めて実用的と感じたパーソナルアシスタント型ハーネス](https://fig.blue/posts/duet-is-the-future/)
<sub>hacker-news ・ 79pt ・ 2026-10-29</sub>
<sub>**原題**: Claude Duet is the first personal-assistant-type harness that feels useful</sub>

個人ブログ fig.blue が Claude Duet のレビューを公開した。著者は過去に Muse、Dot、NanoClaw ほか複数のパーソナルアシスタント型ハーネスを試した経験を持ち、Claude Duet が「面倒より実用的」と感じた初めての製品だと述べている。

**評価ポイント**

*速さ*: バックグラウンド処理が必要な場面でも、まずユーザーへの応答を優先する設計を感じると述べている。Claude Duet は Opus 5.5 で動いているとされるが、他の Claude UI では経験したことのない速さで動作するとしている。

*チャンネル機能*: Slack に近い「チャンネル」の概念を採用。Claude Duet はユーザーの代わりにチャンネルを作成・整理する。Cmd+K でチャンネル一覧を表示してすばやく切り替えられる。チャンネル同士が参照し合える設計で、作業を適切な文脈に保つ役割を果たす。

*アクセスポリシー*: GitHub リポジトリのアクセスをチャンネルごとに制限できる。認証情報を要求しない方針で、Claude が既に持つコネクターエコシステムを優先して使う。最大で Chrome セッション経由のログインを代行する程度にとどまる。

*短い応答*: 長文での返答を避け、絵文字リアクション（👍 など）で簡潔に応答する場面がある。Muse はほぼ何にでも 👍 を付けるのに対し、Duet は追加説明なしの OK の意思表示として使い分けているとしている。

**階層構造**

著者が評価する設計の核心は、アクセスと文脈の階層構造にある。最上位は全作業ストリームの俯瞰ビューを持ち、ローレベルなアクセスは持たない。チャンネルはより多くのアクセスを持つが文脈は制限される。チャンネルが起動するサブスレッドはさらに制限された文脈でコードサンドボックス内で動作する。Desktop アプリは許可された場合のみローカルホストへアクセスできる（通常は QA やデプロイ工程のみ）。

**懸念点**

ベータ版のため不具合がある。スレッドが実行中でも表示されないケースや、リポジトリアクセスが正しくアタッチされないケース（エージェント起動とアクセス付与の間の競合状態の可能性）が確認されている。音声インタラクションは Dot が依然として優れており、Duet は「音声テキスト変換の延長」にとどまるとしている。

#### [Claude Code で「API Error: Stream idle timeout - partial response received」が出たときの直し方（CLAUDE_STREAM_IDLE_TIMEOUT_MS と長い出力の分割）](https://qiita.com/homhom44/items/34211c5b1960ace4aa0c)
<sub>qiita ・ 0pt ・ 2026-10-29</sub>

Qiita のトラブルシューティング記事。Claude Code が長い推論中や大きなファイルを書いている最中に発生する `API Error: Stream idle timeout - partial response received` エラーの原因と対処法をまとめている。確認環境は Claude Code 2.1.312、macOS 26.6。

**エラーの種類**

- `API Error: Stream idle timeout - partial response received`: 何らかのデータが届いたあとにストリームが停止した場合
- `API Error: Stream idle timeout - no chunks received`: まったくデータが届かないまま停止した場合

**原因**

Claude Code は 4 種類のストリーム監視タイマーを持つ（公式 Network configuration ドキュメントに記載）: First-byte deadline、Event-level watchdog、Byte-level watchdog、Body idle timeout。ストリームが静かになると、ぶら下がり続けた接続を切断して再試行またはエラーにする仕組み。

- Event-level watchdog のデフォルト: 300 秒
- Byte-level watchdog のデフォルト: 直接 Anthropic API の場合 180 秒、ゲートウェイ経由は 300 秒

バージョン 2.1.104 以前は watchdog が切断した際に非ストリーミングへ自動切替が行われていたが、部分データ受信時の切替が廃止されて以降、誤検出がそのままエラーとして表示されるようになった。

Claude Code 2.1.312 のバイナリに `CLAUDE_BYTE_STREAM_IDLE_TIMEOUT_MS`、`CLAUDE_ENABLE_BYTE_WATCHDOG`、`CLAUDE_ENABLE_STREAM_WATCHDOG` の 3 つの環境変数が存在することをバイナリ文字列解析で確認している。

**対処法**

1. **タイムアウト時間を延ばす**: `~/.claude/settings.json` の `env` に `"CLAUDE_STREAM_IDLE_TIMEOUT_MS": "600000"` を追記して Claude Code を再起動。GitHub Issues #46987 では 600,000（10 分）で解消したという報告が複数ある。公式ドキュメントによると 5 分未満の値は 5 分に引き上げられ、byte-level の上限は 30 分。

2. **`CLAUDE_ENABLE_STREAM_WATCHDOG=1` を削除**: settings.json に手動で追加していた場合、これが原因であるという報告がある。公式では watchdog を強制的にオンにする変数とされている。

3. **byte-level のみ個別調整**: `CLAUDE_BYTE_STREAM_IDLE_TIMEOUT_MS` は byte-level watchdog のみを制御し（10 秒〜30 分）、`CLAUDE_STREAM_IDLE_TIMEOUT_MS` より優先される。

4. **長い出力を分割する**: 大きなファイルや計画書を一度に書かせると静止時間が長くなる。「まず章立てだけ」「次に 1〜3 章」のように分割すると発生しにくくなったという複数のユーザー報告がある（非公式の回避策）。

エラー後に `continue` と送ると続きを書かせられるが、自動では再開しない。社内プロキシ・ゲートウェイ越しの場合、機器がストリームをバッファリングしている可能性がある。ルーターの再起動・IPv6 無効化・MTU 縮小で改善した例も Issues に報告されている。このイシューは現在も未解決の状態。
