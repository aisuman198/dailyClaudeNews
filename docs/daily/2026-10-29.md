#### [社会科学におけるコーディングエージェントの利用実態調査](https://www.anthropic.com/research/coding-agents-social-sciences)
<sub>anthropic-blog ・ 2026-10-28</sub>
<sub>**原題**: Coding Agents Social Sciences</sub>

Anthropic の経済研究チームが、1,260 人の定量的社会科学者を対象に 2026 年 2〜3 月に実施した調査結果を公開した。本調査は Claude Max アカウントへのアクセスを提供する研究の参加者募集を経て収集されており、AI ツールに関心のある研究者が多く選抜されている点に留意が必要と論文内で述べられている。

回答者の 81% が研究プロセスへの AI チャットボット利用経験を持つが、Claude Code・Codex・Cursor 等のコーディングエージェントを週 1 回以上定期利用しているのは 20% にとどまる。Claude Code がエージェント利用者の 86% に使われており、次いで Codex（31%）が多い。調査はクラウドプロバイダの Opus 4.6 をめぐる議論（2025 年 12 月末）から約 2 か月後に実施されたものだが、関心層が集まった回答者の中でも 5 人に 1 人しかエージェントを採用していなかった。

分野別では経済学者（39%）と政治学者（25%）の利用率が最も高く、公衆衛生（6%）・教育（4%）・コミュニケーション（6%）は一桁台にとどまる。職位別では博士課程・ポスドクが約 25% で最多、テニュア取得教員はその半数以下。名前の性別分類では、男性名の研究者が女性名の研究者の 2 倍超の利用率を示す。Top 25 大学（Nature Index 基準）の研究者は他校の研究者より 40% 利用率が高い。これらの差異はすべて p<0.05 水準で有意であり、LLM 全般の利用格差よりもコーディングエージェントの利用格差のほうが大きいとされる。

研究者が AI を使う目的として最多は定量データ解析のためのコード生成（エージェント利用者の 97%、その他の AI 利用者の 77%）であり、次いで文章の編集、手法のアドバイス求め、背景調査の順。文章の下書き作成に AI を使ったことがあるのは全 AI 利用者の 3 分の 1 にとどまる。

コーディングエージェント利用者は同分野・同職位の他の研究者と比べ、ワーキングペーパーの投稿数が約 75% 多く、グラント申請も多いという自己申告データが示された。一方、学術誌への投稿件数には有意差が見られなかった。ただしこれはエージェントを選んで利用している研究者とそうでない研究者の記述的な比較であり、因果関係の解釈はできないと論文内で明記されている。また、このパターンはエージェントがプロジェクトの立ち上げには有効だが、投稿直前の最終仕上げには貢献しにくいことを反映している可能性もある。

AI の研究生産性効果については回答者の 88% が 10 点満点で 5 点超、半数が 8 点以上と肯定的だが、70% の回答者は社会科学全体への影響についてはパブリッシャブルな論文への寄与よりも悲観的であり、査読過負荷や選択的な報告・リスク回避型の研究増加への懸念が示されている。Google Antigravity も調査で確認の対象として挙げられていた。本調査は大規模な無作為化実験（現在進行中）のベースライン調査として位置づけられており、今後の追跡報告でエージェントアクセスを提供した実験群との比較が公開される予定。

#### [Claude による創薬加速の初期成果](https://www.anthropic.com/research/early-progress-drug-development)
<sub>anthropic-blog ・ 2026-10-28 ・ 継続話題（2回目）</sub>
<sub>**原題**: Early Progress Drug Development</sub>
<sub>関連: https://www.anthropic.com/research/early-progress-drug-development</sub>

Anthropic の生命科学チームが、6 社との創薬協業で得た初期成果と今後の方針を公開した。各社の詳細なテクニカルレポートも合わせて公開されている。

**Generate Biomedicines（がん治療向け CAR T 細胞療法）**：血液がんに有効な CAR T 細胞療法を固形腫瘍にも応用するため、遺伝子指示の一部を短縮する設計を Claude Code で進めた。6 人の研究者が取り組んだ結果、標準版より約 70% 短い設計が得られた。この設計では免疫細胞が産生する受容体タンパク質が約 10 倍増加し、腫瘍細胞の殺傷効率が向上し、免疫細胞の活性維持時間も延長した。

**Divergence Labs（食物アレルギー治療）**：IgE 抗体を免疫細胞から完全に切り離す薬剤の開発に取り組み、Claude がほぼ自律的に約 35,000 件の抗体設計を約 1 か月で生成した。初期試験で、IgE に結合する候補 3 件と IgE を免疫細胞から引き離す候補 20 件が得られ、そのうち 3 件は標準薬よりも高い効果を示した。次の段階では両機能を持つ 2 アームの薬剤構築を進める。

#### [Claude Code v2.1.312 Bedrock/Vertex 系の短いシステムプロンプト化と変更点まとめ](https://qiita.com/picnic/items/7183ad4e831bf8243897)

v2.1.312 で影響が大きい変更は 3 点。

第一に、Amazon Bedrock・Google Vertex AI・Microsoft Foundry・Mantle 経由でカスタムデプロイ名や推論プロファイル ARN を指定している場合、Claude Code がモデル名を認識できなければ**短いシステムプロンプト**が使われるようになった（破壊的変更）。中身が Claude Sonnet や Claude Haiku であっても対象となる。フルのシステムプロンプトを維持したい場合は `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=0` を設定する。

第三に、OpenTelemetry の `claude_code.safety_event` の送信が停止した。このイベントに依存するダッシュボードやアラートの見直しが必要になる。また、Anthropic 公式マーケットプレイスのプラグインが宣言する固定 URL のリモート MCP サーバーで、`mcp_server.name` が `custom` から実際のサーバー名へ変わった。effort 値についても、タスク途中で変更した際に実際に効いているレベルが表示されるようになった（従来は変更前のレベルが表示されていた）。

prompt / agent フックには同時実行上限が追加された（1 セッションあたり最大 24 個、timeout 超過分は別枠で 12 個。1 秒未満の timeout は 1 秒として扱われる）。サブエージェントの `autoCompactWindow` は、`CLAUDE_CODE_AUTO_COMPACT_WINDOW` で設定したウィンドウがコンテキストを小さくする方向にのみ有効となった（大きくする方向には効かない）。

バグ修正としては、サブディレクトリの非常に大きな CLAUDE.md・ルールファイルを冒頭だけ読んだ状態で Write が上書きしてしまう問題、`claude -p` で不正なコマンド名 1 件があると全コマンドが読み込まれない問題、Bash で git リポジトリの深い階層へ `cd` するとパス指定スキルが検出されなくなる問題などが修正された。VS Code・Slack（Claude Tag）・Code Review・Cloud sessions でも複数の修正が入っている。

#### [Codex は既定で OPENAI_API_KEY などの環境変数を実行コマンドにそのまま渡す：shell_environment_policy で外す設定（codex 0.165.0 で確認）](https://qiita.com/supportapp3/items/56cf6468be08e14c76dd)
<sub>qiita ・ 2026-10-28</sub>

Codex がコマンドを実行する際にどの環境変数を渡すかは `config.toml` の `[shell_environment_policy]` セクションで制御される。公式ドキュメントによると `ignore_default_excludes` の既定値は `true` であり、変数名に `KEY`・`SECRET`・`TOKEN` を含む変数も自動では除外されない。codex-cli 0.165.0 の `codex sandbox` を使った Linux 環境での検証でも、設定なしでは `OPENAI_API_KEY`・`GITHUB_TOKEN`・`STRIPE_SECRET`・`AWS_ACCESS_KEY_ID` などがそのままコマンドに渡ることが確認された。

`ignore_default_excludes = false` を設定するとこれらは除外されるが、`DB_PASSWORD` や `DATABASE_URL`（URL 内にパスワードが含まれる場合も含む）は変数名がパターンに合致しないため残る。これらは `[shell_environment_policy.filters]` セクションで `"*PASSWORD*" = "exclude"` のように個別指定する必要がある。より強く絞るには `inherit = "core"` を設定すると `HOME`・`LANG`・`PATH` 等の最小限のみが引き継がれる。`inherit = "none"` では `PATH` も引き継がれず、`set` で必要な変数を足す形になる。`set` は除外処理の後に実行されるため、一度除外した変数を `set` で復元することもできる。

設定を確認するには `codex sandbox -- env` でサンドボックス内に渡る変数の一覧を確認することを推奨している。なお本記事の検証は Linux 環境の `codex sandbox`（ログイン不要）のみで行ったものであり、ログインしたエージェント本体が実行するコマンドでの動作は未検証。

#### [Codex の実行ログを効率的に分析するツールを作った](https://qiita.com/Yusg_6/items/35c21534ec128884360c)

Codex の実行履歴を記録した Rollout JSONL はあるセッションで約 400 万トークンに達する場合があり、全文を LLM に渡すのはコスト・コンテキスト長の両面で非効率だとして、必要な情報だけを抽出して分析する Python スクリプトと Codex Skill の組み合わせを作成・OSS 公開した。

Python スクリプトが提供する 5 つのコマンドを組み合わせ、セッション概要の取得→ボトルネック候補の集計→特定ツール呼び出しの詳細調査という段階的な絞り込みを行う構成。`overview` は直近セッションの概要（モデル名・ツール呼び出し数など）を出力し、`report` は大量出力・長時間処理・コマンド失敗・出力切り詰め・重複操作の 5 種類の無駄候補を集計する。`calls` は実行結果の全文を取得せず操作概要と文字数のみを返し、`detail` で特定ツール呼び出しの引数・出力・前後のコンテキストを上限文字数付きで確認できる。`message` ではユーザーや Codex のテキストメッセージを取得して当時の判断経緯を確認できる。SKILL.md には「対象特定→集計→必要な詳細調査の順に進める」「同じ情報を繰り返し取得しない」「十分な根拠が揃ったら調査を終了する」といったルールを追加し、Codex が不要な大量出力を避けるよう制御している。

3 セッション分の JSONL（合計約 540 万トークン）をこのスキルで分析したところ、実際にツールから Codex へ渡したトークン数は約 2.9 万トークンであり、JSONL 全文比で情報量を 99.46% 削減できたと報告されている。分析全体のトークン消費は約 43.5 万トークン、実行時間は約 119 秒。3 セッションに共通するボトルネックや個別の手戻りの原因、改善案の提示まで完了できたとしている。なお、これは JSONL 全文読み込みとの情報量比較であり、スキルなしの手法との厳密な比較実験ではないと著者は述べている。

#### [Claude Code で "Prompt is too long" と "Error during compaction: Conversation too long" が出たときの戻し方（/compact が効かない場合も）](https://qiita.com/homhom44/items/6cd66e20358d554fb8b1)
<sub>qiita ・ 2026-10-28</sub>

Claude Code 2.1.312（macOS 26.6）で確認されたコンテキスト上限超過エラーへの対処法をまとめた記事。会話・添付ファイル・ツール定義・メモリファイル（CLAUDE.md 等）の合計がモデルのコンテキストウィンドウを超えると `Prompt is too long` や `Context limit reached` が表示され新しい入力を受け付けなくなる。通常は自動コンパクションが先に働くが、`DISABLE_AUTO_COMPACT` で無効化されていたり、上限ぎりぎりまで膨らんでいたりすると `/compact` 自体がリクエスト超過で失敗する。

対処は上から順に試す。まず `/compact` を実行し、`Error during compaction: Conversation too long` が出たら Esc を 2 回押す（または `/rewind`）ことで数ターン前に戻り、再度 `/compact` する。次に `claude update` でバージョンを更新する（GitHub Issues #18211 では v2.1.11 で MCP と圧縮の相性問題が修正、Issues #23047 でも改善が行われたと担当者が回答しているが、その後も同問題の報告が続いているとされる）。最終手段は `/clear` で会話を破棄する。実行前に現在の状況と次にすることをファイルに書き出しておくと、少ないトークン消費で再開できる。

1 往復だけで上限に達する場合は `Prompt is too long · this conversation is a single exchange and cannot be compacted` と表示され、添付ファイルの縮小・`/mcp disable` による未使用 MCP サーバーの無効化・CLAUDE.md の削減が有効。`/context` コマンドでウィンドウの内訳（システムプロンプト・ツール定義・メモリファイル・メッセージ別）を確認できる。自動コンパクション失敗に原因（認証失敗・モデル利用不可等）が付いている場合はその原因を先に解消しないと `/compact` も同じ理由で失敗し続ける。Claude Code が知らないモデル ID を使っている場合はウィンドウが 200K とみなされ、200K 付近でエラーが出ることがある。

#### [medium 2 件でも確認役が「可」なら止まる：Claude Code の修正ループを空回しした結果](https://qiita.com/kaiyaku_iyada/items/f703fba0bb9bc76e3711)
<sub>qiita ・ 2026-10-28</sub>

Claude Code のデスクトップアプリのワークフロー機能を使い、有料版コンテンツの下書き修正に「直す役」と「確認役」の副エージェントをループで動かした運用記録。構成は「確認役が可を返すまで最大 3 周まわし、毎周新しい副エージェントを呼ぶ。不可なら確認役が返した問題の一覧を次の直す役へ渡す」というもの。可の基準は「high が 0 件かつ medium が 1 件以下」としている。直す役は読み違いと判断した場合は直さず理由を 300 字以内で返答し、確認役は JSON schema で `verdict`（可/不可）と `problems`（文字列配列）を返す。副エージェントはいずれも claude-opus-5-5 が使用された。

2026 年 10 月 20 日の実行では、1 回きりの台本での確認が不可（high 1 件・medium 3 件）となった後、ループの 1 周目で可（low 2 件）が返り終了した。1 回きり（約 11 分、241,128 トークン）とループ 1 周（約 7 分、224,407 トークン）の 2 回で完了した。

Node.js 24.14.1 を使った空回しテストで 3 シナリオを検証した結果、以下の 2 つの穴が確認された。シナリオ B（直す役が 1 件を読み違いとして断り続け、確認役が毎周それを挙げ直す）では 3 周すべて不可のまま 6 体を消費して終了する。台本には意見が割れた際に検出する仕組みがなく、3 周後の処理も未定義。シナリオ C（確認役が medium 2 件を挙げつつ verdict は「可」を返す）では、台本が verdict のみを見て止まるため基準を満たさないまま終了する。対策として、問題の重さ判定を schema の severity 欄で受け取り、可かどうかの判定を台本側で数えて行う形が有効だと述べている。また、1 回目と 2 回目で基準を変えた（high のみ→high かつ medium 1 件以下）理由が記録に残っていないことも課題として挙げている。
