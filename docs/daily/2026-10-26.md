#### [OpenAI・Anthropic が LLM 価格を数ヶ月で最大 80% 引き下げた理由](https://minimaxir.com/2026/10/cheap-llms/)
<sub>hacker-news ・ 40pt ・ 2026-10-25</sub>
<sub>**原題**: OpenAI and Anthropic cut their LLM prices by up to 80% within a few months. Why?</sub>

2026 年 6 月から 10 月にかけて OpenAI と Anthropic が主要 LLM の価格を段階的に引き下げた経緯と背景を、元 BuzzFeed シニアデータサイエンティストの Max Woolf が分析した記事。価格はすべて入力 MTok / 出力 MTok / キャッシュ読み取り MTok の順。

**価格変動の時系列**

2026 年 6 月 26 日、OpenAI は GPT-5.6 Sol（$5/$30/$0.50）・Luna（$1/$6/$0.10）・Terra を発表した。6 月 30 日、Anthropic は Claude Sonnet 5（$2/$10/$0.20、当初は期間限定価格としていた）を発表した。7 月 24 日、Anthropic は Claude Opus 5（$5/$25/$0.50）を発表した。一部のベンチマーク結果は Fable 5 を上回ったが、実世界の評価は賛否両論だった。

7 月 30 日、OpenAI は GPT-5.6 Luna の価格を 80% 引き下げ $0.20/$1.20/$0.02 とした。8 月 10 日、Anthropic は Sonnet 5 の価格引き下げを恒久化した。8 月 21 日、OpenAI は GPT-5.6 Sol を約 20% 引き下げ、向こう 3 ヶ月間 $4/$20/$0.40 とした。

9 月 1 日、Anthropic は Fable 5.1（$10/$50/$0.25）を発表した。Fable 5（$10/$50/$1.00）と比較してキャッシュ読み取りコストが 75% 削減された。コーディング用エージェントではキャッシュ読み取りコストがトークン総支出の 96〜99% を占め、キャッシュヒット率は 90〜100% に達するため、この 75% 削減はモデル利用コストの 70〜75% 削減に相当すると著者は指摘する。9 月 3 日、OpenAI は GPT-6 Astra（$10/$50/$1）を発表した。Fable 5.1 と同規模で性能は同等だが、キャッシュ読み取りコストの低減はない。

9 月 22 日、OpenAI は GPT-6 Sol（$2/$10/$0.20）と GPT-6 Luna（$0.10/$0.50/$0.01）を発表し、前世代から入出力コストを半額にした。同日 Anthropic は Claude Opus 5.5（$4/$20/$0.20）を発表した。Anthropic は「Opus 5.5 は Opus 5 より少ない計算量で提供でき、価格はそれを反映している」と説明しており、入出力コスト 20% 削減・キャッシュ読み取りコストのより大きな削減により、Fable 5.1 を上回る性能でトータルコストは 40〜60% 削減となった。

9 月 29 日、GPT-6 Sol が性能面で期待外れだったとして、OpenAI は 1 週間後に GPT-6.1 Sol（$2/$10/$0.10）を発表した。キャッシュ読み取りコストを半額にして Anthropic の「入力の 5%」比率に並び、6 月の GPT-5.6 ファミリー登場からの累計値下げ幅は 75% に達した。

**背景：オープンウェイトモデルとの競争**

著者はオープンウェイトモデルとの競争を価格低下の主因として挙げる。DeepSeek V4 Flash（2026 年 4 月）はキャッシュ読み取りコストが入力の約 2% と OpenAI・Anthropic モデルの 5〜10% より大幅に低く、OpenRouter 上で当時 13 社のプロバイダーが提供していた。更新版の DeepSeek Flash V4.1 1017 は Artificial Analysis インデックスで 45 点（前版 24 点）と性能が大きく向上し、OpenRouter 上の提供プロバイダー数は 29 社に増加した。DeepSeek 自身の価格は $0.15/$0.60/$0.003 で前版とほぼ同水準。著者は 7 月の GPT-5.6 Luna の 80% 値下げをこうした小型オープンウェイトモデルへの対抗として位置づける。

Moonshot AI が発表した Kimi K3.1 Pro は、Artificial Analysis インデックスで Opus 5.5（58 点）に匹敵する 55 点の性能を、同等のキャッシュ読み取りコストながら入出力は半額（$2/$10/$0.20）で提供する。重みは 11 月 4 日に公開予定で、現時点で Kimi K3 の重みを 20 社超が OpenRouter 上で提供していることから、同等の価格で多数のプロバイダーへの普及が見込まれる。さらに Kimi K3.1 Pro の価格は元の Kimi K3（$3/$15/$0.30）より低く設定されている。

Vercel の AI モデルゲートウェイのデータによれば、トークン単価は 2026 年 4 月比で 43.3% の水準まで低下している一方、モデルが安くなるペースより改善が速いため総支出額は増加している。

#### [Claude Code で何を送っても "API Error: 400 due to tool use concurrency issues" になる詰んだセッションの直し方](https://qiita.com/homhom44/items/8ec10d50d106821f4673)
<sub>qiita ・ 0pt ・ 2026-10-25</sub>

Claude Code で 400 エラーが出続け何を入力しても解消しない状態からの救済手順をまとめた記事。確認環境は Claude Code 2.1.310、macOS 26.6、2026-10-25。

**症状と原因**

発生するエラーは「API Error: 400 due to tool use concurrency issues. Run /rewind to recover the conversation.」または「`thinking` or `redacted_thinking` blocks in the latest assistant message cannot be modified.」のいずれか。会話履歴内の tool_use・tool_result・thinking ブロックの並びが API の期待する形と合わなくなっており、破損した履歴を毎回送り直すためループする。

公式 Error reference によると、同じ原因から発生する 400 エラーには 5 種類の表示がある：tool use concurrency issues、orphaned tool_result in conversation history、duplicate tool_use ID in conversation history、unexpected tool_use_id found in tool_result blocks、thinking blocks cannot be modified。

GitHub Issues へのユーザー報告として、ツール並列実行の中断・重い PreToolUse/PostToolUse フックの使用・plan モード終了直後・`--teleport` での別環境からのセッション持ち込み・複数 PDF の同時読み込み等がトリガーとして挙げられている（いずれも公式確認ではない）。thinking ブロックのエラーは `/resume` 直後やコンパクション後に起きやすいという報告もある。

**対処手順（上から順に試す）**

1. `/rewind`（または Esc を 2 回押す）：エラー発生前のチェックポイントを選んで会話を巻き戻す。公式も最初の対処として挙げている。VS Code 拡張で `/rewind` が出ない時期があり、その場合は `claude --resume` で CLI から同じセッションを開いて戻した例が報告されている。
2. `claude update` で更新後、終了して `claude --continue` で同じ会話を再開する。v2.1.156 より前では単純なツール使用でも発生し `/rewind` では直らなかった。
3. thinking のエラーのみ：Tab キーで thinking をオフにしてから送る（ユーザー報告、公式手順ではない）。
4. `/clear` で会話履歴ごと捨てる。文脈は失われるが確実に抜けられる。

最終手段として `~/.claude/projects/` 以下のセッション `.jsonl` を手動編集して壊れた thinking ブロックを取り除いたという成功報告が GitHub Issues に複数あるが、公式手順ではなくファイル形式は変わりうるため、実施する場合は事前のバックアップが必須。

#### [Claude Code v2.1.310 リリース：企業ゲートウェイの互換性問題が直った話](https://qiita.com/Sidejob/items/1ac689b79fd92be83f10)
<sub>qiita ・ 0pt ・ 2026-10-25</sub>

2026 年 10 月 24 日（UTC）にリリースされた Claude Code v2.1.310 の変更点を、大企業の社内環境で `claude -p` を使った自動化パイプラインを運用する立場から整理した記事。

**企業ゲートウェイ互換性の修正**

企業のセキュリティゲートウェイや社内プロキシが、Claude Code のリクエストに含まれる `effort-2025-11-24` というベータヘッダー値や、会話途中で追加されるシステムメッセージを不正なヘッダーとして拒否することで、リクエストが失敗するケースがあった。v2.1.310 からは該当環境を検出して自動リトライする際にこれらを除いた形で再送信するようになった。外部 API 通信をすべてセキュリティゲートウェイ経由にする大企業環境で特に出やすい問題だと著者は説明する。Azure API Management 等の独自リクエスト検査を入れている環境でも、会話途中で形式が変わるシステムメッセージが拒否されるケースがあった。

**バックグラウンドクリーンアップのバグ修正**

`cleanupPeriodDays` を大きい値に設定している場合、日時計算の誤りにより最近貼り付けた画像が「古いファイル」と判定され、バックグラウンドクリーンアップで誤って削除されるバグが修正された。「長く保持したいから大きい値を設定した」という意図が逆に働く、見つかりにくい問題だったと著者は説明する。

**Monitor ツールの拡張**

Bedrock・Vertex・Foundry 経由で Claude Code を動かしている環境でも Monitor ツールとプラグインモニターが使えるようになった。テレメトリや非必須トラフィックが無効になっている厳格なネットワーク制限環境でも動作する。長い前景スリープ（long foreground sleeps）もこれらの環境でブロックされるようになり、`claude -p` を使った無人実行パイプラインで意図せず長時間待機するケースを防ぐ。

**コンパクションの修正**

「Prompt is too long」エラー後のコンパクション処理で、base64 や SVG のような情報密度の高いテキストを含む会話が十分に圧縮されず次のリクエストも同じ理由で失敗するループが発生していた。この問題が修正された。長時間の自動実行パイプラインでスクリーンショットやグラフ・SVG ファイルを含む応答が積み重なる場合に出やすい問題だったとされる。

**Windows でのフック修正**

Git Bash がインストールされていない Windows 環境で、PreToolUse と PermissionRequest フックのコマンドが引用符で囲まれたパスのみの形式の場合に、本来ブロックすべきツール呼び出しを通してしまうバグが修正された。Windows のタスクスケジューラで Claude Code の自動実行を組んでいる環境でフックによるアクセス制御をしている場合に関係する変更。

**その他の変更**

VSCode 拡張でプランレビューカードの Enter キー操作でプランが誤って承認されるバグの修正、ブランチ切り替え後のクラウドセッションパネルのエラー修正。Enterprise クラウドセッションではクラウドセッションと Remote Control の権限をカスタムロールに追加（ロールごとのアクセス制御が可能になった）、クラウド環境設定のファイル読み込みボタン追加、エラー表示の改善、設定変更時の確認画面追加が行われた。非インタラクティブセッション（`-p`・Agent SDK）でのコンパクション時のメモリ使用量改善、tmux・kitty・Ghostty・iTerm2 での画像レンダリング改善も含まれる。

#### [Claude API の SDK 2.0.0 は temperature を引数で渡すと送る前に止まる——上げる前に探す行と 2 択](https://qiita.com/sumitsuke/items/0e2a4909594d15911a66)
<sub>qiita ・ 0pt ・ 2026-10-25</sub>

Anthropic SDK 2.0.0 で temperature を引数として渡すと送信前に TypeError が発生することを確認した検証記事。環境は Windows 11・Python 3.12・anthropic 0.101.0 と 2.0.0（実際の API は未使用、127.0.0.1 にローカルの受け口サーバーを立てて検証）。

**公式の仕様変更**

移行ガイド「Migrating to API version 2026-10-21」には「API 版 2026-10-21 では temperature・top_p・top_k を送ると 400 エラーが返る（デフォルト値でも同様）」「最新メジャーバージョンの SDK および CLI からはこれら 3 つのパラメータが削除された」と明記されている。

**検証結果（計 22 回実行）**

旧 SDK（0.101.0）で temperature を渡した場合は API 版 2023-06-01 のヘッダーで本文に temperature がそのまま届く。新 SDK（2.0.0）でパラメータなしの場合は API 版 2026-10-21 のヘッダーで届く。新 SDK（2.0.0）で temperature を引数で渡した場合は 4 回中 4 回すべて送信前に `TypeError: Messages.create() got an unexpected keyword argument 'temperature'` で停止した（デフォルト値の 1.0 を渡した場合も同様）。extra_body 経由で渡すと API 版 2026-10-21 のヘッダーで届くが、公式は 400 が返ると記載しているため逃げ道にはならない。

**バージョンアップ前の 3 つの対処**

1. **該当箇所の検出**：記事内で提供している AST ベースの Python スクリプトを使い、.py ファイル内で temperature・top_p・top_k を引数または辞書のキーとして渡している行を列挙する。値を変数から組み立てる箇所は静的解析では検出できないため、`grep -n "temperature\|top_p\|top_k"` との併用を推奨している。著者自身の手元の .py 897 本に適用したところ、Anthropic API に 3 つのパラメータを渡している箇所はゼロだった。
2. **外すか API 版 2023-06-01 に留めるかを選択**：公式の 2 択。デフォルト以外の値（たとえばより一貫した出力のための低 temperature）に依存している呼び出しは、パラメータを削除するか、そのリクエストだけ API 版 2023-06-01 に留める。
3. **SDK バージョンと API バージョンの対応を把握**：0.101.0 → 2023-06-01、2.0.0 → 2026-10-21。SDK を使わずに直接 API を呼ぶ場合は `anthropic-version` ヘッダーを 2026-10-21 に設定する。

なお、2.1.0（2026-10-22 時点の PyPI 最新版）は未検証。また、Claude Sonnet 4.6 等の temperature 非デフォルト値を受け付けるモデルへのリクエストはその効果が失われる点も注意が必要。
