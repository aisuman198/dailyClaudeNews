#### [「Claude のフルソナは何か？」とその他の問い](https://herecomesthemoon.net/2026/11/whats-claudes-fursona/)
<sub>hacker-news ・ 176pt ・ 2026-11-27</sub>
<sub>**原題**: "What's Claude's fursona?" and other questions</sub>

各 AI モデルに「フルソナ（furry サブカルチャーで自分を代表する動物キャラクター）があるとしたら何か」と 50 回ずつ問い、回答を集計した調査記事。OpenRouter API を通じて約 20 モデルを対象に実施し、Claude Haiku 5.5 でデータを注釈した。総費用は約 50 ドル。

Claude モデルの傾向として、コルビッド（カラス等）やタコを選ぶことが多い。Claude Fable 5.2 はコルビッドを 35/50 回選択し、生成した画像のほぼすべてに真鍮の鍵を含めたとしている。Claude Opus 5.5 はタコを 40/50 回選択した。Claude モデルは他のモデルが外見を重視するのとは対照的に、行動や性格でフルソナを説明する傾向があると分析されている。スカーフ・鍵・温かい飲み物のマグカップが画像に繰り返し登場した。

Gemini モデルはサイバネティクスや LED バイザー顔の「プロトゲン」（furry コミュニティ発祥の種族）を一貫して好む傾向があり、ネオン・サイバーパンク的な美学が全 Gemini モデルに共通していた。GPT-6.2 Astra は他の GPT モデルとは異なり、ガ（蛾）を一貫して選択し（38/50）、「Lumen」「Margin」等の名前をつけることが多かった。Grok 4.7 は疲れ果てたキツネがオフィスで働く現代的なイメージを一貫して選んだ。モデル全般の傾向として、人間の furry に人気な狼・猫・ドラゴンはほとんど選ばれなかった。ほとんどのモデルはジェンダーに言及せずキャラクターをデフォルトで they/them として扱った。

調査は 3 つの分析で構成される。テキストでのフルソナ回答（各モデル 50 回クエリ）、SVG 生成（各モデル 3 クエリ×6 回イテレーション）、画像生成プロンプトの作成（各モデル 3 クエリ×3 回イテレーション）である。SVG と画像生成ループでは Claude Fable 5.2 で Python スクリプトをブートストラップし、Haiku 5.5 でデータを注釈した。

品質維持の核心は、AI のセッション記憶に依存せず、人物設定・世界観・年表・章構成・伏線などの「正典」をすべてリポジトリのファイル（bible/・plot/・log/・chapters/）に置く設計にあった。CLAUDE.md に「ファイルの記述を会話の記憶より必ず優先する」と最重要ルールとして明記し、章ごとに新しいセッションで書き始める運用とした。エージェントへの指示ファイル（CLAUDE.md / AGENTS.md 等）はツール別に分けつつ、作品の事実ファイルは両エージェントで共通とした。

品質維持には 4 つのスキルを整備した。`/write-chapter` は生成モデルが字数目標に対して短く書く傾向と自己申告での認識不能を考慮し、コマンドによる字数の実測と 8 割未満での加筆を義務付けた。`/polish` は推敲スキルで 7 つの観点を 1 つずつ確認し、修正案を出した時点で作者の判断を挟む設計にした。`/continuity-check` は書いた本人の見落としへの対策として、整合性確認を別のエージェント（continuity-checker subagent）に担わせ、使用可能ツールを Read・Glob・Grep のみに制限して本文改変を防止した。`/build-book` は EPUB と HTML の私家版を組み立てるスキルである。

つまずいた点として次の 3 点を挙げている。まず Claude 用と Codex 用でスキルの内容がずれていき、章によって推敲の観点が異なる状態が生まれた。次に、クラウドセッションで `wc -m` がロケール非 UTF-8 のためバイト数を返し、6,500 字程度の章が 14,568 と誤計測された（`LC_ALL=C.UTF-8` で解決）。最後に、どちらのエージェントで書いたかがコミット履歴から判別できなかった。これらの教訓はテンプレートリポジトリ（tadanok/novel-template）に反映した。

#### [claude-code-action で "SDK execution error" と "Claude Code native binary not found" が出たときの直し方](https://qiita.com/homhom44/items/f61e4877d7400be7f4c8)
<sub>qiita ・ 1pt ・ 2026-11-26 ・ 継続話題（2回目）</sub>

GitHub Actions の anthropics/claude-code-action において `SDK execution error: ReferenceError: Claude Code native binary not found at /home/runner/.local/bin/claude` または `SDK execution error: Error: Claude Code process exited with code 1` が発生した際の調査と対処法をまとめた記事。確認環境は Claude Code 2.1.332・macOS・2026-11-27 時点。

`native binary not found` については、claude-code-action v1.0.218（2026-09-08 リリース、Claude Code 2.1.265 に更新したリリース）以降の ubuntu-latest 環境で、インストーラが終了コード 0 を返しながらも `/home/runner/.local/bin/claude` を作成しない問題が issue #1817 で報告されている。同一の SHA・バージョン・ランナーイメージで 45 分の間に成功と失敗が混在するケースもあり、ランナー側の環境への依存が疑われる。修正 PR（#1848、インストール後に実行ファイルの存在を確認する内容）は 2026-11-27 時点で未マージ。なお、アクション本体は現在 Claude Code 2.1.332 を入れる構成になっている。

`exited with code 1` については原因が複数存在し、API の残高不足、提供終了済みモデル ID の使用（`claude_args` で現行モデルを `--model` で明示すると解消）、`claude_args` への `--output-format json` 指定（アクションが stream-json で動かすため競合）等が issue #892 に報告されている。また issue #1205 の `Internal error: directory mismatch for directory ".../tsconfig.json"` も同じ `exited with code 1` の形で出る場合があり、CLAUDE.md がシンボリックリンクだった際の問題（issue #1187）の二次症状との推測がある。

対処法として、(1) 動作していた時点のコミット SHA（v1.0.217 相当: `9c5ddab2e6d17b83ea679153b31f1d5f023cf636`）にアクションを固定する、(2) `path_to_claude_code_executable` 入力で Claude Code を事前インストールしてパスを渡す、(3) 環境変数 `DEBUG_CLAUDE_AGENT_SDK=1` を設定して子プロセスの実際のエラーを表示させる（`show_full_output: true` だけでは起動直後に落ちたときのエラーは表示されなかったとの報告あり）、の 3 つを紹介している。

#### [Codex CLI に貼った API キーは ~/.codex/sessions と SQLite に平文で残る](https://qiita.com/supportapp3/items/48ddf2dba69dc2382f41)
<sub>qiita ・ 0pt ・ 2026-11-27</sub>

Codex CLI 0.172.0 および 0.171.0 において、プロンプトに入力した API キーがどこに残るかをダミーキーで検証した記事。HOME をクリーンな環境に向け、127.0.0.1 上のモックサーバーに接続した状態で確認した。

`codex exec` 1 回の実行で、API キーは `~/.codex/sessions/<日付>/rollout-*.jsonl`・`state_5.sqlite`（threads テーブルの title・first_user_message・preview 列）・`thread_history_1.sqlite`（thread_items テーブルの item_json 列）の 3 か所に平文で保存された。threads.title にはプロンプトの先頭がそのままタイトルとして入るため、キーを含んだまま記録される。

jsonl ファイルを `rm` しても SQLite 2 ファイルにはキーが残り、`codex archive` は jsonl を別ディレクトリに移動するだけで SQLite にも残る。`codex delete` を実行すると jsonl と SQLite の行は消えるが、ファイル自体に `grep -a` で文字列が残る。これは SQLite の `secure_delete` が無効（デフォルト）であるためで、Codex プロセスを停止した上で `VACUUM` と WAL チェックポイントを実行することでファイルからも消えることを確認した。なお、この操作は Codex の公式手順ではない。

`codex exec --ephemeral` を使用した場合は jsonl にも SQLite にも一切残らなかった。一方、`-c 'history.persistence="none"'` オプションは rollout と SQLite への保存を止めなかった。

推奨対応として、(1) 貼ってしまったキーをまず無効化して作り直す、(2) `codex delete` で会話ごと削除後 VACUUM を実行する、(3) 一回限りの操作は `codex exec --ephemeral` を使う、(4) そもそもキー自体をプロンプトに貼らず環境変数の名前だけを伝える、を挙げている。
